## A. Вехи в ленте сайта и в канале

РЕШЕНИЕ ЗАФИКСИРОВАНО: веха — НЕ вторая карточка в `deals[]`, а запись
ленты, указывающая на ту же карточку. Каждый случай «одна сделка — две
карточки» в истории проекта признавался дефектом и сливался скриптом
(Астра, ВТБ/RWB); на отдельных карточках ломаются счётчики (профили
компаний, аналитика, TOTAL_DEALS) и дедупликация притока. Читательский
сценарий владельца при этом сохраняется целиком: своя строка в ленте со
своим заголовком и датой вехи, свой пост в канале, своя страница момента
(страница этапа из части 1).

Данные:
- `events[].headline` — новое поле: человеческий заголовок вехи
  («Правкомиссия одобрила покупку Компании А»). Пишется рутиной при
  создании вехи, проходит консоль (см. ниже), правится ответом-текстом
  как обычный пост. `dealEvents()` уже читает `e.headline` в
  `historicalTitle` — проверить и использовать.
- Закрытый список постворси-видов: `approval`, `closed`, `cancelled`
  (`signed` — обсудить с владельцем отдельно, в v1 не включать).
  Существенное изменение цены/периметра видом события не является — в v1
  не веха.

Создание вехи (шаг почасовой рутины притока, после enrich):
- Если `enrich.py` добавил к карточке, УЖЕ находящейся в базе на сайте,
  событие постворси-вида — рутина тем же прогоном: вычитка карточки
  (Шаг 0 REVISION_BRIEF) → `review.py <id> --milestone <kind> --write`
  (снимок берётся ДО обогащения более поздними фактами — порядок важен,
  см. предупреждение в REVISION_BRIEF) → пишет `headline` → черновик
  поста вехи в консоль.
- Если карточка ещё в pending — веха не нужна: карточка сама ещё новость.
- ДЕДУП СОБЫТИЙ ОБЯЗАТЕЛЕН ДО ЭТОГО ШАГА: `enrich.py` не должен
  добавлять второе событие того же `kind` (два издания об одном
  одобрении ФАС = одно событие). Проверить, есть ли guard; нет — добавить
  с тестом. Ключ дедупа вехи: стабильный `event.id` (`<deal_id>-<kind>`,
  часть 1 уже присваивает).

Лента сайта (`static/index.html`):
- Сборщик ленты объединяет карточки и вехи: веха = {deal, event} с
  `newsworthy` и `headline`, дата — дата события. Отдельный видимый
  признак (чип «Веха · Согласование» / «Веха · Закрытие»).
- Клик по вехе → `#/deal/<id>` (актуальная карточка; блок «Ход сделки»
  уже сам появляется при 2+ этапах, ранние этапы уже кликабельны).
- ЗНАМЕНАТЕЛИ НЕ ТРОГАТЬ: TOTAL_DEALS(), аналитика, счётчики профилей
  считают ТОЛЬКО карточки. Тест: пометка вехи не меняет число сделок на
  главной и в аналитике.
- `isDealShownOnSite()` применяется к родительской карточке вехи.

Канал:
- Поправка к правилу «одна сделка — один пост» (CLAUDE.md обновить):
  один ЖИВОЙ пост (редактируется «⟳ Обновлено») + отдельные посты-вехи
  по закрытому списку видов, каждая — через консоль.
- Черновик вехи в консоль: сообщение вида «📌 [веха <deal_id>:<kind>]»
  с теми же кнопками, что у поста (пост в канал / без поста), ответ
  текстом заменяет текст поста вехи. Callback-регэксп в `main.py`
  (`mod:...`) расширить: разделитель `deal_id` и `kind` — символ,
  проходящий `[\w-]` (использовать `~`, двоеточие не пройдёт).
- Молчание сутки = веха выходит (как карточки). `check_post.py`
  вычитывает пост вехи как обычный.
- Когда веха-пост создан, СТАРЫЙ механизм для этого же события
  (редактирование живого поста с уведомлением) уведомление НЕ шлёт —
  двойной сигнал читателю запрещён; живой пост просто получает
  «⟳ Обновлено» без нотификации. Закрытие сделки сегодня идёт
  «исключением» через живой пост — при включении вех закрытие становится
  вехой, исключение из send_telegram снять.
- `telegram_posts[deal_id]` расширить: `{...как сейчас, stage_posts:
  {event_id: {message_id, at}}}`. Старые записи без stage_posts — норма.
- Дедуп постов: один event_id — один пост, повторная попытка — отказ.

Тесты: инвариант test_data «каждая веха ссылается на существующее
событие существующей карточки и несёт headline»; UI-тест «веха в ленте
открывается, счётчик сделок не изменился»; ingest-тест «второе событие
того же kind не добавляется»; постовый тест «на событие с вехой не
уходит двойное уведомление».

## B. Цветные плашки статусов

НОВЫЙ СТАТУС В ДАННЫЕ НЕ ЗАВОДИТЬ. «Обсуждается» уже покрывает и
переговоры, и планы («Лента может купить») — отдельное значение

- «Обсуждается» — синяя плашка;

- «Закрыта» — зелёная (как сейчас);
- «Не состоялась» — красная/серая (как сейчас).
Применить ВЕЗДЕ, где рендерится статус: лента, шапка карточки, страница
этапа, компактная строка «Ход сделки». Проверить контраст в обеих темах
(тёмная — отдельно). Playwright: по одной карточке каждого статуса, обе
темы, 360/1280.

## D. Предварительный отсев сырья («сомнительных») перед консолью

БОЛЬ: владелец вчера вручную отбросил ~100 мусорных «сомнительных»
(свадебный «выкуп», макроэкономика, потребительские гайды). Механический
фильтр это не возьмёт — нужен отсев моделью, благо приток теперь
почасовой и модель уже в контуре.

Новый шаг рутины притока между promote и send_drafts. Контракт:
- Скрипт `pipeline/ingest/raw_screen.py`:
  - без аргументов: печатает свежие неотправленные сомнительные
    (id | заголовок | причины ворот | ТОП-СОВПАДЕНИЕ С БАЗОЙ через
    matcher: id карточки + сила сигнала — для распознавания «это
    дополнение, а не новая»);
  - `--drop <id> <id> … --reason "…" --write`: помечает
    `decided_raw[id]='auto-drop'` + `raw_titles` (не покажутся никогда);
  - `--enrich <id>=<deal_id> --write`: помечает «это дополнение к
    существующей карточке» — сырьё не идёт в консоль, а встаёт в
    очередь обогащения (рутина читает статью и несёт факты в указанную
    карточку через review.py; случай Alumni Partners/«Полекс» —
    объявление консультанта об уже известной сделке, самое ценное — имя
    консультанта в law.adv).
- Рутина (модель) судит каждый пункт по трём классам:
  1. МУСОР УВЕРЕННО → --drop;
  2. похоже на сделку ИЛИ непонятно → в консоль, как сейчас;
  3. совпадает с существующей карточкой → --enrich.
  ПРИ СОМНЕНИИ — ПОКАЗЫВАТЬ. Правило дома: терять сделку молча дороже,
  чем показать человеку лишнее.

  СПИСОК КЛАССОВ «МУСОР УВЕРЕННО» — ИЗМЕРЕН, А НЕ НА ГЛАЗ (21 августа,
  118 реально восстановленных заголовков из истории `decided_raw`/
  `raw_titles`, drop-решения владельца + все 12 take для контроля нулевых
  ложных срабатываний):
  - свадьбы, похороны/кладбища, личный быт («Купить место на кладбище
    можно через Госуслуги», «Выкуп, каравай и икона в банкетном зале»);
  - макроэкономика/госфинансы без конкретной сделки (курсы, статистика,
    межгосударственная сырьевая торговля вроде «Россия купила у Бразилии
    какао-бобы», комментарии ЦБ);
  - потребительские гайды и советы («риски при покупке квартиры»,
    опросы вроде «Больше половины владельцев iPhone готовы купить
    Android»);
  - спорт (трансферы игроков, результаты матчей — «"Барселона" купит у
    "Манчестер Сити" Родри», «"Фенербахче" и "Лион" сыграли вничью»);
  - политика/геополитика без сделки, включая метафорическое
    «купил»/«продал» («Пашинян не продал абрикосы европейцам», «Белый
    дом перешёл к стратегии удушения Ирана»);
  - НОВОЕ, не было в списке владельца: мошенничество/криминал, где
    «покупка»/«продажа» — способ обмана, не предмет статьи («Мошенники
    начали продавать фейковые билеты», «кража данных карт под видом
    продажи формы»);
  - НОВОЕ: вакансии («Вакансия Менеджер проектов M&A в Т-банк»);
  - НОВОЕ: вебинары и образовательный контент про M&A вообще, не про
    конкретную сделку («Личный фонд в структуре сделки — на вебинаре...»);
  - НОВОЕ: дайджесты и подборки — шире, чем текущий `DIGEST` в
    classify.py: не только «топ-N», но и «Крупнейшие M&A-сделки в
    российском АПК за год», «Продажа ТРЦ и новые деревья: главное в
    Кургане за 13 августа».
  ПРОВЕРЕНО НА СЕБЕ: ни один из 12 заголовков `take` не подходит ни под
  один из этих классов — ложных auto-drop на реальных сделках при этом
  замере ноль. Список заведомо неполон (собран по ОДНОЙ партии решений,
  как и любой словарь в этом проекте) — расширять по мере находок, тем
  же приёмом: замер по `decided_raw` перед тем, как добавить класс.

  ОТДЕЛЬНАЯ НАХОДКА ТОГО ЖЕ ЗАМЕРА: одна и та же несостоявшаяся история
  («Рижский вокзал») встретилась в отброшенном сырье ЧЕТЫРЕ раза за
  месяц с разными формулировками («не состоялась в третий раз», «снова
  не состоялась», «вновь не состоялась») — точный `raw_key()` их не
  склеивает. Это не мусор в смысле «не по теме», а ПОСТОЯННО
  ПОВТОРЯЮЩАЯСЯ НЕ-НОВОСТЬ: `raw_screen.py` показывает список одним
  экраном, и рутина, увидев несколько похожих заголовков подряд, может
  выкинуть их одним вызовом `--drop <id1> <id2> ... --reason "..."`
  (флаг уже поддерживает несколько id) — отдельного кода для склейки
  такого класса не потребовалось.
- ЗАМЕР ДО ВКЛЮЧЕНИЯ — СДЕЛАН (см. выше, цифры и заголовки — в этом
  файле, не только в докстринге скрипта, чтобы не потерять при следующей
  правке `raw_screen.py`): 0 ложных auto-drop на 12 take, список классов
  уточнён по 118 реальным drop. Из повторного профильного риска —
  границы найденных классов узкие и текстовые (конкретные слова:
  «кладбище», «свадьб», «вакансия», спортивные клубы), не «любая
  недвижимость»/«любая политика» — так же, как остальные словари
  проекта, держать узко и расширять по находкам, а не расширять формулировку
  заранее «на всякий случай».
- Отчётность: `ops_status.py приток` получает параметр `--screened <N>`
  («отсеяно автоматически: N») — ноль тоже печатается. Авто-дропы
  остаются в moderation_state (git) с причиной — аудит возможен всегда.
- Отдельный класс — СП: «Правительство одобрило создание СП X и Y»
  режется воротами за «нет предмета», хотя у СП предмета-покупки и не
  бывает. В ворота правило НЕ вносить без замера; в v1 отсев помечает
  такие «похоже на СП: стороны есть, предмет — само СП» и показывает
  человеку с этой подсказкой.
- Его ручные drop — размеченный корпус для learn.py: отдельной задачей
  прогнать по нему кандидатов на 2–3 дешёвых механических правила
  (свадебная лексика, «сколько стоят»-гайды), каждое — с замером полноты
  по своей базе (не потерять «тендерное предложение о выкупе»).
