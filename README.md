# КОМПАС

Платформа о сделках, компаниях и консультантах российского рынка. Карточки собираются из публичных источников, объединяют новости об одной сделке в единый жизненный цикл и показывают сведения через две профессиональные линзы: «Экономист» и «Юрист». 

## Что уже работает

- лента сделок с поиском, фильтрами, несколькими отраслями и сохранением подборок;
- карточки сделок со сторонами, предметом, суммой, структурой, согласованиями, консультантами и источниками;
- этапы сделки: переговоры, подписание, согласование, закрытие или срыв;
- профили компаний и консультантов, отраслевая аналитика, связи по сделкам и сравнение до трёх компаний;
- ИИ-ассистент по базе и, при настройке, по свежей выдаче Яндекса;
- вход по email и паролю, подписки, комментарии и обращения в редакцию;
- подписка на конкретную сделку, личная лента уведомлений, недельная сводка, почта и Telegram;
- сохранённые диалоги с ассистентом, вебинары, копирование/публикация ссылок и PDF-экспорт для платной подписки;
- готовый контур ЕГРЮЛ и БФО: сопоставление юрлиц, финансовая история, история участников, изменения и исходные документы;
- пайплайн сбора, классификации, дедупликации, обогащения и ручного допуска новых карточек.

Данные могут быть неполными или содержать ошибки: платформа не достраивает неизвестные факты догадками и сохраняет ссылки на первоисточники.

## Локальный запуск

```bash
pip install -r requirements.txt
uvicorn main:app --reload
# http://127.0.0.1:8000
```

Тесты:

```bash
python3 -m pytest -q
```

## Переменные окружения для production

Обязательные для полноценного запуска:

- `DATABASE_URL` — PostgreSQL, только для аккаунтов (вход, подписки,
  уведомления, комментарии) — сама база сделок и компаний в SQL не хранится,
  читается из `static/data/*.json` и эта переменная ей не нужна; без
  `DATABASE_URL` аккаунты работают на локальной SQLite;
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM` —
  уведомления и недельная сводка (для входа с 2 августа 2026 не нужен —
  вход по email и паролю, без письма);
- `COOKIE_SECURE=true` — secure-cookie на HTTPS;
- `APP_BASE_URL` — публичный адрес для ссылок из писем и Telegram;
- `API_FNS_KEY`, опционально `API_FNS_BASE_URL`, `API_FNS_TIMEOUT`, `API_FNS_MIN_INTERVAL` — ЕГРЮЛ и БФО;
- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET` — Telegram-уведомления (личные, боту в личку). Трёх переменных мало: пока не выполнен `python3 pipeline/publish/setup_telegram_webhook.py --write`, Telegram не знает, куда слать `/start`, и привязка бота к аккаунту не завершается — молча, без ошибки на экране;
- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHANNEL_ID` — автопостинг сделок в канал (`pipeline/publish/send_telegram.py`); токен один и тот же, `TELEGRAM_CHANNEL_ID` — отдельная переменная (`@username` канала или числовой id);
- `TELEGRAM_API_BASE` — релей до Bot API (Cloudflare Worker). На российском хостинге практически обязателен: прямая связь Timeweb → `api.telegram.org` даёт около трети отказов на соединение. Пусто = прямой `api.telegram.org`.

Полный шаблон: `.env.example`.

Личные уведомления по подпискам («сообщи о сделках в отрасли X от суммы Y»)
рассылает САМ САЙТ на старте после деплоя (`subscription_feed.scan_on_startup`),
а не приток: приток работает в одноразовом контейнере в другом облаке, а база
пользователей стоит во внутренней сети хостинга и оттуда недостижима.
Отдельного расписания у сверки нет и не нужно — новые карточки попадают на
сайт ровно одним способом, деплоем нового `deals_promoted.json`. Первый прогон
на пустой таблице `deals_seen` никого не уведомляет, а только запоминает состав
базы: иначе подписчик получил бы залп по всей истории рынка.

Для ИИ-ассистента и веб-поиска:

- `YANDEX_API_KEY`;
- `YANDEX_FOLDER_ID`;
- опционально `YANDEX_MODEL`, параметры поиска из `yandex_search.py`.

Без ключей ИИ фронтенд и база продолжают работать, а ассистент возвращает локальный fallback.


## Подключение API-ФНС

Интеграция уже подготовлена. Внешний API не вызывается при обычном открытии карточки: сведения сначала загружаются в собственную БД, нормализуются и затем быстро отдаются интерфейсу. Неоднозначное совпадение по названию не публикуется автоматически.

После обновления файлов и получения доступа:

```bash
pip install -r requirements.txt
python3 pipeline/migrate_launch_db.py
export API_FNS_KEY="ваш-ключ"
python3 pipeline/sync_fns.py --all --auto-confirm
```

Команда выполняет три стадии:

1. переносит 1 800+ публичных профилей компаний из JSON в SQL;
2. ищет российские юридические лица и автоматически подтверждает только строгие уникальные совпадения;
3. загружает ЕГРЮЛ, БФО и историю изменений для подтверждённых ИНН.

Сомнительные варианты сохраняются в `legal_entity_candidates` для редакционной проверки и не показываются пользователям. Очередь можно проверить в Excel:

```bash
python3 pipeline/review_fns_candidates.py --export fns-review.csv
# поставить yes в колонке approved у правильных строк
python3 pipeline/review_fns_candidates.py --import-file fns-review.csv
python3 pipeline/sync_fns.py --sync
```

Конкретную компанию также можно подтвердить вручную и затем синхронизировать:

```bash
python3 pipeline/sync_fns.py --company-id citibank --inn 7710401987
python3 pipeline/sync_fns.py --sync --company-id citibank
```

Проверка без записи в БД:

```bash
python3 pipeline/sync_fns.py --seed --dry-run
python3 pipeline/sync_fns.py --match --auto-confirm --limit 100 --dry-run
```

Интерфейс автоматически показывает подтверждённые данные в карточках компаний и финансовый контекст участников в сделках. Бесплатный пользователь видит последний отчётный год и последние изменения; полная история и исходные файлы доступны платному пользователю. Для банков и других организаций, отсутствующих в ГИР БО, интерфейс не выдаёт отсутствие данных за нулевые показатели.

## Где лежат данные

- `static/data/deals_promoted.json` — единственный источник данных о сделках и
  компаниях: интерфейс читает только его, приток пишет только в него;
- `static/index.html` — интерфейс: стили и рендер, данных о сделках в нём нет;
- `db/models.py` — нормализованная SQL-схема, аккаунты, подписки, комментарии и редакционные обращения;
- `pipeline/ingest/` — регулярный приток новых публикаций и обновлений существующих сделок.

Сделки пока читаются фронтендом из JSON. SQL-схема уже существует, но переход к единому каноническому хранилищу остаётся задачей до масштабирования.

## Как устроены приток и качество данных

Три рутины, три разных глагола — они не дублируют друг друга, а покрывают три разные вещи, которые происходят с данными:

| рутина | когда | что делает |
|---|---|---|
| **приток** | раз в сутки | новости → черновик → карточка, под присмотром человека |
| **публикация** | ежечасно, днём | решения из консоли → сайт → пост в Telegram-канал |
| **качество** | ежечасно | сначала видимые поломки, потом дочитывание старых карточек |

### Приток: от новости до карточки

```
fetch → triage/classify → match → enrich / draft → promote → review → консоль модерации
```

- `pipeline/ingest/fetch.py` — забирает сырьё из реестра источников (`pipeline/ingest/sources.json`), ничего не решает;
- `pipeline/ingest/classify.py` — фильтр «это вообще сделка?»;
- `pipeline/ingest/match.py` — это НОВАЯ сделка или продолжение уже известной (индекс строится по ВСЕЙ базе: и `deals_promoted.json`, и кураторским карточкам внутри `index.html`);
- знакомой сделке `pipeline/ingest/enrich.py` дополняет только пустые поля и двигает статус только вперёд, никогда не переписывает то, что уже подтверждено;
- новой — `pipeline/ingest/draft.py` строит черновик, `pipeline/ingest/promote.py` пропускает его через ворота (дубль? валюта словом? одна сторона в двух ролях?) и решает: пустить / отдать человеку / отказать;
- `pipeline/ingest/review.py` — «проверка чтением»: каждая правка обязана нести дословную цитату источника (см. ниже) — это то, что не даёт модели придумывать факты;
- всё, что прошло ворота, уходит не в базу напрямую, а в Telegram-консоль основателей (`pipeline/publish/send_drafts.py`) с кнопками «опубликовать / придержать / изменить / выкинуть» — решения возвращаются через вебхук в `main.py` и применяет их `pipeline/ingest/approve.py`.

### Качество: review.py и дословная цитата

Любая правка существующей карточки — новая сумма, статус, согласование, структура сделки — идёт через `pipeline/ingest/review.py` и таблицу `FIXES` в `pipeline/ingest/fixes/*.py`. Механика простая и жёсткая: значение обязано быть **дословной подстрокой** цитаты из реально скачанного текста источника (`data/inbox/raw/*.jsonl`, качается `pipeline/ingest/fetch_article_texts.py`). Разрешено вырезать лишнее и поставить заглавную букву — сочинить, переформулировать или домыслить нельзя, скрипт откажет сам. Так же проверяются дата (день/месяц внутри уже известного года), статус и отрасль (только слово из закрытого словаря). Правки, которые не сводятся к этой модели (слияние дублей, смена года у даты, точечные структурные исправления), — отдельные одноразовые скрипты в `pipeline/` с `assert` на исходное состояние поля, а не запись в `deals_promoted.json` руками.

Двухуровневая очередь дочитывания (`pipeline/ingest/REVISION_BRIEF.md`, поле `deep_researched`/`followup_researched`): первый уровень — полный обыск карточки по всем источникам, какие вообще есть в интернете, не только по тем 51 ленте, что видит приток; второй — месячная дельта поверх уже сделанного первого уровня (ловит то, что стало известно уже ПОСЛЕ первого прохода — интервью, поздние объявления юрфирм). На август 2026 у **1371 из 1568 карточек (87%)** есть хотя бы один проход «прочитано против источника, ничего не выдумано» (`reviewed`); из них **1359 прошли и полный глубокий обыск** (`deep_researched`), а 183 — ещё и второй, месячный уровень (`followup_researched`).

### Ручные миграции

Правки данных — только скриптом в `pipeline/`, с сухим прогоном без аргументов и записью по `--write`; ручная правка JSON руками не переживёт следующий прогон рутины. Для текущих кураторских исправлений:

```bash
python3 pipeline/fix_curated_cards.py --write
python3 pipeline/merge_deal_histories.py --write
```

Новая самостоятельная карточка проходит через `pipeline/ingest/promote.py`. Полностью автоматическая публикация новых карточек намеренно отключена флагом `NEW_CARDS_NEED_REVIEW`: первый прогон на живом потоке показал высокий риск ложных срабатываний классификатора — решение по новой сделке всегда принимает человек в консоли.

## Деплой

Проект запускается через `Procfile`. Перед публичным запуском необходимо:

1. подключить постоянный PostgreSQL и SMTP;
2. применить миграцию данных в SQL либо зафиксировать резервное копирование JSON и БД;
3. настроить мониторинг ошибок, логирование и резервные копии;
4. настроить SMTP, зарегистрировать вебхук бота (`python3 pipeline/publish/setup_telegram_webhook.py --write` — один раз с боевого хоста, иначе привязка Telegram к аккаунту не завершается) и еженедельный cron `python3 pipeline/send_weekly_digest.py`;
5. подготовить административную очередь комментариев и обращений;
6. добавить правовые документы и политику обработки данных.

Подробный продуктовый и коммерческий аудит: `LAUNCH_AUDIT.md`. Продуктовые ориентиры по зарубежным аналогам: `PRODUCT_RESEARCH.md`. Редакционный стандарт: `COPY_AUDIT.md`.
