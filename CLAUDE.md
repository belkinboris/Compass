# Правила работы в репозитории «Компас»

Читать вместе с `PRODUCT_ROADMAP.md` (принципы, бэклог, журнал). Здесь — техника:
как устроен репозиторий, чем запускать, что проверять и какие соглашения приняты.

## Что это

Одностраничное приложение о сделках M&A российского рынка. FastAPI отдаёт
статику, весь интерфейс — один файл `static/index.html` (~1900 строк, без
сборки и без внешних зависимостей). Данные лежат в JSON и подгружаются на клиент.

## Структура

```
main.py                       FastAPI: раздача статики, /health, /api/ask
yandex_search.py              обёртка над Яндекс XML-поиском (для ассистента)
test_kompas.py                17 тестов: yandex_search + /api/ask
test_data.py                  23 теста: инварианты базы (без браузера)
test_ui.py                    16 тестов: дымовые проверки экранов (Playwright)
.github/workflows/tests.yml   CI: данные и API отдельно, интерфейс отдельно
static/index.html             ВЕСЬ интерфейс: стили, данные-константы, рендер
static/data/deals_promoted.json   основная база (1333 сделки, 1846 компаний)
static/data/bulk_deals.json       компактные записи
static/data/deals_2026.json       исходник по 2026
pipeline/                     скрипты разбора и чистки данных
```

Внутри `static/index.html`:
- `COMPANIES`, `DEALS`, `FIRMS`, `INDUSTRIES` — захардкоженные кураторские данные;
- `loadBulkDeals()` подмешивает `deals_promoted.json` к `DEALS` и `COMPANIES`;
- `route()` — хеш-роутер; `render*()` — по экрану на функцию.

## Запуск и проверка

```bash
uvicorn main:app --reload            # http://127.0.0.1:8000
python3 -m pytest -q                 # 56 passed: 17 API + 23 данных + 16 интерфейса
python3 -m pytest test_data.py -q    # только инварианты базы, без браузера (0,1 с)
```

Три набора тестов:

| файл | что проверяет | нужен браузер |
|---|---|---|
| `test_kompas.py` | `yandex_search` и `/api/ask` | нет |
| `test_data.py` | инварианты базы: ссылки, роли, соглашения о записи | нет |
| `test_ui.py` | экраны открываются, не падают, не переполняют | да |

Скриншоты и проверка интерфейса — Playwright, браузер уже стоит:

```python
br = await p.chromium.launch(executable_path="/opt/pw-browsers/chromium")
```

Не запускать `playwright install` — браузер предустановлен
(`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`). Это правило про ЭТУ машину: в CI
(`.github/workflows/tests.yml`) Chromium ставится явно, потому что там его нет.
`test_ui.py` использует предустановленный путь, только если файл существует.

## Обязательная проверка перед коммитом

1. `python3 -m pytest -q` — 56/56. Инварианты базы и дымовые тесты интерфейса
   теперь живут в `test_data.py` и `test_ui.py`, а не в одноразовых скриптах.
2. **Семантический diff JSON**, а не глазами по строкам: сравнить с `HEAD` и
   убедиться, что изменились только те поля, которые собирались менять, а состав
   сделок, профилей компаний и `match_keys` не поехал:

```python
old = json.loads(subprocess.run(['git','show','HEAD:static/data/deals_promoted.json'],
                                capture_output=True, text=True).stdout)
new = json.load(open('static/data/deals_promoted.json'))
# сравнить set(id), companies, match_keys и посчитать, какие поля изменились
```

3. Для правок интерфейса — Playwright: страницы открываются, в консоли нет
   ошибок, нет горизонтального переполнения на 360 / 390 / 1280:

```python
await pg.evaluate("document.documentElement.scrollWidth - document.documentElement.clientWidth")
```

## Соглашения

- **Язык — русский:** интерфейс, комментарии, сообщения коммитов.
- **Комментарий объясняет «почему», а не «что».** Особенно ценно записывать, что
  уже пробовали и почему отвергли: в этом коде так задокументированы отказ от
  угадывания названия актива по последним словам с заглавной и защита от
  отрицаний вроде «вне торгов».
- **Правки данных — только скриптом в `pipeline/`,** с сухим прогоном без
  аргументов и записью по `--write`. Ручные правки JSON затрёт следующий прогон.
- **Скрипт пайплайна начинается с docstring:** что чинит, почему это сломано,
  как запускать.
- **Проверки перед записью.** В скриптах стоят `assert` на исходное состояние
  поля — если данные уже другие, скрипт падает, а не портит их молча.
- **Плейсхолдеры не считаются данными.** «Не раскрыта», «Публично не сообщалось»,
  «Не привлекался», «—» — это пустота. Проверять регистронезависимо: в базе
  встречались и «не раскрыта», и «Не раскрыта» (из-за чего стиль приглушения
  не применялся к двум третям карточек).
- **Один и тот же текст лежит в двух полях.** `eco.rationale` («Цель сделки») и
  `extra` («Дополнительная информация») у 678 сделок совпадали дословно. Правя
  одно, проверяйте второе — иначе исправленное и неисправленное окажутся на
  одной странице.
- **`[А-ЯЁ]` под `re.I` совпадает и со строчными.** Проверка «здесь заглавная
  буква» молча не работает; если она нужна, писать `(?-i:[А-ЯЁ])`. На этом уже
  один раз потеряли начало фразы.
- **Замер важнее записанной цифры.** «Осталось 57 карточек» из бэклога оказалось
  неверным: словарь, которым считали, не знал половины формулировок. Прежде чем
  доделывать хвост, перемерьте его своим определением.
- **Правило, написанное для начала строки, не увидит того же дефекта в конце.**
  Чистка мета-комментариев год работала только с текстами, которые начинались со
  слова-источника, — а шум чаще стоит в последнем предложении. Прежде чем
  считать дефект закрытым, проверьте, где он на самом деле встречается. Второй
  раз те же грабли: `fix_truncated_fields.py` искал обрыв в начале значения
  (закрывающая скобка, перекос кавычек) и не видел 32 «Согласования», оборванных
  в конце — на висящем «;» или без подлежащего в начале.
- **Имя компании — не место для доли.** У 48 профилей из 1846 в названии стояла
  доля из заголовка сделки («ООО «Винтео» , 51%», «оставшиеся 49,9% акций ООО
  «Информ»»), и это имя показывалось в плашке сторон, в каталоге и в поиске.
  Чинится вырезанием. Одиннадцать записей сначала признали непочинимыми («это
  лоты из нескольких юрлиц, резать — значит потерять часть сделки»), и вывод был
  неверен: резать нельзя ДО ОДНОГО ИМЕНИ, а доли и предлоги вырезаются, и все
  юрлица остаются («ООО «Датана» и 49% ООО «Датабриз»» → «ООО «Датана» и ООО
  «Датабриз»»). Лоту вместо разбиения ставится признак `lot`: у сделки одно поле
  «предмет», и разбив лот на профили, пришлось бы выбрать одно юрлицо из трёх.
- **Одинокая запятая — не слово, а порог в три знака — не для коротких слов.**
  Проверка «результат ложится на источник слово в слово с точностью до
  окончаний» дважды промахнулась мимо верной правки: `,` считалась словом, а её
  «основа» после вырезания пунктуации пуста и не совпадает ни с чем; и «Пять» не
  выводилось из «пяти» — общего начала два знака при пороге три. Пунктуацию из
  сравнения выкидывать, для коротких слов держать отдельную ветку с закрытым
  списком окончаний (иначе «Вера» и «Вета» станут одним словом). Обе ветки —
  под `assert` в самом скрипте.
- **Тире — это и подпись, и знак препинания.** «Покупатель — Сделка по
  приобретению ЦОД…» надо чинить, а «Продавец — «Фаберлик» (производитель
  парфюмерии)» трогать нельзя. Различает их то, что стоит ПОСЛЕ тире:
  самостоятельное предложение о сделке — подпись; раскрытие того, что перед
  тире, — знак препинания.
- **Сумма пишется одним способом.** Валюта — только значком: `₽` после числа,
  `$` и `€` перед. Пометка недостоверности — только «(по оценке)», без имени
  оценщика: оно в «Оценке и дисконте». Правки — через `pipeline/normalize_sum.py`.
- **`\b` после приставки ломает правило.** `^не\s+раскры\b` не совпадает с «не
  раскрыта»: после «раскры» идёт буква, границы слова там нет. Правило молча не
  срабатывало ни на одной карточке из 618.
- **`page.on("console")` не ловит падения страницы.** Необработанное исключение
  приходит в `page.on("pageerror")`, и без него «ошибок в консоли 0» ничего не
  доказывает: у 3 фирм из 64 `renderFirm` падал на `rx.test`, `innerHTML` не
  присваивался, пользователь оставался на прежнем экране — и все прогоны
  Playwright считали это чистым результатом. Слушать оба события; отдельно
  проверять, что страница действительно отрисовалась (искать её собственный
  элемент, а не отсутствие ошибок).
- **Пояснение объясняет смысл числа, а не устройство базы.** «85 записей в
  базе: 75 подробных карточек и 10 кратких записей» — это наша разметка, а не
  ответ на вопрос пользователя. Слова «подробная карточка», «краткая запись»,
  «запись», «знаменатель», «bulk» на экран не выносить: 19 пояснений из 36
  говорили именно так. Разницу между множествами называть тем, что пользователь
  видит («у этих сделок известны только заголовок и источник»). Это же касается
  данных: у 516 профилей из 1846 описанием стояло «Профиль сформирован по итогам
  чтения bulk-базы (партия 4, 2022+)».
- **Выключка вправо — только для колонки однородных чисел.** У показателей
  карточки значения разнородные: 741 из 1200 (62%) длиннее 80 знаков, медиана
  111, максимум 599. Прижатые вправо, они начинались с разных вертикалей и
  давали рваный левый край. Сетка «подпись | значение» с общей левой линией и
  мерой в 72 знака читается ровно; мелкий текст тоже ограничивать по мере
  (в знаках, а не в пикселях), иначе подпись уходит в одну строку на 1018px.
- **Блок, который всегда полон, ничего не подбирает.** «Похожие сделки» стояли
  у всех 1352 карточек и всегда ровно из пяти строк: порог в точности равнялся
  весу отрасли, и одной общей отрасли хватало, чтобы пройти. Если у подборки
  нет ни одной карточки без результата — это не подбор, а добивание до лимита;
  проверяйте распределение размеров, а не наличие блока.
- **Скрытые состояния проверяются отдельно.** Панель расширенных фильтров
  переполняла экран на 100px, но только в открытом виде, — а открывают её
  ссылки `#/theme/`. Пока состояние не открыто, Playwright его не видит:
  перечислите состояния экрана (открыто/закрыто, пусто/полно) и пройдите каждое.
- **Проверяйте экран и на недогруженной базе.** База (4,7 МБ) приезжает вторым
  запросом, и до этого в `DEALS` 19 карточек из 1352, а в `COMPANIES` 36 из 1882.
  Все подписанные знаменатели в этот момент врут: «Аналитика» писала «54 записи —
  19 подробных карточек». Playwright это видит, только если задержать оба JSON
  (`context.route` + `asyncio.sleep`), — без задержки локальный сервер отдаёт их
  мгновенно и дефекта не видно.
- **Переполнение ищут на самом длинном значении, а не на первой карточке.**
  `white-space:nowrap` у пометки суммы жил четыре прогона и давал до 219px
  горизонтального переполнения на 360px у 74 карточек — проверки его не видели,
  потому что открывали карточки с короткой пометкой «(по оценке)». Перед
  проверкой вёрстки выберите записи с максимальной длиной поля и гоняйте по ним.
  Родственная ловушка: у флекс-элемента `min-width` по умолчанию `auto`, и он не
  сжимается ниже своего min-content — длинное значение выталкивает строку за
  экран, пока не поставишь `min-width:0`.
- **Заглушка — это когда ВСЯ строка заглушка.** Проверка «строка содержит „не
  раскрыта“» прячет факты: «не раскрыта (EV оценена в 21 млрд ₽)» и
  «Приобретение 100% уставного капитала ООО напрямую; сумма и структура не
  раскрыты» — это данные, а не пустота. Правило анкерить с обеих сторон
  (`^…$`), иначе за «честным пустым состоянием» исчезнет оценка.
- **В JS `\w` — это `[A-Za-z0-9_]`, кириллицы там нет.** `не\s+раскрыт\w*` не
  совпадает с «Не раскрыта»: после «раскрыт» идёт «а», а её `\w` не знает.
  Правило молча не срабатывает ни на одной строке. Писать `[а-яё]*`. Родня того
  же семейства, что `\b` после приставки: и то и другое ломается беззвучно,
  поэтому любой предикат прогонять на списке заведомых заглушек и заведомых
  фактов, а не проверять на глаз.
- **У числа на экране два свойства: величина и множество.** Подпись почти всегда
  называет тему, а не множество, — и тогда число врёт, оставаясь арифметически
  верным. «Сделок в базе» на профиле компании считало сделки плюс автоматические
  совпадения по названию в заголовке: у 82 профилей из 1809 сделок не было ни
  одной, а счётчик показывал до 7. Прежде чем подписывать число, выпишите, из
  какого множества оно получено, — и подпишите именно множество.
- **Соседние числа считаются от разных знаменателей.** На «Аналитике» их было
  три (1494 записи базы, 1201 запись в столбцах графика, 1352 подробные
  карточки), и ни один не назывался: читатель делит на первый попавшийся.
  Если на экране больше одного знаменателя — называть каждый, у каждого графика.
- **Честное пустое состояние честно, только если факта нет НИГДЕ в карточке.**
  Линза «Юрист» писала «структуру, условия и согласования не называли» у 82
  сделок, у которых на соседней вкладке было написано «ФАС одобрила сделку в
  конце июня 2025 года». Пустое поле и отсутствующий факт — разные вещи: прежде
  чем показывать пустое состояние, проверьте соседние поля той же карточки.
  Проверять надо не глазами: искали предложения, где рядом стоят орган и
  действие, — и нашли в полях, куда никто не смотрел.
- **Разное время в заголовках — не всегда разнобой.** «Покупает» и «купил»
  противоречат друг другу, только если противоречат статусу сделки: идёт —
  настоящее, закрыта — прошедшее. Из 1006 заголовков с глаголом 847 согласованы
  со статусом и лишь 70 нет. Прежде чем причёсывать всё под одну форму,
  проверьте, нет ли у разнобоя смысла.
- **Инвариант можно заменить, но не отменить.** Правило «результат — дословный
  кусок текста карточки» не работает, когда имя в тексте стоит в родительном
  падеже: «Светлана Рыбальченко» там не встречается. Отменять проверку в таких
  случаях нельзя — её заменяют более слабой, но всё ещё механической: результат
  обязан слово в слово ложиться на кусок текста, отличаясь только окончаниями
  (общее начало ≥ 3 знаков и ≥ 60% длины короткого слова). И правило проверяется
  на себе: `assert`, что заведомо чужое имя на этот текст не ложится.
- **Переносить факт в правильное поле можно, сочинять — нет.** Граница
  проверяемая: нормализованный результат обязан быть подстрокой
  нормализованного поля-источника. Тогда разрешённые правки — только вырезать
  лишнее и поставить заглавную букву, а `assert` в скрипте ловит любую попытку
  «слегка переформулировать». В `pipeline/extract_approvals.py` это главная
  проверка, а не украшение.
- **Одно поле — одна линза.** `eco.share` показывался и на «Обзоре», и на
  «Экономисте», а у 249 карточек из 307 предмет назывался ещё и в плашке прямо
  над строкой: один и тот же абзац на 206 знаков читался дважды. Прежде чем
  добавлять поле на экран, проверьте, где оно уже показано, — и что соседний
  структурный блок не говорит того же самого другими словами.
- **Прежде чем наполнять поле, проверьте, не показан ли факт под другой
  подписью.** Наполнение «Структуры сделки» из текста отменено на проверке: 20
  из 30 отобранных предложений уже стояли на экране в «Предмете / доле». Это
  было бы не новое знание, а то же самое в двух местах. Проверка дешёвая —
  сравнить кандидата со всеми подписанными полями карточки, а не только с тем,
  которое заполняешь.
- **Признак дефекта — повод прочитать, а не основание стереть.** «В поле
  „Согласования" нет ни одного слова об одобрении» пометило 16 значений, но у
  трёх из них согласование было настоящим: «премьер-министр подписал
  распоряжение о продаже», «Банк России направлял предписание Росимуществу».
  Автоматическая чистка по такому признаку удалила бы факты. Признак сужает
  выборку для чтения глазами — решение принимает человек, и оно записывается в
  таблицу скрипта вместе с причиной.
- **Запятая внутри числа ломает шаблон с `[^,]`.** Правило
  `привлек\w*\s+[^,]{0,40}(?:млн|млрд)` не совпало с «привлекла 12,5 млн»: класс
  `[^,]` обрывается на запятой в числе. Замер показал 8 карточек вместо 13 — и
  среди пропущенных была ровно та, с которой пришёл вопрос. В русских суммах
  запятая — часть числа, а не разделитель: писать `[^.;]`.
- **Заголовок говорит об этой сделке, текст — обо всей истории актива.** Один и
  тот же признак («купил у X», «X продал») в заголовке почти всегда про эту
  сделку, а в «Дополнительной информации» сплошь и рядом про предыдущую смену
  собственника: «ранее, в 2011 году, „Газметаллпроект" выкупил у Елены
  Батуриной», «в 2024 году приобрела у Полюса „Лензолото"». Из 215 карточек с
  признаком продавца 91 имели его в заголовке — эта партия прошла чтение почти
  без отказов (3 из 91), остальные 124 заведомо шумнее. Партии разделять по
  месту признака, а не брать всё разом.
- **`продавц\w*` не совпадает со словом «Продавец».** Основа «продавц» есть у
  всех падежей, кроме именительного: «продавца», «продавцы», «продавцом» — да,
  «продавец» — нет. Четыре прогона искали сторону сделки этим шаблоном и не
  видели 99 карточек, подписанных «Продавец — X», а в бэклоге всё это время
  стояло «осталось ~50 кандидатов, и те шумные». Родня `\b` после приставки и
  `\w` в JS: правило молчит, а замер выглядит законченным. Любой шаблон по
  русскому слову прогонять на всех падежах, начиная с именительного.
- **Заглавная буква сразу после предлога — плохая граница имени.** Правило
  «купил Y у X» искало `у\s+[А-ЯЁA-Z]`, а в тексте между предлогом и именем
  почти всегда стоит строчное пояснение: «у основателя Анатолия Покатилова», «у
  экс-депутата Госдумы Бекхана Агаева», «у компании «Курс»». Мимо прошли 54
  карточки, из них 14 с настоящим продавцом.
- **Поле, заполненное в данных, может быть не показано на экране.** У IPO и
  раундов плашка сторон устроена иначе («Инвестор → Получатель инвестиций»), и
  ячейки продавца в ней нет вовсе: 6 карточек из 597 с известным продавцом не
  показывали его нигде. Нашёл это не diff данных, а Playwright — проверка «на
  экране есть слово „продавец"». Заполнив поле, проверьте его НА ЭКРАНЕ, причём
  на карточке каждого типа сделки.
- **«Продавец» не всегда сторона сделки.** В карточках про маркетплейсы это
  слово значит «продавец на маркетплейсе»: «сервис аналитики для продавцов на
  маркетплейсах», «финансирование продавцов». Механический признак засчитал бы
  три такие карточки за названного продавца. Проверять, о ком речь, а не
  считать совпадение слова фактом.
- **Проверка «результат лежит в тексте» не работает на перечислениях.** Между
  именами продавцов почти всегда стоят слова, которых в результате нет:
  «Продавцы — основатели сети Михаил Норкин и Андрей Сафронюк». Сплошная
  проверка такое имя не подтверждает. Резать результат по «и» и запятым и
  проверять каждую часть отдельно — и обязательно проверить, что подмена одного
  имени («Михаил Норкин и Иван Петров») правило НЕ проходит.
- **Точка не значит конец предложения.** «18,8 млрд руб.», «январь 2022 г.»,
  «Калужская обл.», «Fortum Russia B.V.» — на этом уже один раз разрезали текст
  посередине и потеряли по половине фразы в 65 полях. Списку сокращений не
  верить: надёжнее правило «точка + пробел + заглавная», оно ошибается в
  безопасную сторону — склеит два предложения, а не разрежет одно.

## Известные проблемы

- Линза «Юрист» пуста у 75% карточек (структура 6%, согласования 10%, условия 2%).
- 155 профилей компаний не привязаны ни к одной сделке.
- У покупателя две формы записи: `buyer` (ссылка на профиль) и `buyer_name`
  (имя текстом) — вторая для инвестиционных раундов, где у фондов профилей нет.
  Одновременно заполнять обе нельзя, это ловит тест.
- Данных о группе компаний в базе почти нет (`holding` — у 2 профилей из 1846),
  поэтому «Контроль у X» и «Под контролем: N» на странице компании считаются на
  лету по закрытым сделкам M&A с контрольным пакетом и всегда подписаны сделкой.
  В настоящем времени это не утверждается: перепродажу вне базы мы не увидим.
- 9 «профилей компаний» — на деле лоты из нескольких юрлиц («ООО «Датана» и ООО
  «Датабриз»»). У них стоит признак `lot`, и страница компании прямо пишет, что
  это не одна компания. На отдельные профили лот не разбит: у сделки одно поле
  «предмет».
- Вся база грузится на клиент одним файлом: 4,6 МБ на диске, **774 КБ по сети**
  (`GZipMiddleware` в `main.py`). Экраны, зависящие от неё, до загрузки
  показывают «Загружаем базу сделок», а не цифры по 19 карточкам.
- Данных о цепочке владения нет: `ownership` пуст, `holding` — у 2 компаний.
- Тип сделки сведён к пяти значениям (M&A, Инвестиция, IPO, Продажа с торгов,
  Финансирование · структурная сделка). База шире M&A: 115 карточек — инвестиции,
  35 — IPO. На странице отрасли это видно блоком «Что это за сделки».
- Адрес для правок — константа `CONTACT_EMAIL` в `static/index.html`, одна на
  футер и на кнопку «Уточнить или дополнить» в карточке.
- Роли сторон выверены вручную только за 2026 год. Прогон 32 нашёл 3 карточки,
  где продавец стоял предметом сделки, прогон 40 — ещё 7; их нашла не сплошная
  выверка, а проверка «профиль уже занят другой ролью» при связывании продавца
  с профилем (прогон 41 добавил ещё 10 — всего 17). Обратный случай (предметом стоит ПОКУПАТЕЛЬ) известен у 4 карточек
  и механически пока не измерен: наивное правило даёт 11 кандидатов, и все 11 —
  верные записи о buyback и MBO.
- Продавец известен у 597 карточек из 1333 (45%), с профилем компании связаны
  165. Признак «продавец» исчерпан: оставшиеся 8 карточек прочитаны и отклонены
  («Продавец публично не раскрывался»). Непрочитанными остаются «основатель /
  владелец X» (40) и «доля X» (36) — оба дают в основном не продавца.

## Чего не делать

- Не создавать pull request без явной просьбы.
- Не переписывать историю git, не делать `push --force`.
- Не удалять данные массово и не «чистить» профили компаний без разбора: среди
  них есть настоящие активы сделок.
- Не добавлять внешние CDN, шрифты и сервисы — всё должно работать из России.
- Не подменять отсутствующие данные правдоподобными: пустое поле честнее.
