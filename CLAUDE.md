# Правила работы в репозитории «Компас»

Читать вместе с `PRODUCT_ROADMAP.md` (принципы, бэклог, журнал). Здесь — техника:
как устроен репозиторий, чем запускать, что проверять и какие соглашения приняты.

## Что это

Одностраничное приложение о сделках M&A российского рынка. FastAPI отдаёт
статику, весь интерфейс — один файл `static/index.html` (~1900 строк, без
сборки и без внешних зависимостей). Данные лежат в JSON и подгружаются на клиент.

## Структура

```
main.py                       FastAPI: раздача статики, /health, /api/ask
yandex_search.py              обёртка над Яндекс XML-поиском (для ассистента)
test_kompas.py                17 тестов: yandex_search + /api/ask
test_data.py                  42 теста: инварианты базы (без браузера)
test_ui.py                    39 тестов: дымовые проверки экранов (Playwright)
test_ingest.py                89 тестов: приток (фильтр, сопоставление, пост, черновик, ворота,
                              обогащение известной сделки, страховка на живом потоке,
                              темп публикации и правила личных подписок)
test_launch_features.py       31 тест: ФНС, подписки, уведомления, экспорт, модерация
test_accounts.py              29 тестов: аккаунты, комментарии, правки
test_auth.py                  29 тестов: регистрация, вход, сессии, пароль
.github/workflows/tests.yml   CI: данные и API отдельно, интерфейс отдельно
.claude/hooks/session-start.sh    ставит зависимости: контейнер рутины пуст (нет httpx и pytest)
static/index.html             ВЕСЬ интерфейс: стили и рендер (данных в нём НЕТ)
static/data/deals_promoted.json   ЕДИНСТВЕННЫЙ источник данных: ~1560 сделок,
                              ~1860 компаний, match_keys, merged, telegram_posts
pipeline/                     скрипты разбора и чистки данных
pipeline/ingest/              приток: реестр, забор, фильтр, сопоставление, черновик,
                              ворота в базу, обогащение известных карточек и
                              проверка новой карточки чтением (review.py)
pipeline/publish/             публикация: формат телеграм-поста и правила обновления
data/inbox/                   сырьё притока и отчёты разбора (в git не хранятся)
```

Внутри `static/index.html`:
- `COMPANIES`, `DEALS`, `MINI_DEALS`, `CHANNEL_DEALS` — ПУСТЫЕ массивы, их
  наполняет загрузчик; `FIRMS` и `INDUSTRIES` — справочники, не данные о сделках;
- `loadBulkDeals()` читает `deals_promoted.json` — один запрос, один источник;
- `route()` — хеш-роутер; `render*()` — по экрану на функцию.

## Запуск и проверка

```bash
uvicorn main:app --reload            # http://127.0.0.1:8000
python3 -m pytest -q                 # 364 passed (≈4 мин: интерфейс и аккаунты — самое долгое)
python3 -m pytest test_data.py -q    # только инварианты базы, без браузера (0,1 с)
```

Три набора тестов:

| файл | что проверяет | нужен браузер |
|---|---|---|
| `test_kompas.py` | `yandex_search` и `/api/ask` | нет |
| `test_data.py` | инварианты базы: ссылки, роли, соглашения о записи | нет |
| `test_ui.py` | экраны открываются, не падают, не переполняют | да |

Скриншоты и проверка интерфейса — Playwright, браузер уже стоит:

```python
br = await p.chromium.launch(executable_path="/opt/pw-browsers/chromium")
```

Не запускать `playwright install` — браузер предустановлен
(`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`). Это правило про ЭТУ машину: в CI
(`.github/workflows/tests.yml`) Chromium ставится явно, потому что там его нет.
`test_ui.py` использует предустановленный путь, только если файл существует.

## Обязательная проверка перед коммитом

1. `python3 -m pytest -q` — 282/282. Инварианты базы и дымовые тесты интерфейса
   теперь живут в `test_data.py` и `test_ui.py`, а не в одноразовых скриптах.
2. **Семантический diff JSON**, а не глазами по строкам: сравнить с `HEAD` и
   убедиться, что изменились только те поля, которые собирались менять, а состав
   сделок, профилей компаний и `match_keys` не поехал:

```python
old = json.loads(subprocess.run(['git','show','HEAD:static/data/deals_promoted.json'],
                                capture_output=True, text=True).stdout)
new = json.load(open('static/data/deals_promoted.json'))
# сравнить set(id), companies, match_keys и посчитать, какие поля изменились
```

3. Для правок интерфейса — Playwright: страницы открываются, в консоли нет
   ошибок, нет горизонтального переполнения на 360 / 390 / 1280:

```python
await pg.evaluate("document.documentElement.scrollWidth - document.documentElement.clientWidth")
```

## Соглашения

- **Язык — русский:** интерфейс, комментарии, сообщения коммитов.
- **Комментарий объясняет «почему», а не «что».** Особенно ценно записывать, что
  уже пробовали и почему отвергли: в этом коде так задокументированы отказ от
  угадывания названия актива по последним словам с заглавной и защита от
  отрицаний вроде «вне торгов».
- **Правки данных — только скриптом в `pipeline/`,** с сухим прогоном без
  аргументов и записью по `--write`. Ручные правки JSON затрёт следующий прогон.
- **Скрипт пайплайна начинается с docstring:** что чинит, почему это сломано,
  как запускать.
- **Проверки перед записью.** В скриптах стоят `assert` на исходное состояние
  поля — если данные уже другие, скрипт падает, а не портит их молча.
- **Плейсхолдеры не считаются данными.** «Не раскрыта», «Публично не сообщалось»,
  «Не привлекался», «—» — это пустота. Проверять регистронезависимо: в базе
  встречались и «не раскрыта», и «Не раскрыта» (из-за чего стиль приглушения
  не применялся к двум третям карточек).
- **Один и тот же текст лежит в двух полях.** `eco.rationale` («Цель сделки») и
  `extra` («Дополнительная информация») у 678 сделок совпадали дословно. Правя
  одно, проверяйте второе — иначе исправленное и неисправленное окажутся на
  одной странице.
- **`[А-ЯЁ]` под `re.I` совпадает и со строчными.** Проверка «здесь заглавная
  буква» молча не работает; если она нужна, писать `(?-i:[А-ЯЁ])`. На этом уже
  один раз потеряли начало фразы.
- **Замер важнее записанной цифры.** «Осталось 57 карточек» из бэклога оказалось
  неверным: словарь, которым считали, не знал половины формулировок. Прежде чем
  доделывать хвост, перемерьте его своим определением.
- **Правило, написанное для начала строки, не увидит того же дефекта в конце.**
  Чистка мета-комментариев год работала только с текстами, которые начинались со
  слова-источника, — а шум чаще стоит в последнем предложении. Прежде чем
  считать дефект закрытым, проверьте, где он на самом деле встречается. Второй
  раз те же грабли: `fix_truncated_fields.py` искал обрыв в начале значения
  (закрывающая скобка, перекос кавычек) и не видел 32 «Согласования», оборванных
  в конце — на висящем «;» или без подлежащего в начале.
- **Имя компании — не место для доли.** У 48 профилей из 1846 в названии стояла
  доля из заголовка сделки («ООО «Винтео» , 51%», «оставшиеся 49,9% акций ООО
  «Информ»»), и это имя показывалось в плашке сторон, в каталоге и в поиске.
  Чинится вырезанием. Одиннадцать записей сначала признали непочинимыми («это
  лоты из нескольких юрлиц, резать — значит потерять часть сделки»), и вывод был
  неверен: резать нельзя ДО ОДНОГО ИМЕНИ, а доли и предлоги вырезаются, и все
  юрлица остаются («ООО «Датана» и 49% ООО «Датабриз»» → «ООО «Датана» и ООО
  «Датабриз»»). Лоту вместо разбиения ставится признак `lot`: у сделки одно поле
  «предмет», и разбив лот на профили, пришлось бы выбрать одно юрлицо из трёх.
- **Одинокая запятая — не слово, а порог в три знака — не для коротких слов.**
  Проверка «результат ложится на источник слово в слово с точностью до
  окончаний» дважды промахнулась мимо верной правки: `,` считалась словом, а её
  «основа» после вырезания пунктуации пуста и не совпадает ни с чем; и «Пять» не
  выводилось из «пяти» — общего начала два знака при пороге три. Пунктуацию из
  сравнения выкидывать, для коротких слов держать отдельную ветку с закрытым
  списком окончаний (иначе «Вера» и «Вета» станут одним словом). Обе ветки —
  под `assert` в самом скрипте.
- **Тире — это и подпись, и знак препинания.** «Покупатель — Сделка по
  приобретению ЦОД…» надо чинить, а «Продавец — «Фаберлик» (производитель
  парфюмерии)» трогать нельзя. Различает их то, что стоит ПОСЛЕ тире:
  самостоятельное предложение о сделке — подпись; раскрытие того, что перед
  тире, — знак препинания.
- **Сумма пишется одним способом.** Валюта — только значком: `₽` после числа,
  `$` и `€` перед. Пометка недостоверности — только «(по оценке)», без имени
  оценщика: оно в «Оценке и дисконте». Правки — через `pipeline/normalize_sum.py`.
- **`\b` после приставки ломает правило.** `^не\s+раскры\b` не совпадает с «не
  раскрыта»: после «раскры» идёт буква, границы слова там нет. Правило молча не
  срабатывало ни на одной карточке из 618.
- **`page.on("console")` не ловит падения страницы.** Необработанное исключение
  приходит в `page.on("pageerror")`, и без него «ошибок в консоли 0» ничего не
  доказывает: у 3 фирм из 64 `renderFirm` падал на `rx.test`, `innerHTML` не
  присваивался, пользователь оставался на прежнем экране — и все прогоны
  Playwright считали это чистым результатом. Слушать оба события; отдельно
  проверять, что страница действительно отрисовалась (искать её собственный
  элемент, а не отсутствие ошибок).
- **Пояснение объясняет смысл числа, а не устройство базы.** «85 записей в
  базе: 75 подробных карточек и 10 кратких записей» — это наша разметка, а не
  ответ на вопрос пользователя. Слова «подробная карточка», «краткая запись»,
  «запись», «знаменатель», «bulk» на экран не выносить: 19 пояснений из 36
  говорили именно так. Разницу между множествами называть тем, что пользователь
  видит («у этих сделок известны только заголовок и источник»). Это же касается
  данных: у 516 профилей из 1846 описанием стояло «Профиль сформирован по итогам
  чтения bulk-базы (партия 4, 2022+)».
- **Выключка вправо — только для колонки однородных чисел.** У показателей
  карточки значения разнородные: 741 из 1200 (62%) длиннее 80 знаков, медиана
  111, максимум 599. Прижатые вправо, они начинались с разных вертикалей и
  давали рваный левый край. Сетка «подпись | значение» с общей левой линией и
  мерой в 72 знака читается ровно; мелкий текст тоже ограничивать по мере
  (в знаках, а не в пикселях), иначе подпись уходит в одну строку на 1018px.
- **Блок, который всегда полон, ничего не подбирает.** «Похожие сделки» стояли
  у всех 1352 карточек и всегда ровно из пяти строк: порог в точности равнялся
  весу отрасли, и одной общей отрасли хватало, чтобы пройти. Если у подборки
  нет ни одной карточки без результата — это не подбор, а добивание до лимита;
  проверяйте распределение размеров, а не наличие блока.
- **Скрытые состояния проверяются отдельно.** Панель расширенных фильтров
  переполняла экран на 100px, но только в открытом виде, — а открывают её
  ссылки `#/theme/`. Пока состояние не открыто, Playwright его не видит:
  перечислите состояния экрана (открыто/закрыто, пусто/полно) и пройдите каждое.
- **Проверяйте экран и на недогруженной базе.** База (4,7 МБ) приезжает вторым
  запросом, и до этого в `DEALS` 19 карточек из 1352, а в `COMPANIES` 36 из 1882.
  Все подписанные знаменатели в этот момент врут: «Аналитика» писала «54 записи —
  19 подробных карточек». Playwright это видит, только если задержать оба JSON
  (`context.route` + `asyncio.sleep`), — без задержки локальный сервер отдаёт их
  мгновенно и дефекта не видно.
- **Переполнение ищут на самом длинном значении, а не на первой карточке.**
  `white-space:nowrap` у пометки суммы жил четыре прогона и давал до 219px
  горизонтального переполнения на 360px у 74 карточек — проверки его не видели,
  потому что открывали карточки с короткой пометкой «(по оценке)». Перед
  проверкой вёрстки выберите записи с максимальной длиной поля и гоняйте по ним.
  Родственная ловушка: у флекс-элемента `min-width` по умолчанию `auto`, и он не
  сжимается ниже своего min-content — длинное значение выталкивает строку за
  экран, пока не поставишь `min-width:0`.
- **Заглушка — это когда ВСЯ строка заглушка.** Проверка «строка содержит „не
  раскрыта“» прячет факты: «не раскрыта (EV оценена в 21 млрд ₽)» и
  «Приобретение 100% уставного капитала ООО напрямую; сумма и структура не
  раскрыты» — это данные, а не пустота. Правило анкерить с обеих сторон
  (`^…$`), иначе за «честным пустым состоянием» исчезнет оценка.
- **В JS `\w` — это `[A-Za-z0-9_]`, кириллицы там нет.** `не\s+раскрыт\w*` не
  совпадает с «Не раскрыта»: после «раскрыт» идёт «а», а её `\w` не знает.
  Правило молча не срабатывает ни на одной строке. Писать `[а-яё]*`. Родня того
  же семейства, что `\b` после приставки: и то и другое ломается беззвучно,
  поэтому любой предикат прогонять на списке заведомых заглушек и заведомых
  фактов, а не проверять на глаз.
- **У числа на экране два свойства: величина и множество.** Подпись почти всегда
  называет тему, а не множество, — и тогда число врёт, оставаясь арифметически
  верным. «Сделок в базе» на профиле компании считало сделки плюс автоматические
  совпадения по названию в заголовке: у 82 профилей из 1809 сделок не было ни
  одной, а счётчик показывал до 7. Прежде чем подписывать число, выпишите, из
  какого множества оно получено, — и подпишите именно множество.
- **Соседние числа считаются от разных знаменателей.** На «Аналитике» их было
  три (1494 записи базы, 1201 запись в столбцах графика, 1352 подробные
  карточки), и ни один не назывался: читатель делит на первый попавшийся.
  Если на экране больше одного знаменателя — называть каждый, у каждого графика.
- **`deals_promoted.json` шире, чем то, что видит посетитель.** Число «X
  сделок» на главной странице (`TOTAL_DEALS()`) — это НЕ `deals.length` из
  JSON: `isDealShownOnSite()` в `static/index.html` фильтрует по году сделки
  (`SITE_MIN_YEAR = 2022`), и на 17 августа в базе 1562 записи, а на экране —
  1371 (191 карточка датирована раньше 2022 года и хранится, но никогда не
  показывается). Сравнивая «сколько сделок в файле» со «сколько показывает
  сайт», легко принять честную фильтрацию за пропажу данных — прежде чем
  считать разницу дефектом, проверьте `isDealShownOnSite()`, а не только
  длину массива.
- **Честное пустое состояние честно, только если факта нет НИГДЕ в карточке.**
  Линза «Юрист» писала «структуру, условия и согласования не называли» у 82
  сделок, у которых на соседней вкладке было написано «ФАС одобрила сделку в
  конце июня 2025 года». Пустое поле и отсутствующий факт — разные вещи: прежде
  чем показывать пустое состояние, проверьте соседние поля той же карточки.
  Проверять надо не глазами: искали предложения, где рядом стоят орган и
  действие, — и нашли в полях, куда никто не смотрел.
- **Разное время в заголовках — не всегда разнобой.** «Покупает» и «купил»
  противоречат друг другу, только если противоречат статусу сделки: идёт —
  настоящее, закрыта — прошедшее. Из 1006 заголовков с глаголом 847 согласованы
  со статусом и лишь 70 нет. Прежде чем причёсывать всё под одну форму,
  проверьте, нет ли у разнобоя смысла.
- **Инвариант можно заменить, но не отменить.** Правило «результат — дословный
  кусок текста карточки» не работает, когда имя в тексте стоит в родительном
  падеже: «Светлана Рыбальченко» там не встречается. Отменять проверку в таких
  случаях нельзя — её заменяют более слабой, но всё ещё механической: результат
  обязан слово в слово ложиться на кусок текста, отличаясь только окончаниями
  (общее начало ≥ 3 знаков и ≥ 60% длины короткого слова). И правило проверяется
  на себе: `assert`, что заведомо чужое имя на этот текст не ложится.
- **Переносить факт в правильное поле можно, сочинять — нет.** Граница
  проверяемая: нормализованный результат обязан быть подстрокой
  нормализованного поля-источника. Тогда разрешённые правки — только вырезать
  лишнее и поставить заглавную букву, а `assert` в скрипте ловит любую попытку
  «слегка переформулировать». В `pipeline/extract_approvals.py` это главная
  проверка, а не украшение.
- **Почему `review.py` не поймал ни одну из трёх находок владельца сам —
  и что с этим сделано.** Карточка ПСБ/«Атом» была ПРОЧИТАНА (`reviewed:
  2026-08-14`, дословные цитаты через FIXES) — и всё равно несла неверный
  тип, непровязанные профили и (в других карточках того же класса)
  источник, названный в тексте, но не добавленный в `src`. Причина не в
  недосмотре одной карточки, а в границе самого шага: `check()` в
  `review.py` проверяет, что КАЖДОЕ ДОБАВЛЯЕМОЕ значение дословно выводимо
  из цитаты (защита от выдумки) — но ничего не проверяет ПОСЛЕ того, как
  факты уже добавлены: он не перепроверяет `type`, когда новый факт меняет
  картину сделки; не требует, чтобы упомянутое в тексте издание было в
  `src`; не ищет существующий профиль компании перед тем, как принять имя
  текстом. Три отдельных, узких проверки, каждая — за пределами того, что
  «дословность» вообще может поймать (дословность про ЧТО написано, не про
  СОГЛАСОВАННОСТЬ написанного). Измерено по всей базе тем же вечером:
  - **21 карточка** несла `seller`/`buyer_name` текстом, хотя профиль с
    ТОЧНО таким именем уже существовал в базе (Банк «Траст» — 10 карточек,
    Росимущество, пять названных физлиц и др.) — почти всегда потому, что
    профиль появился в базе ПОЗЖЕ карточки, а связывание никто не
    перезапускал. Мгновенно и безопасно чинится: `pipeline/
    link_named_parties_to_existing_profiles.py` (та же граница, что уже
    была в `link_orphan_profiles.py`, — точное совпадение имени, без
    вхождения подстрокой, иначе повторится урок «Hempel»/«Morgan Stanley»)
    — все 21 связаны и подтверждены сверкой профиля со сделкой глазами.
    Родня `link_orphan_profiles.py`: тот скрипт ищет ПЕРВУЮ сделку
    профилям без единой — этот ищет ЛЮБУЮ ЕЩЁ карточку с текстовым именем,
    когда профиль давно не «orphan». Оба стоит перезапускать периодически,
    не один раз: новые профили появляются каждую неделю (G2/дочитывание),
    а карточки, написанные раньше их, о них не узнают сами.
  - **76 карточек** называют издание В ТЕКСТЕ (эко/юр поля, `extra`,
    `events[].note` — например, «По данным Reuters, брокером сделки
    выступил...»), которого нет в `src`. НЕ ПОЧИНЕНО автоматически и не
    должно быть: часть таких упоминаний — это атрибуция ВНУТРИ уже
    процитированного источника («Коммерсантъ» пишет «по данным Reuters»),
    и добавлять «Reuters» в `src` было бы неверно — источник, который мы
    реально читали, это Коммерсантъ, а не Reuters (см. уже записанный урок
    «Источник — то, что подтверждает факт, а не то, как о нём узнали»).
    Отличить «мы читали X и забыли добавить» от «X упомянут ВНУТРИ Y,
    которого мы читали» может только чтение конкретной карточки — список
    76 кандидатов записан как приоритет G7 (дочитывание), не как задача
    для скрипта.
  - **18 карточек** несут `type: "M&A"`, продавца не называют, а текст
    сигналит допэмиссию/закрытую подписку — тот же класс, что и ПСБ/
    «Атом». Здесь шум СИЛЬНЕЕ, чем в классе источников: «Тинькофф
    приобретает Росбанк» и «МТС приобрела 51% в... Vinteo» тоже попали в
    выборку, хотя это обычные M&A, где допэмиссия — механизм расчёта, а не
    природа сделки (инвестор извне против cash-in/cash-out — см. запись
    выше). Список из 18 id — тоже кандидаты для G7, не для скрипта: каждый
    требует прочитать, идёт ли речь о смене контроля или только о притоке
    капитала в компанию.
- **Четвёртая форма того же слепого пятна: дословная цитата в НЕ СВОЁМ
  поле.** У «HeadHunter приобрёл 51% Happy Job» (`gebead2e8`) `law.terms`
  нёс «Стандарты, методика, контроль качества, бенчмаркинг и порядок
  присуждения сертификатов «Отличное место для работы» останутся
  неизменными и будут соответствовать мировым практикам.» — дословная
  цитата TAdviser, `review.py` её пропустил верно: значение реально лежит
  в источнике слово в слово. Но это не условие СДЕЛКИ (не индемнити, не
  earn-out, не обязательство сохранить бренд/команду/производство — та
  категория, для которой поле вообще заведено), а фраза-заверение из
  пресс-релиза, адресованная клиентам сертификации Happy Job («ваш
  сертификат остаётся действительным») — про то, как продолжает работать
  ПРОДУКТ цели, а не на каких условиях её купили. Владелец нашёл это сам,
  открыв карточку после случайного одобрения кнопкой в Telegram, и спросил
  прямо: «если бы ты это читал, ты бы тоже пропустил?» — да, читая с
  вопросом «это условие ИМЕННО ЭТОЙ сделки или сообщение клиентам цели»,
  пропустить трудно; правку писал саб-агент рутины притока, и его же
  докстринг честно признаёт, что согласований, консультантов и настоящих
  договорных условий не нашлось НИ В ОДНОМ из девяти прочитанных
  источников — материала для линзы «Юрист» у карточки не было вовсе,
  и единственное подтянутое предложение подменило честную пустоту.
  Снято `pipeline/fix_headhunter_happyjob_law_terms.py` — вкладка «Юрист»
  теперь не рендерится (все три поля пусты, правило от 18 августа).
  `check()` в `review.py` не может и не должен ловить этот класс: он
  проверяет, что текст РЕАЛЕН и точно процитирован, а не что он относится
  К ТОЙ СУЩНОСТИ, для которой заведено поле (условие сделки vs описание
  продукта, обещанное клиентам цели, а не покупателем клиентам). Родня
  урока про `law.terms` из раздела «Что искать для линзы «Юрист»» — но тот
  список называет, ЧТО туда класть, а этот случай про обратное: как
  отличить похожую по форме, но чужую по смыслу фразу, которая туда не
  должна попасть, даже если она дословно верна.
- **Тип сделки определяет не только ярлык, но и КАКИЕ роли вообще
  существуют.** «ПСБ купил 16,9% акций... «Атом»» несла `type: "M&A"» и
  показывала «Продавец: не раскрыт» — но собственная цитата на карточке
  говорила прямо: «пакет выкуплен в рамках дополнительной эмиссии за
  денежные средства». Допэмиссия ЗА ДЕНЬГИ (cash-in) — деньги идут самой
  компании, продающего акционера нет в принципе; «Продавец не раскрыт» тут
  не честная пустота, а несуществующая роль, поданная как забытое поле.
  Сигнал уже был на экране (владелец сам объяснил разницу cash-in/cash-out
  18 августа) — читать нужно не только «что написано», но и «какая
  структура сделки это подразумевает»: допэмиссия/закрытая подписка — это
  ЛИБО продажа существующего пакета (cash-out, есть продавец), ЛИБО
  инвестиция в компанию (cash-in, продавца нет вовсе), и текст источника
  почти всегда называет, что именно произошло с деньгами.
- **Плашка стороны и предмет сделки достойны собственного профиля не
  меньше самой стороны.** У той же карточки `asset` нёс «российский
  производитель электромобилей "Атом" [АО "Кама"]» — пересказ вместо
  имени юрлица, и ни «Кама», ни покупатель «ПСБ» не были кликабельны.
  Профиль «Кама» в базе уже БЫЛ (`gcc2d3689`) — но это другая компания
  (картонный комбинат, продан «Свезе» в 2024-м): связать target с ней
  значило бы повторить урок «Стороной сделки может быть записан профиль
  совсем другой сущности». Заведён новый профиль под именем, не
  совпадающим по транслитерационному ключу с существующим омонимом
  («Кама» (Атом)), а не единственно верное короткое «Кама» — иначе
  `test_no_company_twins` справедливо посчитал бы его дублем чужой
  компании. Родня уже записанного «Конкретно звучащее имя компании тоже
  бывает однофамильцем», только здесь омоним — не риск, а факт, найденный
  сразу при попытке связать сторону.
- **Служебный id ленты протекает на экран не только через `src`, но и
  через `events[].source` — это ДВА разных потребителя одной таблицы
  имён.** `pipeline/source_names.py` уже резолвил `src` через
  `edition_label()` (урок про «web:kommersant.ru», 6 августа), но код,
  добавляющий ЭТАПЫ сделки, копировал внутренний id ленты напрямую в
  `events[].source` — тот же класс дефекта вернулся 18 августа для
  «tg:rusven». Замер по всей базе (регэксп `^(tg|web):` по первому
  элементу пары) нашёл не одну карточку, а пять записей в четырёх —
  находка одной ошибки глазами владельца была поводом измерить класс
  целиком, а не почистить одну карточку. `edition_label()` заодно научен
  резолвить t.me по имени канала в пути ссылки — раньше отдавал голый
  «T.me», ничем не лучше исходного дефекта.
- **Компактная строка «Ход сделки» показывала полный текст этапа рядом с
  кнопкой «Открыть этап», которая вела на страницу с ТЕМ ЖЕ текстом.**
  Просьба владельца 18 августа: в компактной строке — только этап и дата
  (текст почти всегда дублирует сумму/статус/предмет, уже показанные
  рядом), а кнопка на отдельную страницу — только если у этапа есть факт,
  которого больше нигде на карточке нет (`noteIsNovel()` — тот же
  признак, которым уже решали, показывать ли блок «Ход сделки» целиком на
  карточке с одним этапом, см. запись про g21795ec9/ALMI Partner). Строка
  без такого факта показывается простым текстом, без ссылки: переход в
  никуда (та же страница, тот же текст) хуже, чем нерабочая с виду кнопка.
- **Вкладка без данных, оставленная видимой «на всякий случай», — это
  приглашение нажать на пустоту.** «Экономист»/«Юрист» были всегда видны,
  просто приглушённые (`.thin`), когда линза пуста — задумано как честная
  подсказка, но на короткой карточке (например, простая сделка с
  недвижимостью, где юридических условий никто не публиковал) выглядело
  как нерассказанная история. Просьба владельца 18 августа: вкладка без
  данных не рендерится вовсе, а не показывается приглушённой — карточка
  показывает ровно те вопросы, на которые есть ответ. Родня уже
  записанного «Блок, который всегда полон, ничего не подбирает» — здесь
  зеркально: блок, который иногда пуст, не обязан существовать, чтобы
  сказать об этом.
- **Одно поле — одна линза.** `eco.share` показывался и на «Обзоре», и на
  «Экономисте», а у 249 карточек из 307 предмет назывался ещё и в плашке прямо
  над строкой: один и тот же абзац на 206 знаков читался дважды. Прежде чем
  добавлять поле на экран, проверьте, где оно уже показано, — и что соседний
  структурный блок не говорит того же самого другими словами.
- **Прежде чем наполнять поле, проверьте, не показан ли факт под другой
  подписью.** Наполнение «Структуры сделки» из текста отменено на проверке: 20
  из 30 отобранных предложений уже стояли на экране в «Предмете / доле». Это
  было бы не новое знание, а то же самое в двух местах. Проверка дешёвая —
  сравнить кандидата со всеми подписанными полями карточки, а не только с тем,
  которое заполняешь.
- **Признак дефекта — повод прочитать, а не основание стереть.** «В поле
  „Согласования" нет ни одного слова об одобрении» пометило 16 значений, но у
  трёх из них согласование было настоящим: «премьер-министр подписал
  распоряжение о продаже», «Банк России направлял предписание Росимуществу».
  Автоматическая чистка по такому признаку удалила бы факты. Признак сужает
  выборку для чтения глазами — решение принимает человек, и оно записывается в
  таблицу скрипта вместе с причиной.
- **Запятая внутри числа ломает шаблон с `[^,]`.** Правило
  `привлек\w*\s+[^,]{0,40}(?:млн|млрд)` не совпало с «привлекла 12,5 млн»: класс
  `[^,]` обрывается на запятой в числе. Замер показал 8 карточек вместо 13 — и
  среди пропущенных была ровно та, с которой пришёл вопрос. В русских суммах
  запятая — часть числа, а не разделитель: писать `[^.;]`.
- **Заголовок говорит об этой сделке, текст — обо всей истории актива.** Один и
  тот же признак («купил у X», «X продал») в заголовке почти всегда про эту
  сделку, а в «Дополнительной информации» сплошь и рядом про предыдущую смену
  собственника: «ранее, в 2011 году, „Газметаллпроект" выкупил у Елены
  Батуриной», «в 2024 году приобрела у Полюса „Лензолото"». Из 215 карточек с
  признаком продавца 91 имели его в заголовке — эта партия прошла чтение почти
  без отказов (3 из 91), остальные 124 заведомо шумнее. Партии разделять по
  месту признака, а не брать всё разом.
- **`продавц\w*` не совпадает со словом «Продавец».** Основа «продавц» есть у
  всех падежей, кроме именительного: «продавца», «продавцы», «продавцом» — да,
  «продавец» — нет. Четыре прогона искали сторону сделки этим шаблоном и не
  видели 99 карточек, подписанных «Продавец — X», а в бэклоге всё это время
  стояло «осталось ~50 кандидатов, и те шумные». Родня `\b` после приставки и
  `\w` в JS: правило молчит, а замер выглядит законченным. Любой шаблон по
  русскому слову прогонять на всех падежах, начиная с именительного.
- **«У» — не всегда предлог продавца.** «Приобретение сетью Лента магазинов у
  дома под брендом Монетка» — это тип магазина; «выкуп собственных акций у
  нерезидентов» и «выкуп у миноритариев» — сторона не названа. Признак «купил …
  у X» сужает выборку для чтения, но именем сам по себе не является.
- **Доля сократилась — не значит, что её продали.** «Доля Анатолия Карпова
  снизилась с 61% до 30,44%», «доля основного владельца сократилась с 70% до
  61,63%» — это размытие при допэмиссии: доли уменьшились, но никто ничего не
  продавал. Пять карточек из 34 по признаку «доля X» отклонены именно поэтому.
- **Заглавная буква сразу после предлога — плохая граница имени.** Правило
  «купил Y у X» искало `у\s+[А-ЯЁA-Z]`, а в тексте между предлогом и именем
  почти всегда стоит строчное пояснение: «у основателя Анатолия Покатилова», «у
  экс-депутата Госдумы Бекхана Агаева», «у компании «Курс»». Мимо прошли 54
  карточки, из них 14 с настоящим продавцом.
- **Поле, заполненное в данных, может быть не показано на экране.** У IPO и
  раундов плашка сторон устроена иначе («Инвестор → Получатель инвестиций»), и
  ячейки продавца в ней нет вовсе: 6 карточек из 597 с известным продавцом не
  показывали его нигде. Нашёл это не diff данных, а Playwright — проверка «на
  экране есть слово „продавец"». Заполнив поле, проверьте его НА ЭКРАНЕ, причём
  на карточке каждого типа сделки.
- **Текстовое поле стороны может быть невидимым: связанный `_id` рендерится
  первым.** Правка `seller` карточки RWB/офис «Открытия» («ВТБ» → «БМ-банк
  (входит в ВТБ)», точнее по выписке ЕГРН) прошла `review.py`, ушла в базу —
  и не изменила ничего на экране: `dealPlate` в `static/index.html` берёт
  `d.seller_id && co(d.seller_id) ? …` РАНЬШЕ текстового `d.seller`, а
  `seller_id` карточки по-прежнему указывал на профиль «ВТБ». Нашлось не
  diff'ом (текстовое поле честно поменялось), а прямым Playwright-чтением
  экрана — тем же приёмом, что и соседний урок про IPO/раунды. Правило то же,
  что у `buyer`/`buyer_name`: пара «ссылка на профиль + текст» не может редакти-
  роваться только с одной стороны — если для точной формулировки профиля нет
  (плодить профиль ради одной сделки не стоит), `_id`-ссылку снимают, а не
  оставляют рядом с текстом, который она перекрывает.
- **Отдельный справочник для «группы компаний» дублирует то, что уже есть в
  `COMPANIES`, и молча ломает ссылку на реальный профиль.** До 18 августа
  2026 группа компаний резолвилась через захардкоженный `HOLDINGS{}` в
  `static/index.html` (2 записи), а `company.holding.id` указывал в него, а
  не в `COMPANIES`. У профиля «УГМК-Инвест» `holding.id` УЖЕ был проставлен
  верно — на настоящий профиль «УГМК» (`g3a8fb04f`), это было сознательным
  решением ещё в `fix_petropavlovsk_buyer_and_asset_case.py` («Новый профиль
  связан с УГМК через `holding`, чтобы это не потерялось») — но
  `HOLDINGS['g3a8fb04f']` не существовало, и бейдж «Входит в группу» молча не
  рендерился ни на дочерней карточке, ни (обратной ссылкой) на карточке
  «УГМК»: связь была в данных и не была видна на экране. Второй, более тонкий
  случай — дубль: `HOLDINGS.vamin_tatarstan` («Группа «Вамин Татарстан»»)
  существовал ОТДЕЛЬНО от уже заведённого профиля `g896e444d` («Вамин
  Татарстан», без единой сделки и без ссылок на него) — та же компания была
  представлена в базе дважды, один раз реальным профилем, один раз текстом в
  чужом объекте. Починено переносом `HOLDINGS` в `COMPANIES`
  (`pipeline/migrate_holdings_to_company_profiles.py`): `holding.id` теперь
  ВСЕГДА ссылается на профиль в той же `COMPANIES`, резолвится через `co()`,
  а не через второй объект. Если у группы ещё нет своего профиля — заводится
  обычный профиль (как у «Арнест»), а не запись в отдельном справочнике: один
  способ хранить компанию, не два. Родня уже записанного урока «Пять мест
  хранения одних и тех же данных — не „исторически сложилось", а готовый
  баг» — только здесь не пять мест, а два, и урок тот же: у каждой сущности
  должно быть ровно одно место, где она заведена.
- **«Продавец» не всегда сторона сделки.** В карточках про маркетплейсы это
  слово значит «продавец на маркетплейсе»: «сервис аналитики для продавцов на
  маркетплейсах», «финансирование продавцов». Механический признак засчитал бы
  три такие карточки за названного продавца. Проверять, о ком речь, а не
  считать совпадение слова фактом.
- **Проверка «результат лежит в тексте» не работает на перечислениях.** Между
  именами продавцов почти всегда стоят слова, которых в результате нет:
  «Продавцы — основатели сети Михаил Норкин и Андрей Сафронюк». Сплошная
  проверка такое имя не подтверждает. Резать результат по «и» и запятым и
  проверять каждую часть отдельно — и обязательно проверить, что подмена одного
  имени («Михаил Норкин и Иван Петров») правило НЕ проходит.
- **Название в кавычках — часто не предмет сделки, а продавец.** Признак дубля
  «общее название в кавычках + та же сумма + 45 дней» дал по базе 5 пар, из
  которых верна одна: банк «Траст», продающий десятки активов, совпадает сам с
  собой («продал пакет акций «РуссНефти» за 1,4 млрд ₽» и «выставил на продажу
  земельный актив за 1,4 млрд ₽»). Рабочий признак — ДВА общих названия при
  одной сумме (тест `test_no_duplicate_deal_cards`).
- **Слияние карточек не должно обрывать ссылку.** Удалённый дубль остаётся в
  карте `merged` («id дубля → id оставшейся»), и `#/deal/<старый id>` открывает
  оставшуюся сделку. Иначе адрес из закладок или из чужого письма молча
  показывает общую ленту — а это выглядит как «сделка пропала».
- **Точка не значит конец предложения.** «18,8 млрд руб.», «январь 2022 г.»,
  «Калужская обл.», «Fortum Russia B.V.» — на этом уже один раз разрезали текст
  посередине и потеряли по половине фразы в 65 полях. Списку сокращений не
  верить: надёжнее правило «точка + пробел + заглавная», оно ошибается в
  безопасную сторону — склеит два предложения, а не разрежет одно.
- **Модальное окно живёт вне `#app` и переживает смену экрана.** Диалог правки
  добавляется в `body`, а перерисовка меняет только `#app`: после перехода по
  адресу подложка оставалась поверх новой страницы и молча перехватывала все
  клики — страница выглядела живой и не отзывалась. Всё, что кладётся мимо
  `#app`, обязано закрываться в `route()`. Поодиночке тест этого не видит:
  дефект нашёлся только на прогоне ВСЕГО набора, где окно оставлял предыдущий
  тест. Прогон одного теста — не проверка изоляции.
- **Тест ссылается на файл, которого нет.** `test_launch_features.py` импортировал
  `pipeline/review_fns_candidates.py`, README описывал его запуск, а самого файла
  в репозитории не было: часть работы приехала загрузкой через веб-интерфейс
  GitHub, и один файл в неё не попал. Загрузку мимо ветки сверять полным
  `pytest`, а не глазами по списку файлов.
- **Обрыв бывает и в НАЧАЛЕ значения, не только в конце.** `fix_truncated_fields.py`
  (A6) ловит значение, которое НАЧИНАЕТСЯ со знака препинания, и перекос
  «открывающих больше». У 13 полей дефект был зеркальным: значение начиналось
  с буквы («Фокус», выручка…»), а перекос — «закрывающих больше» (начало
  потеряно, конец остался). Признаки старого правила не пересекаются с новым,
  поэтому понадобился отдельный скрипт (`fix_truncated_field_heads.py`), а не
  правка старого, — но сама функция восстановления (`recover()` ищет
  предложение целиком в `extra`) переиспользована без изменений.
- **Вложенное название закрывается два раза, если открыто два раза.** Схема
  «[родовое слово] «[имя]»» — «Санаторий «Россиянка»», «ТВК «Авиапарк»» — в
  39 карточках теряла ВТОРУЮ «этажку»: «Санаторий «Россиянка» без неё. Это не
  та же правка, что «прямые кавычки вместо ёлочек» (там дефект — не тот
  символ), и не та, что «вложенные кавычки второго уровня — это не дефект»
  (там внутренняя кавычка ПРЯМАЯ и баланс уже верный): здесь просто не хватает
  одного знака препинания. Признак — количество «, превышающее количество » в
  пределах одного поля; правило проверено на себе: `assert`, что корректно
  вложенные («Торговый дом "Меридиан"») и просто две отдельные пары
  («Россиянка» и «Известия») правкой не трогаются.
- **Досочинить обрубленный факт — не вариант, даже когда цифра рядом.** У
  профиля «Арт-Финанс» название обрывалось на «(зарегистрировано в феврале
  2023 г»; дата выглядела правдоподобно, но не встретилась ни в одной
  карточке с этой компанией — источника для остатка фразы нет. Восстановили
  только то, что доказуемо (закрыли то, что уже написано), а обрубленное
  уточнение сняли целиком вместо того, чтобы дописать дату на глаз.
- **«Сеть закрыта политикой прокси» — факт одной сессии, не константа
  проекта.** `fetch.py` и рутина притока были написаны с фразой «в среде
  разработки исходящий доступ к новостным сайтам закрыт (403 на CONNECT)» —
  верной для той сессии, где это писалось. В другой сессии `curl` и
  `fetch.py --verify` показали 32 источника из 41 живыми. Сетевая политика
  окружения выбирается при создании и может отличаться от сессии к сессии
  (см. системный промпт про remote execution environment) — прежде чем
  доверять записи «сеть не работает», проверить самому, а не переносить вывод
  из одной сессии в другую как данность.
- **Сеть в среде разработки работает — не значит, что она работает в бою.**
  Проверка «api.telegram.org отвечает» делалась ЗДЕСЬ, в среде Claude, и на
  её основании `send_telegram.py` год бил в `api.telegram.org` напрямую. Но
  боевой хост — Timeweb (РФ), а это другая сеть: в соседнем проекте владельца
  на том же Timeweb замерено ~32% отказов на попытку соединения с Telegram
  (19 июля 2026), и решено это релеем на Cloudflare Workers, а не повторами
  — повторы борются со следствием. Отсюда `telegram_endpoint.py` и переменная
  `TELEGRAM_API_BASE`. Урок шире Telegram: у кода два разных места запуска
  (среда разработки и боевой хост), и «проверил исходящую связь» относится
  ровно к тому месту, где проверял. Прежде чем считать внешний адрес
  доступным в бою, спросите, из какой страны и какого дата-центра пойдёт
  запрос.
- **У соседнего проекта владельца уже может быть решение этой же задачи.**
  Вопрос «почему в „Автопосте" автопостинг работает без cron?» дал сразу два
  ответа, которых не было в «Компасе»: планировщик внутри самого веб-процесса
  (APScheduler в `lifespan` FastAPI — не нужен ни внешний cron, ни отдельный
  воркер, если процесс один) и релей до Telegram (см. выше). Оба проекта — на
  одном хостинге, у одного владельца, с одними и теми же ограничениями;
  прежде чем проектировать инфраструктурный кусок с нуля, стоит спросить, как
  это сделано рядом.
- **Стороной сделки может быть записан профиль совсем другой сущности.**
  У сделки ЛСР/Domina Пулково `target` ссылался на профиль компании, у
  которого в базе стояло имя человека («Владимир Селегень») — бессмыслица
  для сделки про отель. Полнотекстовый поиск подтвердил: имя не встречается
  ни в одном поле ни одной сделки — не потерянный факт, а испорченная
  ссылка. Профиль не переименовывается (нечем доказать правильное имя) —
  создаётся новый, верный (лот из юрлиц по тексту самой карточки), старая
  ссылка перенаправляется на него, ошибочный профиль удаляется. Родственный
  урок «предмет вместо стороны», но здесь испорчена не роль, а сам профиль,
  на который роль ссылается.
- **Тормоз, который год держит дверь закрытой, прячет баг за дверью.**
  `NEW_CARDS_NEED_REVIEW` (E9) год не пропускал в базу НИ ОДНОЙ новой
  карточки — и ни разу не проявлялся факт, что `promote.py` вообще не
  писал `eco`/`law` в новую запись. Как только первая карточка реально
  прошла (после ручного обзора живого источника), десятки мест в
  интерфейсе, читающие `d.law.adv`/`d.eco.finadv` без проверки на
  существование объекта, обрушили «Консультантов» и «Аналитику» с
  `pageerror`. Защитный тормоз проверяет ОДНУ причину отказа (фильтр не
  измерен), но не гарантирует, что путь ЗА тормозом вообще рабочий, —
  первый реальный проход через любой долго запертый шаг стоит проверять
  особенно внимательно, а не считать «раз тормоз стоял — значит, за ним
  всё в порядке».
- **Разбор источника доверяет числу из чужого абзаца.** У «ВТБ продал
  Holiday Inn» автоматический разбор взял сумму «100 млрд ₽» — она стояла
  в тексте, но относилась к ДРУГОЙ сделке (продаже всего «Галс-Девелопмента»,
  в периметр которой входит и эта гостиница), а не к гостинице отдельно
  (эксперты оценивали её в 8–10 млрд ₽). Сумма — самое рискованное поле для
  доверия правилу «первое число в тексте»: она почти всегда обязана
  относиться именно к обсуждаемому предмету, а не к соседнему упоминанию.
- **В CSS позже в файле значит сильнее — даже если условие раньше.** Мобильное
  `@media(max-width:560px){.ask input{flex:1 1 100%}}` стояло РАНЬШЕ в файле,
  чем безусловное базовое `.ask input{flex:1}` той же специфичности — и на
  экранах ≤560px побеждало базовое правило, а не мобильное: плейсхолдер
  обрезался («Уточните д…») вместо переноса на свою строку. Условие `@media`
  влияет на то, применяется ли правило вообще, но не на порядок каскада при
  равной специфичности — там решает то, что позже в исходном тексте. Чинится
  переносом мобильного переопределения ПОСЛЕ базового правила, а не
  усилением специфичности.
- **Строчный элемент молча игнорирует `margin-top`/`margin-bottom`.**
  `.company-deal-preview .meta` — `<span>`, и `margin-top:4px` на нём браузер
  не применяет: подпись роли и типа сделки клеилась встык к заголовку
  («…у CitigroupПокупатель · M&A») вместо переноса на свою строку. Чинится
  добавлением `display:block` (или `inline-block`), не увеличением отступа —
  увеличивать было нечего, отступ применялся к несуществующему полю.
- **Порог схожести без нижней абсолютной планки даёт ложные 100% на коротких
  множествах.** Фильтр дублей в `extraHtml()` считал долю общих слов как
  `common / min(|A|, |B|)` — у короткого поля-эталона (например, `eco.val`
  «...41 500 млн ₽...», после отсева стоп-слов и слов короче 4 знаков сведённого
  к одному слову «млрд») ЛЮБОЕ финансовое предложение из другого поля давало
  100% совпадение и удалялось как дубль, хотя по смыслу дублем не было — так
  стёрлось предложение с именами реальных покупателей на карточке Точка/Траст.
  Чинится абсолютным минимумом числа общих слов (`common >= 3`) в дополнение к
  доле, а не только долей — родня уже записанного урока про короткие слова и
  порог в три знака, только здесь короткое не слово, а всё множество.
- **Вертикальное центрирование обрезает оба конца сразу, если контент выше
  контейнера.** Героическая панель (`.hs-in{justify-content:center}` внутри
  `.heroslider{height:100svh;overflow:hidden}`) при недостатке высоты на
  невысоких телефонах теряла И заголовок сверху, И кнопку снизу одновременно —
  с телефона это выглядит как «панель обрезана» без понятной причины. Замена на
  `justify-content:flex-start` с отступом сверху под логотип сохраняет более
  важное (заголовок) и жертвует менее важным (кнопка/точки внизу) при нехватке
  места — типовое решение для контента, чья высота на мобильном непредсказуема,
  предпочтительнее центрирования, которое одинаково рискует обоими концами.
- **Кнопка и её видимый эффект могут быть далеко друг от друга на телефоне.**
  «+ Новый диалог» в ассистенте меняло текст в ленте переписки, но лента стояла
  на ~150–250px ниже кнопки (за переключателем режима) — клик менял состояние,
  но пользователь эту смену не видел и решал, что кнопка не сработала. Если
  результат клика отображается не рядом с самой кнопкой, нужны явные
  `scrollIntoView`/фокус на элемент результата — иначе рабочая кнопка
  неотличима от сломанной.
- **Экранирование Python не равно экранированию JS.** При переносе прототипа
  строкового разделителя `"\x00"` из Python в JS-код тем же текстом получился
  не литерал с последовательностью экранирования, а буквальный нулевой байт,
  записанный в `static/index.html` (найдено по `grep -a` — обычный `grep`
  молча репортует «binary file matches» — и по прямому подсчёту байт `\x00` в
  файле). При переносе регулярок/строк между языками синтаксис экранирования
  проверять для целевого языка, а не полагаться на визуальное сходство.
- **Правка, снимающая одну находку, может тихо сломать другой, более старый
  инвариант.** Источник карточки `g2544a5cb` не подтверждал сделку (вёл на
  статью 2014 года о другой теме) — первое исправление просто очистило `src`
  до пустого списка, показавшееся честным («неверная ссылка хуже отсутствия
  ссылки»). `pytest` тут же поймал `test_every_deal_has_a_source_link`: у
  КАЖДОЙ карточки обязана быть хотя бы одна http-ссылка — это не формальность,
  а прямое обещание продукта («со ссылкой на первоисточник», первая строка
  `PRODUCT_ROADMAP.md`). Пустой список оказался не более честным решением, а
  просто другим нарушением. Починено восстановлением ссылки с честной
  подписью («источник не подтверждён») вместо удаления. Урок: одна находка не
  существует в вакууме — правка на неё обязана пройти ВЕСЬ `pytest`, а не
  только пройти проверку здравым смыслом самой находки.
- **Слаг URL, не называющий стороны сделки напрямую, — не доказательство, что
  источник перепутан.** Три карточки были помечены «источник о другой сделке»
  по признаку «слаг не содержит имён сторон карточки». Живой поиск
  (WebSearch/WebFetch) подтвердил дефект только у одной из трёх: у остальных
  двух слаг использовал метонимию («бенефициар «Петербургской звезды»» вместо
  имени человека, который её контролирует) или альтернативное название той же
  стороны (бренд «Grand Line» вместо юрлица «Металлист») — по существу
  источник был верным, просто не совпадал по буквам. Признак «слаг не
  совпадает по словам» годится, чтобы ОТОБРАТЬ кандидатов для проверки, но не
  чтобы вынести приговор без самой проверки — тот же класс урока, что и
  «признак дефекта — повод прочитать, а не основание стереть».
- **`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` — синтаксис Postgres, не
  SQLite.** При добавлении `password_hash` в уже существовавшую таблицу
  `users` (`create_all()` не трогает существующие таблицы, только создаёт
  недостающие) первая попытка миграции использовала `IF NOT EXISTS` — на
  Postgres (Timeweb) сработало бы, а на локальной SQLite команда молча не
  добавила колонку (проверено напрямую на `kompas.db`: колонка не
  появилась, приложение не упало — ошибка была поймана общим `except`).
  Починено переходом на диалект-независимую проверку через инспектор
  SQLAlchemy (`inspect(conn).get_columns(...)`) и обычный `ADD COLUMN` без
  `IF NOT EXISTS`, который понимают оба диалекта. Тот же класс урока, что
  экранирование между языками: синтаксис, работающий в проде, может молча
  не работать в деве (или наоборот) — проверять миграцию на ОБЕИХ базах, а
  не полагаться на то, что команда «должна быть переносимой».

  адреса в списке, а не равенство), несколько записей туда — это нормально

  `FIXES` в трёх разных файлах `pipeline/ingest/fixes/` всё ещё ссылались
  на неё — тест упал с «карточки нет ни в базе, ни в очереди
  предпросмотра». Это не новый класс ошибки: тот же приём уже применён к
  Visa/BioCatch и Smallest.ai (комментарий в начале `review.py`) — но
  сборка партий дочитывания шла ПОСЛЕ того прецедента и снова наступила на
  те же грабли, потому что скрипт слияния (`merge_duplicate_deals.py` и
  его аналоги) сам по себе не знает, что где-то в `fixes/` есть записи на
  удаляемый id — это не пересекающиеся файлы, и `grep` по всем `fixes/*.py`
  на id дубля перед записью — обязательный последний шаг любого слияния
  сделок, а не факультативная подчистка.
- **`events[0].note` — первое место для чтения в G7, не последнее.** На
  двух карточках подряд (`gdfce7e3d`, `g692dcc6b`) дословная цитата уже
  лежала в кэше самой карточки, но обрывалась на полуслове («…она
  специализирует», «…входила в состав маркетингового партнерств») —
  видимо, ограничение длины при исходном разборе. WebFetch по тому же
  `src` дозабирал ПРОДОЛЖЕНИЕ той же фразы, а не новый факт: дешевле и
  надёжнее сначала прочитать, что уже дозабрано в самой карточке (там
  почти всегда лежит структура сделки целиком, просто не перенесена в поля
  экрана), и только потом идти за недостающим хвостом предложения.
- **Основатель компании — не то же самое, что её нынешний владелец.** У
  «Диалога» статья называет Ольгу Давыдову основательницей сети (2003 год)
  в одном предложении и, ОТДЕЛЬНО, «рациональным шагом для его
  собственника, Ольги Давыдовой» — только второе предложение подтверждает
  её как продавца НА МОМЕНТ СДЕЛКИ. Компания могла сменить владельца много
  раз за 20+ лет; писать основателя в поле `seller` только по факту
  основания — недоказанный перенос, даже если имя больше нигде не
  встречается. Нужна отдельная фраза, называющая роль ПРЯМО («собственник»,
  «владелец», «продал», «выступала продавцом») и относящуюся ко времени
  сделки, а не к истории компании. Родня урока «заголовок говорит об этой
  сделке, текст — обо всей истории актива»: там путали разные СДЕЛКИ одного
  актива, здесь — разные РОЛИ одного человека в разное время.
- **`review.py` не умеет переносить сделку в другой год — и не должен.** У
  `g6d73538c` карточка стояла с датой прихода в приток (4 августа 2026),
  источник же прямо называл декабрь 2025 года: неверны и год, и месяц.
  `date_is_supported()` в `review.py` устроен так, что уточнять день можно
  только ВНУТРИ уже известного года, а перенос в другой год он отклоняет
  всегда — это не недоработка, а сознательная граница: смена года по
  таблице `FIXES` слишком похожа на «утверждение нового», чтобы проходить
  тем же лёгким механическим путём, что уточнение дня. Когда источник
  всё-таки называет другой год, это отдельный одноразовый скрипт со своим
  `assert` на исходное состояние (пример: `fix_osnova_sviblovo_date.py`), а
  не запись в общей таблице. Тот же скрипт вскрыл и соседний случай:
  источник назвал месяц и год, но не число — писать «2025-12-01» значило
  бы выдумать день, поэтому в поле `date` идёт ТОЛЬКО год («2025»), а
  месяц остаётся текстом в `eco.context` (тот же принцип, что уже
  применён к датам-заглушкам «1 января» в `fix_placeholder_dates.py`).
- **Источник может расходиться сам с собой — заголовок и тело статьи не
  гарантированно согласованы.** У `g9254527a` заголовок статьи РИА
  Недвижимость называл учредителя «Флеганова», а тело той же статьи — со
  ссылкой на ЕГРЮЛ — «Ферганов»: разбор притока скопировал имя из
  заголовка источника, унаследовав его опечатку. Это не «наша карточка
  разошлась с источником» (уже описанный класс уроков), а более редкий
  случай — сам источник противоречит себе. Решает это ссылка на более
  авторитетную часть текста (официальный реестр против журналистского
  заголовка), а не дословность сама по себе — дословно верны ОБА варианта,
  вопрос в том, какому верить. Проверено трижды отдельными запросами
  (процитировать заголовок и тело рядом), прежде чем чинить, — расхождение
  внутри источника легко принять за ошибку самого инструмента чтения.
- **Число и дата в статье могут относиться не к репортируемой сделке, а к
  промежуточному шагу или к более раннему моменту истории актива.** У
  «Абсолют Страхование» источник называл сразу два факта, похожих на
  готовые значения для `sum` и `date`, — и оба оказались не про эту
  сделку. Оценка «10 млрд руб.» была из 2024 года, когда актив только
  выставили на продажу; к моменту реального закрытия (2026) цена могла
  измениться сильнее, чем за обычный срок между оценкой и сделкой, — в
  `sum` она не пошла, только в `eco.context` как история. Дата «26 июня»
  относилась не к репортируемому закрытию, а к промежуточному
  корпоративному шагу (передаче актива малоизвестному ОАО, которое затем
  заложило его обратно управляющей компании прежнего владельца) — и год у
  этой даты source вообще не называл. И сумма, и дата были рядом с
  правильными словами («оценивалась», конкретное число дня и месяца) и
  прошли бы механическую проверку `review.py`, но обе описывают не то
  событие, которое несёт карточка. Прежде чем писать число или дату в
  поле сделки, проверьте, к какому именно событию оно относится по
  тексту, — не только что оно похоже на нужный формат.
- **Число может быть верным фактом и совсем не той величиной.** У «Арнест»/
  Reckitt Benckiser в `sum` стояло «18 млрд ₽» — правдоподобная сумма
  сделки для такого актива. Источник же прямо пишет: «Сумма сделки не
  раскрывается. Но по ее итогу Reckitt ожидает убыток на £175 млн (около
  18 млрд руб.)» — это ожидаемый бухгалтерский УБЫТОК ПРОДАВЦА от сделки,
  а не цена актива. Урок «Разбор источника доверяет числу из чужого
  абзаца» (ВТБ/Holiday Inn) — про число не того ПРЕДМЕТА; здесь предмет
  тот же самый, но число — не та ВЕЛИЧИНА (убыток вместо цены). Оба
  случая ловятся одним правилом: прежде чем писать число в `sum`,
  проверьте не только «это про ту сделку», но и «это именно цена, а не
  другая метрика с тем же порядком величины» — рядом почти всегда
  найдётся независимая оценка (здесь — 12–14 млрд ₽ от аналитика), она и
  идёт в `eco.val`, а поле суммы остаётся честно пустым.
  Третий случай того же правила — «Нордлайн»/TotalEnergies: `sum` нёс
  «$4,1 млрд», а источник называет эту цифру как СПИСАНИЕ TotalEnergies
  ВСЕХ российских активов в 2022 году (бухгалтерское обесценение по МСФО),
  а не цену продажи 10%-й доли «Арктик СПГ 2» «Нордлайну» в 2026-м — ни
  один из двух источников карточки цену ЭТОЙ сделки не называет вовсе.
  Починено НЕ через `review.py` (он умеет ДОПОЛНЯТЬ по цитате, но не
  проверяет, что число относится к правильному ГОДУ и ПЕРИМЕТРУ), а
  отдельным одноразовым скриптом с `assert` на исходное значение —
  `pipeline/fix_nordline_arctic_sum_misattribution.py`, тот же приём, что
  уже применяется для смены года в дате. Само число не потеряно: оно
  перенесено в `eco.context` с честной подписью, что это списание
  2022 года, а не цена сделки.
- **Тест, ссылающийся на локальный кэш, зелен только в той сессии, где
  кэш уже создан руками.** `test_full_text_fetch_skips_already_cached_urls`
  проверял `already_fetched()` против файла в `data/inbox/raw/` — а эта
  папка в `.gitignore` (сырьё притока в git не хранится) и в свежем
  контейнере просто не существует. Тест падал на чистом `HEAD`, что
  подтвердил `git stash` + прогон теста в одиночку ДО любых своих правок.
  Тот же класс, что и «сеть закрыта политикой прокси — факт одной сессии,
  не константа», и «тест ссылается на файл, которого нет», только здесь
  причина не сеть и не забытая загрузка, а гитигнор: локальное состояние
  одной сессии тихо стало неявной зависимостью теста. Починка — не
  чинить сам кэш (он и не должен быть в git), а сделать тест
  самодостаточным: `monkeypatch` подменяет путь на `tmp_path`, файл кэша
  тест создаёт сам. Правило шире: тест, который читает НАСТОЯЩУЮ рабочую
  директорию пайплайна (а не `data/inbox/fixtures/`, которая для этого и
  существует, или временную), проверяет не код, а то, что где-то раньше
  кто-то что-то туда положил руками.
- **Диапазон при разборе может схлопнуться в одну цифру и потерять нижнюю
  границу.** У ГК «Коломенский»/«Пеко» `sum` нёс «900 млн ₽ (по оценке)»,
  хотя источник называет диапазон: «Консультант по M&A… оценивает
  стоимость… в 800–900 млн руб. с учетом долга». Автоматический разбор
  взял только верхнюю границу и потерял и «800», и оговорку «с учётом
  долга» — сумма не была неверной (900 — законный край диапазона), но
  была НЕТОЧНОЙ. Признак того же класса, что «Разбор источника доверяет
  числу из чужого абзаца», только здесь число из ТОГО ЖЕ предложения, но
  урезано до одной цифры вместо диапазона.
- **У `review.py` для `sum` и `eco.sum` — разные проверки, и они дают
  разные ответы на одну и ту же правку.** Поле `sum` при точном имени
  проверяется `sum_is_supported()` — распознаёт признаки оценки
  (`оцен`, `могла составить`) и САМ разрешает пометку «(по оценке)»,
  даже если этих слов нет в тексте цитаты. `eco.sum` — уже другое имя
  поля, идёт через общую дословную проверку (`flat(new) in flat(quote)`)
  без всякой скидки на смысл: если в цитате написано «оценивает», а не
  «по оценке», пометка `(по оценке)` в `eco.sum` будет отклонена, даже
  когда та же самая пометка для `sum` только что прошла. Не баг —
  пометка и атрибуция всё равно видны рядом, в `eco.val`; но писать
  правку сразу для обоих полей с одинаковым текстом нельзя — `eco.sum`
  проверяют по буквам.
- **Предмет сделки, вырезанный подстрокой из заголовка, стоит не в
  именительном, а в том падеже, который диктует управление глагола.**
  «купил X» — X в винительном («производственную базу»), «присоединение
  X» — в родительном («Дальневосточного банка»), «долю в X» — в
  предложном («производителе картошки»). `guess_parties()` в draft.py
  просто вырезал хвост фразы, и на экране «Предмет:» показывал ровно этот
  падеж — владелец нашёл это в живых постах канала 9 августа, дефект был
  системным, а не разовым. Механическая замена «в начальную форму» не
  подходит: pymorphy сводит слово к лемме, а не согласует прилагательное
  перед ним («дальневосточного банк» вместо «дальневосточный банк»).
  Чинится согласованием ТОЛЬКО головы словосочетания (первого
  существительного) и прилагательных перед ней; всё, что после головы —
  зависимый оборот в своём падеже («производитель [чего?] картошки для
  чипсов») — не трогается никогда. Готового морфологического решения
  недостаточно без защит: первая версия сломала «45% сети X» → «45% сеть
  X» (после «%»/числительного — управляемый родительный, а не сказуемое),
  «Группа компаний X» → «Группа компании X» (голова — первое слово,
  дальше не ищем лучший вариант), «Рив Гош» → «Рив Гоши» (заглавная буква
  — имя/бренд, pymorphy угадывает падеж наугад), «права на X» → «право на
  X» (словоформа «права» неоднозначна между родительным ед. числа и
  именительным/винительным мн. числа одной и той же леммы — смена числа
  меняет смысл). `pipeline/ingest/casing.py` — реализация со всеми
  защитами; замер на 183 карточках дал 19 верных срабатываний и ни одного
  ложного. Правило подключено в draft.py (root cause), исторический хвост
  починен `pipeline/fix_asset_case.py`.
- **Признак «упомянут госорган + слово разрешения» не различает «дали» и
  «не дали» — и не должен.** `test_approval_is_not_left_in_prose` отклонил
  правку `gmru-rodnye-polya`: `eco.context` нёс «Ведомство указало, что…
  не получил разрешение правительства РФ», а `law.appr` оставался пустым.
  Формально предложение говорит об ОТСУТСТВИИ разрешения, а не о
  согласовании, — но тест прав по существу, не только формально: вопрос
  «было ли государственное разрешение» принадлежит «Согласованиям»
  независимо от ответа (да, нет, не раскрыто). Правка — не поспорить с
  тестом, а перенести факт в `law.appr`, оставив в `eco.context` только
  историю без правовой причины. Правило шире одной карточки: если фраза
  называет госорган и решение (одобрил/не одобрил/не получил разрешения),
  её место — `law.appr`, а не соседнее поле, каким бы уместным оно ни
  казалось по смыслу истории.
- **Пропуск предложения ПОСЕРЕДИНЕ цитаты рвёт дословность так же, как
  пропуск в начале или в конце.** Три раза за один день (`gmru-kolomenskoe-peko`
  eco.share, `gmru-geopromining-zabaikalie` eco.share, `gmru-nordgold-chukotka`
  eco.val) `review.py` отклонял правку с формулировкой «значение не лежит
  в цитате дословно» — хотя каждое слово результата было взято прямо из
  источника. Причина одна и та же: между двумя нужными кусками текста
  стояло третье предложение («сказано в отчетности компании», «Как
  отмечает эксперт, если первые вложения…»), и `new` перескакивал через
  него к следующему нужному куску — а проверка требует, чтобы
  `flat(new)` было НЕПРЕРЫВНЫМ куском `flat(quote)`, без разрывов.
  Лечится не борьбой с проверкой, а включением пропущенного предложения
  в `new` целиком, даже если оно не несёт полезного факта само по себе:
  дословность — это про порядок символов, а не про то, нужна ли каждая
  фраза читателю.
- **Прохождение `review.py` не гарантирует, что на экране будет то, что
  заявлено в `why`.** У `gmru-vysochaishy-komi-oil` правка `eco.val`
  прошла проверку дословности (её `new` — честная подстрока `quote`), но
  начиналась не с начала цитаты, а с середины — вступительное
  предложение с именем эксперта («Руководитель проектов Strategy
  Partners Анна Васильева предупреждает…») осталось только в `quote`,
  для проверки, а не в `new`, который реально идёт на экран. `why` при
  этом утверждал «с атрибуцией» — а атрибуции читатель не видел вовсе.
  `review.py` проверяет ДОСЛОВНОСТЬ, а не ПОЛНОТУ смысла, который правка
  обещает. Поймано не таблицей `FIXES`, а прямым чтением текста на
  странице после записи — тем самым шагом Playwright, который для
  других карточек выглядит формальностью («слово есть на экране»).
  Правило: если `why` обещает конкретный факт (имя, атрибуцию, число),
  проверяйте текстовым поиском именно ЭТО слово на странице, а не просто
  что раздел непустой.
- **Правило меряют в точке ПРОИЗВОДСТВА, а не по сохранённому полю.**
  Правило падежа предмета замерили по полю `asset` в базе — «19
  срабатываний на 183 карточках, ложных ноль», замер выглядел
  законченным. Но `asset` заполнен у 179 карточек, а РОЖДАЕТСЯ предмет
  из заголовка: `guess_parties()` достаёт его у 1027. Прогон по
  заголовкам с выключенной нормализацией показал косвенный падеж у 244
  предметов, из которых правило чинило НОЛЬ. Разница между двумя
  замерами — не погрешность, а разные множества: сохранённое поле
  показывает результат ПОСЛЕ правила (и потому всегда выглядит чистым),
  заголовок — материал ДО него. Прежде чем считать правило рабочим,
  прогоните его по входу, а не по выходу.
- **Запрет, написанный для головы словосочетания, нельзя проверять на
  всей фразе.** У правила падежа отказы (кавычки, латиница, заглавная
  буква) задумывались для ГОЛОВЫ — «Рив Гош» не склоняем, потому что это
  бренд. Проверялись же они на каждом слове фразы, а у предмета сделки
  почти всегда есть хвост с названием: «онлайн-школу ProductStar»,
  «российскую «дочку» Goldman Sachs», «частную сеть АЗС Elke Auto». Один
  латинский или закавыченный токен в хвосте глушил правило целиком, и
  оно молчало на 244 предметах из 1027. Родня уже записанного урока
  «правило, написанное для начала строки, не увидит того же дефекта в
  конце», только зеркальная: здесь проверка была шире, чем нужно, а не
  уже. Спрашивайте не «что запрещено», а «ГДЕ это запрещено».
- **`pymorphy.parse(word)[0]` — не лучший разбор.** У составных слов
  порядок не по вероятности: у «онлайн-школу» первым идёт мужской род со
  score 0,093, женский с 0,907 — вторым. Порог достоверности
  (`score < 0.1`) из-за этого зарубал верное слово. Брать `max(...,
  key=score)`. Соседняя ловушка того же семейства: неоднозначность надо
  проверять по СЛОВОФОРМЕ, а не по лемме — у «телеком» лучший разбор
  творительный от «телек», а два других дают именительный от «телеком» с
  той же вероятностью, и правило превращало «телеком провайдера» в
  «телек провайдера».
- **Асинхронный рендер не попадает в анимацию появления.** `route()`
  запускает проявление (`.reveal` -> `.reveal.in`) сразу после вызова
  рендера. `renderPreview` — единственный рендер, который ждёт `fetch`:
  к моменту, когда карточка появляется в DOM, проявление уже отработало
  по разметке состояния загрузки, и все 13 блоков навсегда остаются с
  `opacity:0`. Снаружи это «страница пустая, только жёлтая плашка», при
  этом в консоли чисто, элементы на месте, `inner_text` их видит.
  Проверка «текст есть на экране» такое не ловит — нужна проверка
  вычисленной прозрачности. И ловится это ТОЛЬКО на холодной загрузке:
  на тёплой странице (общий `page` в `test_ui.py` уже прогрет)
  pending.json успевает вернуться раньше кадра, и дефекта нет. Любой
  `async` рендер обязан сам перезапустить проявление в конце.
- **«Не привлекался» — это утверждение, а не пустота.** У карточки ГАП
  «Ресурс»/Granmulino в «Финансовом консультанте» стояло «Не
  привлекался», а в статье прямо сказано: «Советником в сделке со
  стороны продавца выступал инвестбанк Unicorn». Пустое поле читатель
  простит, ложное отрицание — нет, и заметить его труднее: глаз
  скользит мимо заполненного поля. Дочитывая карточку, проверяйте не
  только прочерки, но и все категорические отрицания («Не привлекался»,
  «Публично не сообщалось», «Не раскрывались»).
- **«Цель сделки», совпадающая с «Дополнительной информацией» слово в
  слово, — это не заполненное поле.** У 7 карточек из 9 первой партии
  дочитывания `eco.rationale` был дословной копией `extra`, у двух — с
  протёкшей служебной пометкой разбора внутри («(МТС-банк
  (покупатель))»). Формально поле не пусто, счётчик заполненности
  доволен, а читатель видит один и тот же абзац дважды. Это уже
  записано как «один и тот же текст лежит в двух полях», но там речь
  шла о ручных правках; здесь копию делает САМ импорт, то есть дефект
  системный и есть у сотен карточек. Дочитывая, сверяйте `rationale`
  с `extra` до того, как искать новые факты.
- **Счётчик заполненных полей легко накрутить, не дав читателю ничего.**
  Соблазн при дочитывании базы: расширить механическую раскладку
  «Дополнительной информации» по полям на карточки, где объекты `eco`/
  `law` уже есть. Замер: 815 карточек «получили бы» новые поля — но 776
  из них это «остаток текста в „Контекст"» (переклейка ярлыка), а 516 —
  срабатывание правила `share` на любом предложении с процентом. Медиана
  заполненности выросла бы, содержание — нет. Прежде чем радоваться
  приросту метрики, посмотрите, ЧТО именно в неё попало.

## Что искать для линзы «Юрист» при чтении статьи (просьба владельца, 9 августа)

Линза «Юрист» пуста была у 75% карточек 9 августа; кампания дочитывания
(четыре параллельных потока, читающих `law.struct`/`appr`/`terms` по цитате)
подняла заполненность за неделю — замер 17 августа тем же регэкспом
заглушек (`PLACEHOLDER` из `static/index.html`, переведённым на Python
дословно) по всем 1563 карточкам: `struct` заполнен у 39,8% (622),
`appr` — у 20,7% (323), `terms` — у 20,6% (322), линза пуста целиком
(все три поля — заглушка или пусто) у 43,3% (676). Задача читать статьи
именно под эту линзу остаётся — она не закрыта, просто продвинулась
сильнее, чем документация успевала отражать.

Читая статью, ищите не только «кто кому сколько», но и ЧЕМ обставлена сделка:

- **заверения об обстоятельствах** (representations and warranties) — что
  продавец подтвердил о предмете;
- **возмещение потерь / индемнити** — кто платит, если заверение окажется
  неверным, и есть ли предел;
- **ограничение ответственности** — потолок, срок предъявления претензий,
  порог существенности;
- **отлагательные и отменительные условия** — что должно случиться до
  закрытия (согласие ФАС, правкомиссии, кредиторов, смена контроля);
- **опцион** — колл/пут, обратный выкуп, право первого отказа, tag/drag along;
- **отложенный платёж (earn-out)** — часть цены зависит от будущих
  показателей;
- **эскроу и обеспечение** — где лежат деньги до закрытия, залог, поручительство;
- **неконкуренция и неперемание сотрудников** — на какой срок и территорию;
- **обязательства сохранить бренд, команду, производство** — часто
  единственное «условие», которое вообще раскрывают в российских сделках;
- **применимое право и порядок разрешения споров** — редко, но встречается.

Перед тем как писать найденное предложение в `law.terms`, задайте ему один
вопрос: это условие, на котором ПОКУПАТЕЛЬ согласился на СДЕЛКУ, — или
сообщение о том, что ПРОДУКТ/БРЕНД цели продолжит работать как раньше,
адресованное её собственным клиентам? Второе дословно похоже на первое
(«стандарты и сертификаты сохранятся» рядом читается как «условие сделки»),
но это пресс-релизная реассюранс-фраза, а не переговорное условие — ей не
место в «Юристе», даже если она НАЗЫВАЕТ те же слова («сертификат»,
«стандарт»), что и настоящее обязательство сохранить бренд. Ловится это
только вопросом «кому и о чём эта фраза», не формой — см. урок про
`gebead2e8`/HeadHunter выше.

Всё это идёт в `law.terms` (условия), `law.struct` (как устроена сделка
юридически) и `law.appr` (согласования), с тем же требованием дословной
цитаты. Если условие названо в тексте, но лежит у нас в «Контексте» или
«Дополнительной информации» — это перенос, а не новое утверждение, и делать
его нужно.

- **Список узнаваемых согласующих органов в тесте не покрывает все реальные
  согласования — расширять его, а не избегать поля.** `test_approval_names_a_body`
  проверяет `law.appr` регуляркой `APPROVING_BODY` со списком слов (ФАС, ЦБ,
  президент, министерства…). У фонда «Восход»/ракеты «Воронеж» единственное
  согласование в источнике — заключение АО «ЦНИИМаш» (головной институт
  госкорпорации «Роскосмос») по эскизному проекту, и слова «Роскосмос» в
  списке не было: честная, дословная правка упала на пустом месте. Чинится
  не переносом факта в другое поле (это было бы то же самое «пояснение
  объясняет устройство теста, а не смысл поля»), а добавлением нового
  органа в список — тем же путём, что уже добавляли «министерств[а-яё]*»
  для зарубежного регулятора. Второй урок того же прогона: фраза,
  называющая ограничение регулятора («ЦБ сохранил более 50%»), не всегда
  содержит узнаваемое слово из списка в ЭТОЙ конкретной цитате — если рядом
  в источнике есть предложение, где регулятор назван по имени явно («Банк
  России»), лучше цитировать его, а не самое релевантное по смыслу
  предложение.
- **Число из подзаголовка о выкупе бизнеса может быть суммой ЗАЙМА на его
  финансирование, а не ценой актива — и это не всегда повод её снимать.**
  У «Сергей Дарькин/Владморрыбпорт» `sum` нёс «18,7 млрд ₽» — источник прямо
  называет эту сумму как ДВУХЛЕТНИЙ ЗАЁМ ВТБ под залог недвижимости порта,
  выданный именно для покупки доли, а не как объявленную цену сделки.
  Оставлено как есть (заём, привлечённый специально под покупку контрольного
  пакета, — разумная нижняя граница цены при полном заёмном финансировании,
  в отличие от списания TotalEnergies 2022 года, которое вообще не относится
  к периметру сделки, см. «Число может быть верным фактом и совсем не той
  величиной» выше), но разница между «цена» и «сумма, которую видно по
  факту финансирования» стоит держать в голове при каждой правке `sum`.
- **Полная перезапись JSON из устаревшего снимка стирает чужую уже
  запушенную работу молча — и это не конфликт, git его не видит.**
  Скрипт «Глубокая ревизия — партии 8–10» держал `deals_promoted.json` в
  памяти дольше, чем занял чей-то `git push` между чтением файла и
  записью: он дописал свои поля (`src`, `deep_researched`) для СВОИХ
  карточек и сохранил файл целиком — `json.dump` пишет цельный снимок, а
  не патч, поэтому переименования и 10 описаний из партии 90 (не
  входившие в снимок скрипта, потому что были запушены уже ПОСЛЕ его
  чтения) исчезли, откатившись к состоянию до правки. Коммит лёг прямым
  потомком того, что стёр, — git принял его чистым fast-forward,
  конфликта не было ВООБЩЕ, хотя контент откатился. Это опаснее обычного
  конфликта в `deals_promoted.json` (тот хотя бы виден): здесь пропажа
  обнаруживается только тем, что кто-то натыкается на уже сделанную
  работу как на невыполненную. Смягчение — то, что рутина и так должна
  делать: `git pull --rebase` НЕПОСРЕДСТВЕННО перед записью, а не только
  в начале прогона, и семантический diff к `HEAD` сразу после записи;
  если между чтением файла в скрипте и его записью прошло много
  времени/токенов (несколько партий подряд в одной сессии, долгая
  генерация текста), безопаснее перечитать файл заново прямо перед
  записью, а не доверять снимку, загруженному в начале. Найдено и
  восстановлено `pipeline/fix_komi_tendernoe_names_and_describe_batch50.py`
  повторным (идемпотентным) прогоном.
- **Блок «Ход сделки» целиком не рендерился при одном событии — и прятал
  вместе с пустыми также содержательные `note`.** Починка обрубленного
  `events[0].note` карточки `g21795ec9` (см. `fix_g21795ec9_truncated_note.py`)
  сначала выглядела завершённой: JSON поправлен, `review.py`-подобный
  `assert` на исходное состояние прошёл. Playwright-проверка «текст есть на
  экране» показала обратное: `timelineHtml()` возвращает `""` целиком, если
  `dealEvents(d).length<2` — а у карточек с ОДНИМ событием, чей `kind`
  совпадает с текущим статусом, `dealEvents()` не добавляет вторую
  синтетическую строку, и `rows.length===1` всегда. Восстановленный абзац
  про ALMI Partner был записан в базу и не виден НИГДЕ на сайте — ни на
  самой странице сделки, ни (без ссылки на неё) на отдельной странице этапа.
  Замер по всей базе: 46 карточек с одним событием и непустым `note`.
  Починка — не «показывать всегда» (тест `test_deal_has_timeline_and_inline_correction_dialog`
  специально проверяет обратное на `agrostroy-zemlya`, чей `note` слово в
  слово повторяет `title`, — показывать чистый повтор хуже, чем не
  показывать), а мера НОВИЗНЫ: `noteIsNovel()` считает долю слов `note`,
  которых нет ни в `title`/`extra`, ни в `eco.*`/`law.*` (кроме `adv`).
  Порог 0.9 подобран этим же замером на всех 46 карточках — между «явный
  повтор» (`agrostroy-zemlya` 1.00, `g94268c8d` 1.00 — оба факта дословно
  лежат в `eco.share`/`eco.context`, `g692dcc6b` 0.95 — `note` почти дословно
  повторяет `eco.share`) и следующим по возрастанию значением (0.82,
  `gmru-prodo-star-nafta-broiler` — там `note` начинается с НОВОГО факта
  «Условия сделки стороны не привели», дальше повторяет `eco.val`, и обрублен
  на полуслове тем же дефектом, что и ALMI Partner) есть зазор — порог внутри
  него. Родня уже записанного урока «скрытые состояния проверяются
  отдельно»: здесь скрытым оказалось не расширяемая панель, а целый блок,
  который сам решает, рисоваться ли, по количеству элементов массива.
- **Один и тот же обрыв на ~260 знаках — сигнал общего дефекта ингеста, а не
  разовая порча одной карточки.** Тем же замером (46 карточек с `note`)
  найдено: 27 из 79 непустых `events[].note` по всей базе (не только у
  карточек с одним событием) имеют длину РОВНО 260 знаков, ещё 4 — 259,
  итого 31 из 79 (39%) в диапазоне 255–260 — статистически невозможное
  совпадение для текста, обрезанного по смыслу; это жёсткий лимит длины
  где-то в разборе притока, срабатывающий и на середине слова. Почищен
  только `g21795ec9` (единственный из этого набора, попавший в ночную
  вычитку 40 карточек и проверенный по источнику); `gmru-prodo-star-nafta-broiler`
  найден тем же измерением и НЕ починен — обрыв виден («…«Башк»), но
  восстановление требует того же ручного чтения источника с дословной
  цитатой, что и ALMI Partner, и это за рамками сегодняшней партии. Остальные
  ~29 карточек этого диапазона не проверены вовсе. Это отдельная задача на
  будущий прогон: замерить (`len(note) in (255..260)` по всей базе), прочитать
  источник каждой карточки, восстановить обрубленное тем же приёмом, что
  `fix_g21795ec9_truncated_note.py` — искать полный абзац в кэше `data/inbox/raw`
  или через `fetch_article_texts.py`.
- **Нашли жёсткий лимит — почините его там, где он режет, а не только там,
  где заметили обрыв.** Предыдущий урок нашёл ПРИЗНАК (31 карточка с `note`
  в диапазоне 255–260 знаков) и починил ОДНУ карточку по нему, но не сам
  код, который резал: `draft.py`'s `guess_event()` делал `summary[:260]` —
  срез по индексу знака, слепой к границе слова. Починено на входе:
  `truncate_note()` режет до последнего целого слова и ставит «…», чтобы
  обрыв был виден честно, а не выглядел как короткий, но полный текст.
  Это не чинит уже существующие 30 обрубленных `note` (их слова физически
  потеряны, восстановление по-прежнему требует чтения источника — см. урок
  выше), только останавливает появление новых. Родня уже записанного
  правила «нашли жёсткий лимит — не гадать, а исправить»: находка признака
  дефекта — это повод дочитать код ДО функции, которая его производит, а не
  только до карточки, которую он испортил.
- **Прямой юридический покупатель и конечный бенефициар — разные роли, и
  склеивать их в одно поле `buyer` неверно, даже когда источник называет
  только физлицо.** У g81510c02 («Игорь Ким / МФО «Береке»») заголовок
  называл покупателем Эдуарда Ли — но источник (forbes.kz, дата статьи
  совпадает с датой карточки) описывает ДВЕ сделки: 13 марта 2025 Ли купил
  98,988% ТОО «Сейф-Ломбард» (это отдельный факт, уже был в `extra`), а
  28 марта — Ким вернул МФО «Береке» именно «Сейф-Ломбарду» («Новым и
  одновременно "старым" собственником МФО "Береке" ... стало ТОО
  "Сейф-Ломбард"»), а не лично Ли. Дата карточки совпадает со ВТОРОЙ сделкой
  — значит прямой покупатель по ней юрлицо, Ли лишь контролирует его с
  13 марта. Заведён профиль ТОО «Сейф-Ломбард», `buyer` карточки указывает
  на него, Ли остаётся в заголовке как понятный читателю контекст
  («подконтрольному Эдуарду Ли»), не как прямая сторона. Родня уже
  записанного урока «Стороной сделки может быть записан профиль совсем
  другой сущности» — но там была испорчена ссылка, здесь — верно найдено
  физлицо не той роли: конечный владелец вместо прямого юрлица-покупателя.
  Найдено ночной вычиткой 40 карточек (17-18 августа 2026) как подозрение
  («покупатель, возможно, должен быть юрлицом») — сама вычитка не смогла
  разрешить его без чтения источника целиком, что и было сделано отдельно.

  `"выделение"` даёт пару «Реорганизуемое общество»/«Выделяемое общество»,
  всё остальное (включая отсутствие поля) — старую пару. Термины проверены
  WebSearch по ФЗ «Об АО»: «присоединяемое общество» (ст. 17) и «выделяемое
  общество» (ст. 19) — формулировки самого закона. Слово «сливающееся
  общество», которое звучало правдоподобно и напрашивалось для слияния, в
  законе НЕ встречается — там «общество, участвующее в слиянии» (ст. 16);
  компактный термин не придуман и не введён, для слияния (пока в базе нет
  ни одной такой карточки) UI подстраховочно использует пару присоединения.
  Родня уже записанного урока про «продавц\w*» и падежи: даже когда термин
  кажется очевидным по аналогии, его нужно ПРОВЕРИТЬ по первоисточнику, а не
  досочинить симметрично уже известным словам.
- Адрес для правок — константа `CONTACT_EMAIL` в `static/index.html`, одна на
  футер и на кнопку «Уточнить или дополнить» в карточке.
- **Стороной сделки бывает записан её предмет — и это ловится правилом.**
  «Wildberries & Russ приобрела сеть «Рив Гош»» — продавцом стоял сам «Рив Гош»;
  «Инвестиции Softline Venture Partners в Kickidler» — предметом стоял инвестор.
  Правило «название предмета текстом не совпадает с названием стороны, а имя
  стороны текстом — с профилем предмета» нашло 4 карточки без ложных
  срабатываний и закреплено тестом `test_asset_is_not_a_party`. Сравнивать
  НАЗВАНИЯ, а не только ссылки: половина карточек хранит сторону текстом, а
  предмет профилем, и проверка по ссылкам их не видит.
- **Обратный случай («предметом стоит покупатель») правилом не ловится.** Две

  кандидатов, верен 1; «в тексте покупателем назван профиль из `target`» — 5
  кандидатов, верных 0. Мешают честные записи: buyback, MBO, «Продажа акций АО
  «Разрез «Степановский» на торгах». Класс находится чтением, все известные
  6 карточек исправлены в прогоне 45.
- Роли сторон выверены вручную только за 2026 год. Прогон 32 нашёл 3 карточки,

  выверка, а проверка «профиль уже занят другой ролью» при связывании продавца
  с профилем (прогон 41 добавил ещё 10 — всего 17). Обратный случай (предметом стоит ПОКУПАТЕЛЬ) известен у 4 карточек
  и механически пока не измерен: наивное правило даёт 11 кандидатов, и все 11 —
  верные записи о buyback и MBO.
- Продавец известен у 639 карточек из 1332 (48%), с профилем компании связаны

  продавца хоть какой-то признак есть у 65, и почти все они прочитаны и

## Три рутины и цикл обучения механики (записано 9 августа 2026)

ТРИ РУТИНЫ, ТРИ ГЛАГОЛА. Их намеренно три, а не десять, и делятся они не по
скриптам, а по тому, что происходит с данными:

| рутина | когда | глагол | что делает |
|---|---|---|---|
| приток | 06:50 МСК, раз в сутки | ПРИХОДИТ | fetch → triage → enrich → draft → promote → **сборка чтением** → консоль |
| публикация | 10:00–19:00 МСК, ежечасно | ВЫХОДИТ | решения из консоли → база → посты в канал (с вычиткой) |
| качество | ежечасно | УЛУЧШАЕТСЯ | сначала видимые поломки, потом очередь дочитывания (G7), потом бэклог G1–G6 |

Новое существенное встраивается ВНУТРЬ этих трёх, а не заводит четвёртую:
вычитка постов — шаг публикации, дочитывание старых карточек — шаг качества,
обучение механики — шаг качества. Отдельная рутина заводится только если у
работы своё расписание, которого нет ни у одной из трёх.

У очереди дочитывания (G7) с 18 августа три уровня: день после появления —
полный обыск (`deep_researched`), неделя и месяц — две узкие дельты друг за
другом поверх него, не повтор (`weekly_researched`/`followup_researched`,
`--mark-weekly`/`--mark-followup` в review.py; подробности и метод —
`pipeline/ingest/REVISION_BRIEF.md`). До 18 августа было два уровня (неделя,
месяц) — сдвинуто раньше по итогам разговора с владельцем: цель не «не
тратить токены раньше времени», а «карточка полна независимо от того, зайдёт
ли читатель на неё в первый день или через месяц» — и это требует, чтобы
первый обыск случился как можно раньше, а НЕ позже, компенсируя риск
«слишком рано, мало материала» не удешевлением первого прохода, а тем, что
после него есть ДВЕ точки подстраховки вместо одной. Раньше сам аргумент
за неделю («дать вторичным источникам время выйти, прежде чем тратить
7–10 запросов») был качественным, а не измеренным — конкретного замера,
через сколько дней после первой новости в среднем появляется аналитика и
подробности сделки, не делали ни разу; если возвращаться к вопросу
интервалов снова, начинать с этого замера, а не выбирать число на глаз
второй раз.

ДВА КАНАЛА НАРУЖУ, И ОНИ РАЗНЫЕ. `PushNotification` — телефон владельца,
только настоящий сбой (сеть, git, токен, исключение). `pipeline/ops_status.py`
— строка в Telegram-консоль в конце КАЖДОГО прогона, включая пустой: до
9 августа «прогон был, ничего не нашлось» и «прогона не было вовсе» выглядели
снаружи одинаково — молчанием, и суточный приток так простоял несколько дней
незамеченным.

ЦИКЛ ОБУЧЕНИЯ МЕХАНИКИ. Таблица `FIXES` в review.py — это не только журнал
правок, но и накопленный СПИСОК ОШИБОК МЕХАНИКИ: каждая запись говорит
«правило этого не увидело». `pipeline/ingest/learn.py` разбирает её на классы
и делит промахи на два вида: механика ПРОМОЛЧАЛА (128 из 156 — норма для
полей, требующих смысла) и механика СОВРАЛА (28 — это и есть материал для
новых правил, потому что неправда уезжает в базу и в канал как факт).
Класс с 3+ враньями — кандидат на правило. Правило пишется С ЗАМЕРОМ по всей
базе, и результат — принят ИЛИ ОТВЕРГНУТ — дописывается в `LEARNED`/`REJECTED`
того же файла. Отвергнутая гипотеза с цифрами ценнее ненаписанного правила:
без записи следующий прогон переоткрывает её за токены (9 августа так были
измерены и отвергнуты три подряд гипотезы про отрасль из аннотации).

ЧТО МЕХАНИЗИРУЕТСЯ, А ЧТО НЕТ — ЭТО ИЗМЕРЕНО, А НЕ МНЕНИЕ. Механикой хорошо
берутся форма и запрет: падеж предмета (`casing.py`, 19 срабатываний, 0
ложных), отказ брать число не из того предложения (`NOT_A_PRICE`, зарубает 3,
все три были неверны), отказ принимать родовое описание за имя стороны
(`is_generic_description`, ошибок покупателя 82 → 77). Не берётся смысл:
отрасль по аннотации меряли трижды — точность падала с 75% до 61–71% в каждом
варианте. Отсюда рабочее разделение: механика отвечает за «как записано» и за
«этого брать нельзя», чтение — за «что здесь на самом деле сказано». Убрать
чтение целиком нельзя не из осторожности, а по замеру.

## Приток (`pipeline/ingest`, `pipeline/publish`)

- **Забор ничего не решает.** `fetch.py` только складывает сырьё в
  `data/inbox/raw/<дата>.jsonl`; фильтр и сопоставление гоняются по сырью
  сколько угодно раз без сети. Недоступный источник помечается недоступным и
  попадает в отчёт — успех не подразумевается.
- **Полный текст статьи качается воротами, а не по памяти рутины.** Лента
  отдаёт ~130 знаков аннотации (медиана; 87% записей короче 300), статья —
  ~6400: пока текст не на диске, шаг чтения физически не может подтвердить
  цитатой ни оценку, ни согласования. Дозабор был отдельной командой
  (`fetch_article_texts.py`), которую надо было не забыть, — из 84 карточек
  притока полный текст оказался скачан у 13, и карточка NexTouch/«Квант» два
  дня стояла с пустыми линзами при 326 КБ текста в кэше (нашёл владелец, а не
  пайплайн). С 8 августа `promote.py --write` скачивает тексты всех прошедших
  ворота карточек сам, сразу; уже скачанный адрес второй раз не качается
  (`already_fetched`), сетевая ошибка ворот не валит. Механическое извлечение
  из ПОЛНОГО текста при этом не включено намеренно: «первое число статьи»
  почти наверняка из чужого абзаца (урок «Разбор источника доверяет числу из
  чужого абзаца» — ВТБ/Holiday Inn получил 100 млрд ₽ всей «Галс», эксперты
  оценивали гостиницу в 8–10 млрд) — полный текст читает модель, перенося
  факты через `review.py` с дословной цитатой на каждое поле.
- **«Не читали» и «читали, добавить нечего» обязаны выглядеть по-разному.**
  Оба случая — прочерки в eco/law, и пропуск шага чтения был незаметен, пока
  источник не открыл человек. Прочитанная карточка получает `reviewed:
  <дата>`: правки через `review.py --write` ставят отметку сами, бедный
  источник помечается `review.py --mark-read <id> --write`. Очередь «что ещё
  не прочитано» — это запрос по базе (`from_ingest` без `reviewed`), а не
  ручная проверка. Отметка идемпотентна — повторный прогон не выдаёт старое
  чтение за свежее. Держат тесты `test_reviewed_stamp_is_idempotent` и
  `test_every_fixed_card_carries_a_reviewed_mark`.
- **Непроверенное помечено непроверенным.** Адреса лент в `sources.json` —
  предположения, пока `fetch.py --verify` не проверил их там, где есть сеть.
  Тест `test_sources_registry_is_honest` не даёт поставить `feed_checked` без
  даты проверки. В этой среде исходящие к новостным сайтам закрыты политикой
  прокси (403 на CONNECT), и это не чинится retry.
- **Пороги притока подобраны замером, а не на глаз.** Фильтр меряется на 1333
  заголовках базы (полнота) и на ручном списке соседних тем (точность);
  сопоставление — тем, что каждый заголовок обязан найти сам себя и не найти
  чужую карточку. Меняя правило, перезапустите `--measure` и запишите цифры.
- **Ошибка дороже молчания.** Разбор новости в черновик намеренно молчалив:
  пустое поле правится за секунду, неверное — живёт в базе месяцами. Замер
  прогона 47 на 1333 выверенных карточках: продавец 290 попал / 9 ошибся,
  покупатель 517 / 57, отрасль 757 / 97. Пороги вранья закреплены тестом.
- **Замер сравнивает то, что сравнимо.** «Ошибками покупателя» сначала
  считались «Альфа-банк» против профиля «Alfa-Bank» и «Неофарм» против «ООО
  «Нео-Фарм»» — это одно имя, записанное по-разному. Прежде чем чинить правило,
  проверьте свою линейку.
- **Линейка стареет сама, даже если правило не менялось.** Тест
  `test_draft_error_rate_stays_low` год держал порог «ошибка продавца < 10%»
  на строгом substring-компараторе — и упал не потому, что `guess_parties()`
  стал хуже угадывать, а потому что кампания дочитывания (G9) наполнила базу
  настоящими значениями `seller` там, где раньше стоял прочерк: выборка
  выросла, и в ней стало больше пар вроде «Романа Абрамовича» против «Роман
  Абрамов, Александр Абрамов и партнёры» — оба верно называют продавца, один
  в косвенном падеже, другой в перечислении, а строгая подстрока их не
  видела. Починка — не ослабление порога, а замена компаратора на уже
  проверенную в review.py пословную проверку на падеж (`_same_word`);
  ошибка вернулась к исторической цифре (3,1% против задокументированных
  3%), а не просела ниже — доказательство, что линейку почистили, а не
  сломали в удобную сторону. Правило шире одного теста: любой замер,
  сравнивающий текст с текстом на РАСТУЩЕЙ базе, стоит перепроверять по
  мере роста выборки, а не только когда он покраснеет.
- **Приток не пишет в базу напрямую.** Сначала черновик, потом `promote.py` —
  дверь с замком: ПУСТИТЬ / НА РЕШЕНИЕ (не хватает отрасли — её проставляет
  человек) / ОТКАЗ (дубль, валюта словом, заглушка вместо имени, одна сторона в
  двух ролях). Иначе база наполнится быстро и неверно — а это ровно то, что мы
  20 прогонов исправляли.
- **Приток работает по расписанию.** Рутина «Компас: приток сделок» запускается
  раз в сутки отдельной сессией и проходит цепочку целиком. Частота была
  каждые 3 часа (прогон 60–62, сеть работала) — снижена обратно до суток
  1 августа по прямой просьбе владельца ради экономии токенов, не из-за сети.
- **У публикации в канал нет и не должно быть своего планировщика.**
  `send_telegram.py` — последний шаг цепочки притока, а не отдельная задача по
  расписанию: единственный момент, когда в базе появляется что-то новое для
  канала, — прогон притока, поэтому публикация наследует его расписание.
  Внешний cron на хостинге и планировщик внутри веб-процесса (приём соседнего
  проекта «Автопост») здесь оба лишние и вдобавок опасны: состояние «что уже
  опубликовано» (`telegram_posts`) лежит в git-файле, и процесс на Timeweb,
  записав его, потерял бы запись при следующем деплое — канал получил бы те же
  посты повторно. По той же причине прогон, изменивший ТОЛЬКО `telegram_posts`,
  обязан закоммитить это изменение.
- **`enrich.py` не умеет дописывать консультантов — и это не забывчивость, а
  неизмеренное правило.** Среди его правок есть источник, сумма, стороны,
  статус, заголовок и этап; `law.adv` там нет. Первая попытка написать такое
  правило замерена на 133 живых постах девяти каналов и дала 11 срабатываний,
  из которых ВЕРНЫХ НОЛЬ: в юридических каналах «советник» — это должность
  сотрудника («советник ККМП Алексей Чернышев»), а «консультант» — слово из
  рейтингов («топ-5 юридических консультантов»). Пойманы мастер-класс по
  арбитражу и пост про космонавтов. Ужесточённый признак (фирма + действие по
  сделке) дал 0 ложных, но и 0 верных — в выдаче каналов на тот момент не было
  ни одного объявления о сопровождении. Правило без подтверждённых верных
  срабатываний в базу не пускать.
- **Между «сопровождением» и «сделкой» бывает четыре слова.** Единственный
  реальный образец объявления (t.me/LawFirms/10680) звучит так: «сообщает о
  сопровождении командой корпоративной практики сделки по приобретению…».
  Шаблон `сопровождени\w*\s+сделк` его НЕ ловит — между словами вклинивается
  название практики. Родня урока про `[^,]` внутри числа: шаблон, написанный
  по воображаемой фразе, разбивается о первую же настоящую.
- **Кто консультировал — почти всегда не в тексте карточки.** Замер правила на
  своей же базе дал 2% полноты (5 из 237), и это не дефект правила: карточки
  собирались из деловых СМИ, которые консультантов не называют, а консультанты
  попадали в базу отдельными волнами из объявлений самих фирм. Мерить правило
  извлечения консультантов по тексту карточек бессмысленно — корпус должен
  быть из объявлений фирм.
- **Пять мест хранения одних и тех же данных — не «исторически сложилось», а
  готовый баг.** До 3 августа 2026 сделки лежали в `DEALS` (19), `MINI_DEALS`
  (21) и `CHANNEL_DEALS` (14) внутри `index.html`, в `bulk_deals.json` (107) и
  в `deals_promoted.json` (1350); плюс три файла-копии, которые не читал никто
  (`curated_deals.json`, `curated_companies.json`, `deals_2026.json` на 380 КБ).
  Приток строил индекс по одному файлу и был слеп к 54 карточкам — и это не
  теория: разбор архива @LawFirms объявил «новыми» 7 сделок из 10, которые на
  сайте уже были. Свели всё в `deals_promoted.json`
  (`pipeline/merge_into_one_base.py`): 142 компактные записи стали карточками
  (решение владельца — кратких записей больше нет, есть карточка и блок «мало
  данных»), 19 кураторских и 36 профилей переехали из разметки, лишние файлы
  удалены. Число видимых сделок не изменилось (1320 до и после) — изменилось
  число мест, где их надо искать. ПОБОЧНЫЙ ЭФФЕКТ, который стоит помнить:
  кураторские карточки НИКОГДА не проверялись инвариантами `test_data.py`
  (он читает JSON), и после переезда упало семь тестов — отрасль вне списка,
  профили-близнецы, предмет, он же сторона, согласования без органа. Данные,
  вынесенные из-под проверок, тихо накапливают долг.
- **У базы ТРИ источника данных, и проверка на дубль обязана смотреть во все.**
  19 карточек живут не в `deals_promoted.json`, а прямо в `static/index.html`
  (кураторский массив: citibank, «Балтика», Hugo Boss/«Стокманн»,
  Яндекс/«Заряд!», «Мерседес», TechnoRed…), и `match.py` строил индекс только
  по первому файлу — приток был СТРУКТУРНО слеп к этим сделкам и завёл бы
  дубль на любую новость о них. Разбор архива @LawFirms из-за этого объявил
  «новыми» 7 сделок из 10, которые на сайте уже были. Нашлось не проверкой
  кода и не тестом, а тем, что владелец вбил две сделки, которые точно помнит,
  и обе нашлись на сайте. Чинится `pipeline/ingest/curated.py` +
  `curated.index_all()` вместо прямого `matcher.index_base()`; держат тесты
  `test_curated_deals_are_parsed_from_the_interface_file` и
  `test_match_index_covers_both_halves_of_the_base`. Урок шире дублей: прежде
  чем утверждать «этого у нас нет», выпишите, из скольких мест состоит «у
  нас», — счёт по одному файлу выглядит полным и врёт.
- **Совпадение по названию в кавычках ломается о падеж и о короткий
  заголовок.** Даже с полным индексом объявление «Orion Partners
  консультировала АО «Стокманн» в сделке по покупке… Hugo Boss» не находит
  карточку «Hugo Boss продал российский бизнес «Стокманну»»: в кавычках у
  поста «Стокманн», у карточки «Стокманну» — сравнение строгое. А
  Яндекс/«Заряд!» не находится по другой причине: общее название в кавычках
  есть, но правилу нужны ещё два общих слова, а в коротком кураторском
  заголовке значащая основа всего одна. Оба случая — не «правило плохое», а
  граница применимости: пока она не расширена, объявления сверяются с базой
  человеком, а не молча заводятся как новые.
- **Фильтр, измеренный на ручном списке, не значит фильтр, проверенный на
  живых данных.** «95,3% полноты, 0% ложных» у `classify.py` — это замер на
  18 РУЧНЫХ соседних темах. Первый прогон на реальной сети (166 признанных
  сделками из 1992 записей) показал: из 11 карточек, которые прошли бы
  автоматически, сделкой была одна. Пока фильтр не переизмерен на реальном
  потоке, `promote.py` не пишет новые карточки без человека
  (`NEW_CARDS_NEED_REVIEW`, E9). Меняя скрипты
  притока, помните: их запускает не человек, и отчёт должен быть коротким.
- **Одна сделка — один живой телеграм-пост, плюс отдельные посты-вехи по
  закрытому списку (раздел A, 22 августа).** Новые факты правят тот же живой
  пост строкой «⟳ Обновлено: …», без нотификации (`editMessageText` в
  Telegram по своей природе не уведомляет подписчиков канала — это отдельно
  от `should_notify()`, который решает про ЛИЧНЫЕ уведомления подписчикам,
  сохранившим фильтр, и с публикацией в канал сегодня не связан вовсе).
  Согласование/закрытие/срыв сделки (`review.POSTWORTHY_MILESTONE_KINDS`) —
  ОТДЕЛЬНОЕ сообщение («веха»), не правка живого поста: `review.py
  --milestone <id> <kind> "<заголовок>" --write` ставит `newsworthy`/
  `headline`/`snapshot`, `pipeline/ingest/send_milestone_drafts.py` шлёт
  черновик в консоль с теми же кнопками «пост в канал»/«без поста», что и у
  обычного поста (`deal_id` в `callback_data` несёт вид этапа через `~`:
  `mod:<id сделки>~<kind>:post_ok`), молчание сутки публикует как есть —
  `send_telegram.py` берёт это на себя тем же прогоном, что и живые посты.
  Дедуп — по стабильному `event['id']` в отдельном словаре верхнего уровня
  `telegram_milestones` (не в `telegram_posts[id]` — та форма поля уже
  закреплена тестами как «голое число или null», расширять её вехой
  рискованно и не нужно). Текст поста-вехи берёт поля из СНИМКА события
  (`event['snapshot']`), а не из текущих полей сделки — честность момента,
  та же, что у панели «Карточка на момент этого этапа» на странице этапа.
- **Сила совпадения решает, можно ли писать в базу.** У `match.py` четыре
  сигнала, и они измеримо разные: «общие слова заголовка» — 33 совпадения из
  541 ведут на ЧУЖУЮ карточку (6,1%), «название в кавычках» — 4 из 568 (0,7%),
  «название и сумма» — 0 из 86. Обогащение (`enrich.py`) пишет только по
  сильным: дописать факт в чужую сделку хуже, чем не дописать вовсе.
- **Обогащение дополняет пустое, а не исправляет заполненное.** Прогон правил
  по своим же заголовкам: 933 подтверждения против 114 расхождений — правило
  заменило бы догадкой каждое девятое выверенное значение. Расхождение
  («новость называет другую сумму») — повод показать человеку, а не править.
  Единственное обновляемое поле — статус, и только вперёд: «Обсуждается» →
  «Закрыта» (правило ни разу не назвало закрытой незакрытую сделку — 0 из 256,
  а все расхождения статуса обратного вида).
- **Атрибуты HTML-тега пишут в любом порядке.** Правило автообнаружения RSS-
  ленты искало `<link ... rel="alternate" ... type="application/rss+xml" ...>`
  регуляркой, которая требовала `rel` СТРОГО раньше `type` в тексте тега —
  а часть сайтов пишет `type` первым. Правило молча не находило половину
  реальных тегов. Поймано не чтением, а тестом: `assert` на обоих порядках
  атрибутов сразу («rel до type» и «type до rel») — тест писался ДО того, как
  стало известно, что баг есть, и упал на честной проверке. Чинится не
  усложнением одной регулярки, а раздельной проверкой каждого атрибута внутри
  найденного тега — родня урока «правило для начала строки не видит дефект в
  конце»: любой жёстко заданный порядок в чужой разметке рано или поздно
  встретит зеркальный вариант.
- **Дешёвое расширение источника — обобщённый механизм, а не сайт за сайтом.**
  119 сайтов в реестре стояли `enabled:false` без адреса RSS-ленты — писать
  парсер под каждый (как сделан `parse_mergers_ru_news` под mergers.ru) значило
  бы 119 отдельных разборов HTML под чужую вёрстку. Одна процедура
  автообнаружения `<link rel="alternate" type=".../(rss|atom)+xml">` в `<head>`
  главной страницы нашла и подтвердила рабочую ленту у 8 сайтов (включая
  первый работающий сайт консультанта, `firm:o2`) без единой строки разбора
  под конкретный сайт. Из 119 сработало 8 (6,7%) — это ожидаемо низкий процент
  для метода, который ничего не знает о конкретной вёрстке; расширять дальше
  тем же способом уже нельзя, для оставшихся 111 нужен либо ручной разбор
  (дорого), либо они действительно не отдают ленту.
- **Пустой флекс-элемент всё равно создаёт зазор.** `.deal-meta` на телефоне —
  `flex` с `gap:14px` (сумма + отраслевая метка). Когда суммы у сделки нет
  вовсе (`d.sum === null`, а не текст-заглушка «Не раскрыта»), пустой
  `<div class="deal-sum"></div>` рендерился без содержимого, но `gap` перед
  ним всё равно применялся — метка отрасли съезжала на 14px вправо от
  вертикали заголовка. У карточек с текстом «Не раскрыта» дефекта не было
  (перед меткой есть видимый текст, зазор выглядит уместным), поэтому баг не
  находили: он проявляется только на `null`, а не на строке-заглушке. Чинится
  не CSS-трюком (`:empty{display:none}` пришлось бы вешать на конкретный
  класс и держать в голове), а тем, что пустой блок вообще не рисуется —
  сумма показывается, только если есть что показать.
- **Переход по хешу — не перезагрузка страницы для теста.** Playwright-тест
  вызывал `visit()` (`page.goto(url + "#/...")`) в начале, ожидая чистое
  состояние — но `page` в `test_ui.py` один на весь файл (`scope="session"`),
  а смена хеша на уже загруженной SPA не перезапускает JS: `location.hash =`
  вызывает `hashchange` и повторный рендер, но не переисполняет скрипт и не
  обнуляет глобальные переменные (`feedYear`, `filterInd`, `filterTheme` и
  т. п.). Тест падал ТОЛЬКО в полном прогоне (после теста, оставившего фильтр
  применённым), а поодиночке проходил — тот же класс дефекта, что и
  «прогон одного теста — не проверка изоляции» с модальным окном, только
  источник состояния не DOM, а JS-переменные. Если тест зависит от «чистого»
  состояния фильтров, сбрасывать их явно, а не полагаться на `visit()`.
- **Флаг «загружено» не должен становиться true после неудачи.**
  `loadBulkDeals()` ставил `bulkLoaded = true` СРАЗУ после обеих попыток
  `fetch`, независимо от того, ответили они или нет (`try/catch` глотал
  ошибку в `console.warn` и шёл дальше). На нестабильной мобильной сети
  `deals_promoted.json` (774 КБ) иногда не догружался — и сайт тихо объявлял
  себя полностью готовым с 36 захардкоженными компаниями вместо ~1800: не на
  секунду, как в обычном «догружаем базу…», а НАВСЕГДА, пока пользователь
  сам не обновит страницу и не поймает лучший момент для сети. Воспроизвёл
  один в один (`route.abort()` на `deals_promoted.json` в Playwright дал
  ровно «161 сделка · 36 компаний» — число в число со скриншотом с телефона).
  «Готово» может означать только «данные реально получены», а не «мы
  перестали пытаться их получить» — и второе без честного статуса ошибки на
  экране неотличимо от первого.
- **Порог «слово длиннее N знаков» выбрасывает ровно самые отличительные
  слова.** У `match.stems` он стоял на пяти знаках — и «Hugo Boss», «VK»,
  «МТС», «X5» для сопоставления не существовали: заголовок «Стокманн купил
  российский бизнес Hugo Boss» давал ОДНО слово «россий», ««VK» выкупила
  «Учи.ру»» — ни одного. Правило выглядело безобидной чисткой предлогов, а на
  деле слепило базу к коротким брендам и аббревиатурам; объявления юрфирм по
  таким сделкам не находили свою карточку никогда. Полнота 87,9% → 96,0%
  после того, как латиница и заглавные аббревиатуры получили порог в два
  знака, а родовые слова (`group`, `capital`, `partners`, `holding`) и
  правовые формы ушли в стоп-лист. Порог по ДЛИНЕ — плохая замена порогу по
  СМЫСЛУ: прежде чем отсекать короткое, проверьте, что среди него нет имён.
- **Пресс-релиз — это два текста, склеенных вместе.** Сначала сделка, потом
  реклама фирмы, и реклама называет ДРУГИХ клиентов и ДРУГИЕ сделки. У
  объявления White Square про Nordgold в подвале стоят «Восток Инвестиции»,
  «Каллисто» и Tasty Coffee — сопоставление по всему тексту не выводило
  карточку Nordgold даже в пятёрку ближайших, по голове в 300 знаков она
  занимает первое место. Замер на 91 объявлении: голова — 20 значащих слов и
  1,3 названия в кавычках, весь текст — 79 слов и 2,0 названия, то есть
  половина «сигнала» приходит из рекламного подвала. Сопоставлять по всему
  посту — значит сопоставлять по списку клиентов фирмы. Разделители (`***`,
  «О фирме») для отсечения не годятся: замер дал их у 4% постов, а строку
  реакций — у 58%.
- **Проверка «чем дополнить» не должна быть уже, чем карточка.** Разбор
  @LawFirms сверял пост с шестью полями из тринадцати — и печатал «дополнять
  нечем» карточке `gmru-nordgold-chukotka`, у которой пусты ВСЕ поля, кроме
  заголовка и ссылки. Замечание владельца («не факт же, что в дубле есть вся
  информация, которая есть в посте») верно ровно потому, что проверка была
  уже объекта проверки. Правил извлечения у нас мало, а глаз есть на каждый
  разбираемый пост: показывайте полный перечень пустых полей, даже когда
  правило не смогло ничего вытащить.
- **Найденная карточка — это повод дополнить, а не повод пропустить.** В
  первых 15 объявлениях канала совпадений было восемь, и три из них дали
  консультанта, которого в базе не было (White Square у Nordgold, NEXTONS у
  «Ленты»/«РБФ ритейл», Nextons у Ситибанка). Если разбор притока
  останавливается на «это дубль», то каждая такая находка теряется молча.
- **Список формулировок, собранный по одной партии, — это список ТЕХ
  формулировок, а не всех.** `advisors.lead_advisor` знал «сопровождала»,
  «консультировала», «представляла интересы» — по десятку прочитанных
  постов. В архиве того же канала лежали «обеспечила юридическое
  сопровождение», «осуществила комплексное сопровождение», «сообщает о
  консультировании», «сопроводила приобретение» (совершенный вид) и
  «выступает консультантом» (настоящее время) — тот же смысл, другое слово,
  и правило молчало. Два расширения подряд: 115 → 128 → 134 срабатывания,
  ложных ноль, потерянных ноль. Проверять надо ВСЕ формы глагола (родня
  урока про `продавц\w*`, не совпадающий со словом «Продавец») и все
  синонимы действия, а не те, что попались в выборке. Признак насыщения —
  не «правило выглядит полным», а прогон по всему архиву: после второго
  расширения из 104 оставшихся постов со словом «сопровожд» в начале ни
  один не оказался российским объявлением о сделке.
- **Родовых слов перед именем бывает два подряд.** `re.sub` с якорем `^`
  снимает одно: «Команда практики рынков капитала White Square» → «практики
  рынков капитала White Square», и такой «консультант» попадает на экран.
  Снимать в цикле, пока строка меняется. Родственная ловушка там же:
  жадный `(?:\w+\s+){0,3}` в правиле «пропустить слова до заглавной буквы»
  съедал «рынков капитала Better» целиком (за ним тоже заглавная) и оставлял
  имя «Chance» — квантификатор обязан быть ленивым.
- **Факт бывает записан не в своё поле.** У карточки «Яндекс»/SolidSoft в
  «Консультантах» стояла ОДНА строка с именем Melling, Voitishkin & Partners,
  а «Delcredere — за SolidSoft» лежало текстом в пояснении к ней. На экране
  показывалась одна фирма из двух, хотя в данных были обе. Прежде чем искать
  недостающий факт в источниках, проверьте, не лежит ли он уже в карточке —
  просто в чужом поле.
- **Дата-заглушка хуже пустой даты.** У карточки «ЛУКОЙЛ продаёт зарубежные
  активы компании Carlyle» стояло 1 января 2022 года — след компактного
  импорта, тогда как сама карточка говорит про OFAC и Carlyle, а соседние
  карточки того же сюжета датированы 2025 годом. Дата — не украшение: по ней
  считается год в ленте и в аналитике, и сделка 2026 года три года лежала в
  2022-м. Заглушки вида «первое января» проверять отдельно: их оказалось 368
  из 1538 (24% базы) плюс семь со строкой «unknown».
- **Дата публикации статьи — не дата сделки, и это решает, что можно
  править.** Мета-поле `article:published_time` достаётся у 55% ссылок и
  сразу даёт соблазн подставить его в карточку. Но подборка «Коммерсантъ —
  «Сделки года»» выходит 30 сентября и описывает сделки всего года. Рабочее
  правило: применять дату статьи, только если её ГОД совпадает с годом
  карточки — тогда восстанавливаются месяц и день внутри уже известного
  года и ничего нового не утверждается (125 карточек). Расхождение по году
  правится лишь там, где год статьи назван в тексте САМОЙ карточки, а год
  карточки — нет (5 из 86). Замер по остальным 81: год статьи подтверждён
  текстом у 5, год карточки — у 7, у 74 в тексте вообще нет ни одного года —
  подставлять там нечего, и они остаются как есть.
- **Отсутствующее поле печатается словом «undefined».** У 136 карточек нет
  `status`, а лента и шапка вставляли его в разметку напрямую: на экране

  слова «undefined» в тексте экрана — теперь это тест
  `test_no_undefined_on_screen_for_cards_without_status`.
- **Факт лежит в поле «Дополнительная информация», а не в своём.** У 112

  Прежде чем искать факт в источниках, посмотрите, не написан ли он уже на
  карточке под общей подписью.
- **Проверка «экран не пуст» не видит падения рендера.** У 136 карточек нет
  объекта `eco`, а «Обзор» читал `d.eco.share` без проверки всегда, когда

  равно отрисовывалась, и обе проверки — «экран не пуст» и «ошибок в консоли
  нет» — молчали. Поймал только слушатель `pageerror`. Родня урока E9: пока

  `test_cards_without_eco_or_law_render_without_pageerror`, проверенный на

- **Функция, которую никто не вызывает, выглядит на экране работающей.**
  Подписка на сделки («сообщи об отрасли X от суммы Y») сохранялась, отдавалась
  в кабинет и удалялась — а сверять её с новыми сделками было НЕЧЕМУ: во всём
  коде не нашлось ни одного места, читающего `saved_filters` иначе, чем ради
  показа списка самому владельцу. Интерфейс при этом обещал «Новые совпадения
  появятся в уведомлениях». Ни один тест не падал, потому что всё написанное
  работало; отсутствовало ненаписанное. Ищется это не чтением кода, а обратным
  ходом: выпишите каждую фразу интерфейса, обещающую БУДУЩЕЕ событие, и для
  каждой найдите функцию, которая его производит. Родня урока про тормоз E9:
  там путь за дверью был не проверен, здесь пути нет вовсе.
- **Цепочка из пяти шагов, у которой написаны четыре.** Привязка личного
  Telegram: кабинет просит ссылку → человек уходит в бота → жмёт «Запустить» →
  Telegram шлёт `/start kompas_<токен>` → обработчик связывает chat_id с
  аккаунтом. Написаны были ссылка, токен, обработчик и разбор сообщения —
  всё, кроме `setWebhook`: Telegram никогда не узнавал, КУДА слать. Снаружи
  это выглядит как «нажал и ничего не произошло», без ошибки на экране и в
  логах. Проверять цепочку с внешним участником надо целиком, начиная с
  вопроса «а он-то знает, что мы его ждём?».
- **Значок валюты не с той стороны делает сумму невидимой для правил.**
  У одной карточки стояло «₽25 млрд» вместо «25 млрд ₽» — англоязычная запись
  из источника. Глазами это мелочь, но любое правило, читающее сумму (порог
  подписки, сортировка по величине), ищет число ПЕРЕД значком и такую запись
  молча пропускает: сделка выпадает из выдачи, не вызвав ошибки. Нашлось
  замером «сколько сумм мы не умеем разобрать» — 9 из 1416, из них 2 честно
  неразбираемы («несколько млрд ₽»), 6 чинились правилом, 1 оказалась этим
  дефектом. Держит тест `test_ruble_sign_stands_after_the_number`.
- **Ноль в отчёте фонового прогона неотличим от «смотрели не в ту базу».**
  Приток запускается в одноразовом контейнере, где `DATABASE_URL` не задан, и
  `SessionLocal` честно открывает пустой локальный `kompas.db` — не падая.
  «Уведомлений создано: 0» в таком прогоне не значит «подписчиков нет», а
  значит «мы смотрели не туда», и различить это в отчёте нечем. Поэтому шаги
  рассылки печатают, В КАКУЮ базу они писали, и прямо предупреждают о подмене.
  Та же болезнь, что `bulkLoaded = true` после неудачной загрузки: «готово»
  подменяет «мы перестали пытаться».

- **Адрес базы решает, ГДЕ может стоять код, который в неё пишет.** Строка
  подключения к боевой базе — `postgresql://…@192.168.0.11:5432/…`, то есть
  приватный адрес: он маршрутизируется только внутри сети хостинга. Сайт до
  базы достаёт, потому что он там же; приток, работающий в одноразовом
  контейнере в другом облаке, не достанет НИКОГДА — это не «не настроили
  переменную», а отсутствие маршрута. Полдня можно потратить, обсуждая, дать
  ли рутине `DATABASE_URL`, и не заметить, что вопрос снят самим адресом.
  Прежде чем проектировать шаг «пайплайн пишет в базу пользователей»,
  посмотрите на адрес базы: всё, что её читает или пишет, обязано жить на
  сайте.
- **Расписание не нужно там, где уже есть естественное событие.** Новые
  карточки попадают на сайт ровно одним способом — деплоем нового
  `deals_promoted.json`. Значит, единственный момент, когда есть что сверять с
  подписками, — старт процесса после деплоя, и проверка висит там
  (`subscription_feed.scan_on_startup`). Планировщик внутри процесса (приём
  соседнего проекта «Автопост») здесь просыпался бы 24 раза в сутки, чтобы 23
  раза ничего не найти. Сначала ищите событие, которым уже сопровождается
  появление данных, и только не найдя — заводите таймер.
- **Первый прогон любой сверки «что нового» обязан молчать.** Пока таблица
  `deals_seen` пуста, формально новыми являются все 1538 карточек, и честный
  ответ «всё новое» означал бы залп уведомлений по всей истории рынка. Первый
  прогон только ЗАПОМИНАЕТ состав, уведомления начинаются со следующего, —
  тот же приём, что `seed_telegram_posts_backlog.py` у канала, и его стоит
  закладывать сразу: он нужен всякий раз, когда «новое» определяется через
  отсутствие в накопленном состоянии.

- **Обратная кавычка в комментарии убивает страницу целиком.** Внутри
  JS-шаблонной строки лежал HTML-комментарий, а в нём — имя параметра в
  обратных кавычках (как принято в markdown). Для браузера это конец
  шаблона: `Unexpected identifier`, скрипт не исполняется, сайт белый. Ни
  один экран при этом не «сломан частично» — не работает вообще ничего, и по
  симптому не догадаешься, что дело в комментарии. Родня урока про
  экранирование Python против JS: комментарий внутри чужого синтаксиса — не
  комментарий, а текст, и правила цитирования там чужие. Проверяется одним
  запуском страницы, но только если слушать `pageerror`.
- **Проверка `массив.includes(x)` после `map` всегда ложна.** В аналитике
  стояло `all.forEach(d=>{const inds = DEALS.includes(d) ? dealIndustries(d)
  : [d.ind]; …})`, а `all` собирался как `DEALS.map(d=>({…}))` — то есть из
  КОПИЙ. Сравнение по ссылке не совпадало ни разу, и сделка с двумя отраслями
  всегда считалась только по первой: ветка с `dealIndustries` не исполнялась
  никогда. Дефект молчит — цифры выглядят правдоподобно, тестов нет, экран не
  падает. Признак: `includes`/`indexOf`/`===` по объекту рядом с `map`,
  `filter(...).map(...)`, spread или `JSON.parse(JSON.stringify(...))`. Чинится
  не проверкой, а тем, что нужное поле кладётся в саму запись при сборке.
- **Убрали колонку — поправьте сетку.** `.advisor-card` — `grid` из трёх
  колонок; средняя («Категории практики») снята с экрана, а
  `grid-template-columns` остался трёхколоночным: пустая колонка продолжала
  занимать свою долю ширины, имя жалось влево, счётчик — вправо, между ними
  полкарточки воздуха. Пустой грид-элемент, как и пустой флекс-элемент с
  `gap`, места не освобождает. Удаление блока из раскладки — всегда две
  правки, разметка и сетка.

- **Ствол словаря без границы слова ловится внутри чужого слова.** В словаре
  отраслей `рудник` совпадал внутри слова «со**рудник**и», `сельхоз` — внутри
  «Рос**сельхоз**надзор», `телеком` — внутри «Рос**телеком**», `энергетическ` —
  внутри «ветро**энергетическ**ий», `edtech` — внутри «M**edTech**». На живом
  потоке 4 августа (2167 записей) таких срабатываний 65, и почти все — любая
  новость со словом «сотрудники» получала отрасль горнодобычи. На нашей
  вычищенной базе замер почти не двигается (968/178 -> 965/175): дефект виден
  ТОЛЬКО на сыром потоке, ради которого правило и живёт — мерить словарь по
  своим же причёсанным заголовкам значит не увидеть его вовсе. Цена границы —
  составные слова, где ствол стоит вторым («железобетонных», «газобетона»,
  «судоверфь»): их выписывают в словарь явными формами. Родня уже записанного
  урока про `\b` после приставки, только зеркальная: там граница мешала, здесь
  её отсутствие.
- **В упорядоченном словаре одно слово не может принадлежать двум отраслям —
  выигрывает первая по списку, а не более точная.** 6 августа стем «телевизор»
  добавили в «Машиностроение» (завод «Квант» — «приборостроение, не ИТ»).
  8 августа тот же стем понадобился в «Потребительские товары» (тот же завод —
  готовый бытовой прибор, тот же класс, что заводы Bosch/Kuppersberg) — и его
  просто дописали туда, не заметив, что слово уже стоит выше по списку в
  другой отрасли. `industry_by_words` идёт по списку и отдаёт ПЕРВОЕ
  совпадение: новая запись работала бы только для текстов, не долетающих до
  старой, то есть не работала бы вовсе, и молча. Нашлось не проверкой кода, а
  тем, что `review.py` для карточки `g0431fc51` использовал ИМЕННО ТУ фразу
  («производителя телевизоров»), на которой держалась старая, неверная
  классификация, — иначе конфликт остался бы незамеченным. Правило: добавляя
  стем в словарь, `grep` по всему файлу словаря на это же слово — если оно уже
  где-то есть, решить, в какой ОДНОЙ отрасли ему быть, а не дописывать вторую
  запись поверх первой.
- **Пустые линзы «Юрист»/«Экономист» при живом кэше источника — повод
  перечитать статью, а не констатировать «мало данных».** У карточки
  NexTouch/«Квант» (собрана притоком 6 августа) обе линзы стояли пустыми, а в
  `data/inbox/raw/2026-08-06-articles.jsonl` под тем же адресом лежал полный
  текст статьи TAdviser (326 КБ) с оценкой стоимости эксперта (1–1,5 млрд ₽),
  историей продажи (первая оценка завода — 3 млрд ₽ без долгов), планом
  перезапуска площадок и разбором, почему сделка возможна в процедуре
  банкротства — ни один факт не был использован. Приток ЗАБРАЛ текст (шаг
  fetch отработал), но шаг «проверка чтением» (`review.py`, докстрока в самом
  файле) до карточки не дошёл или не был выполнен по-настоящему. Нашёл это не
  скрипт, а владелец, вручную открывший источник и сравнивший с тем, что на
  экране, — соответствующая память заведена как приоритет G7 в
  PRODUCT_ROADMAP.md: перечитывать недавние карточки с пустыми линзами против
  их собственного кэша выше по важности, чем любая косметика.
- **`\b` после приставки, случай четвёртый: «покупает».** `\bкуп(ил|ит|ует)`
  не совпадает со словом «покупает» — перед «куп» стоит приставка, границы там
  нет. Четыре прогона разбор сторон не видел 40 заголовков базы с известным
  покупателем («Selectel покупает облачного провайдера servers.ru», «VK
  покупает сеть школ Ufirst»). Тот же класс, что `^не\s+раскры\b`, `продавц\w*`
  и `\w` в JS: правило молчит, замер выглядит законченным. Проверять шаблон на
  формах С ПРИСТАВКОЙ, а не только на голом корне.
- **Действие в заголовке бывает существительным.** «Группа „Ригла-Здравсити"
  закрыла сделку ПО ПОКУПКЕ сети „Здоровый город"» — глагол здесь служебный
  («закрыла»), а само действие названо существительным, и правило по глаголам
  покупки молчит. Ровно из-за этого сделка, о которой спросил владелец, неделю
  пролежала в очереди. Служебные глаголы брать ТОЛЬКО завершающие: «изучает
  возможность покупки» и «рассматривает покупку» — это слух, и разница между
  ними и «закрыла сделку по покупке» ровно в служебном слове.
- **Ворота для нового не должны требовать больше, чем есть у старого.** Приток
  не пускал карточку без покупателя и без отрасли — а в базе 431 карточка из
  1541 (28%) покупателя не называет вовсе («UniCredit продаст часть российских
  активов банка инвестору из ОАЭ»), и «Не определена» есть в списке
  `INDUSTRIES` с самого начала. Прежнее правило пропустило бы только 68% нашей
  собственной базы: мы требовали от новых сделок того, чего сами не делали.
  Проверка дешёвая и её стоит делать всякий раз, когда пишется фильтр на вход:
  прогоните его по УЖЕ ЛЕЖАЩИМ данным и посмотрите, сколько своих же записей
  он отвергает.
- **Законное значение, которым не помечено ничего, — непроверенный код.**
  «Не определена» лежала в `INDUSTRIES` и в интерфейсе, но за 1541 карточку ею
  не была помечена ни одна. Как только ею пометили первые четыре, вылезло
  сразу два места: плашка в шапке сделки читалась как второй статус («ЗАКРЫТА ·
  НЕ ОПРЕДЕЛЕНА» — что именно не определено?), а ссылка «Все сделки отрасли
  „Не определена"» вела в бессмысленный список. Родня урока про тормоз E9:
  путь, по которому ещё ни разу не ходили, не проверен, даже если он объявлен.
- **Очередь без причины — это свалка.** Карточки «на решение» складывались в
  `data/inbox/hold/` одними черновиками: ПОЧЕМУ каждая там оказалась, писалось
  в вывод прогона, а прогон идёт в одноразовом контейнере, и вывод человек не
  увидит никогда. Открыв очередь, он видел 41 карточку без единого слова о том,
  чего им не хватает, и должен был выводить это заново сам. Всё, что адресовано
  человеку, обязано нести причину В ТОМ ЖЕ файле.
- **Общие слова — не признак дубля, редкие — признак.** Проверка «два общих
  слова заголовка за месяц» слепила «Совладелец „Депо Три Вокзала" продал долю
  в разработчике» с «Владельцы ATI.SU купили разработчика»: общими были «владел»
  и «разраб», которые стоят в 25 и 34 заголовках базы и не значат ничего.
  Условие «хотя бы одно из общих слов редкое» (встречается не более чем в пяти
  заголовках) убирает такие пары и оставляет настоящие («персей», «biocatch»).
  Считать надо частоту слова по своей базе, а не длину пересечения.
- **Жалоба сервиса без даты — не диагноз.** `getWebhookInfo` возвращает
  `last_error_message` и после того, как всё починилось: «Connection timed
  out» одинаково выглядит и свежей, и прошлогодней, и человек идёт чинить
  несуществующую поломку. Диагноз даёт пара «дата ошибки + сколько обновлений
  ждёт доставки»: свежая ошибка при растущей очереди — доставка действительно
  не идёт; старая при пустой очереди — след прошлого. Печатать надо обе
  величины и сам вердикт, а не сырое поле.
- **Переменные окружения нужны в КАЖДОМ месте, где выполняется код, а не
  там, где их проще всего найти.** `TELEGRAM_REVIEW_GROUP_ID` и
  `TELEGRAM_REVIEW_CHAT_IDS` были прописаны только на Timeweb — там их читает
  `main.py` (вебхук). Но сами сообщения в группу шлёт `send_drafts.py`,
  который выполняется в ДРУГОМ месте: в среде рутин притока/публикации
  (Claude Code Remote, окружение «Default»), а не на боевом хосте. Без этих
  же переменных ТАМ `send_targets()` возвращает пустой список,
  `send_drafts.py` печатает «отправлять некому» и тихо завершается кодом 0 —
  ни ошибки, ни исключения, только строка в логе прогона, которую никто не
  читает каждый день. Родня уже записанного урока про адрес базы («решает,
  ГДЕ может стоять код, который в неё пишет»): токен и адрес получателя —
  тоже данные о ТОМ, ГДЕ бот отправляет, и их нужно продублировать в каждое
  окружение, которое реально выполняет отправку, а не в одно самое заметное.
- **Команда в группе приходит с суффиксом.** Telegram шлёт `/queue@бот`, а не
  `/queue`: правило, написанное под личный чат, в группе молча не срабатывает
  — команда отправлена, бот молчит, причина невидима. Родня урока про право
  решать: личный чат и группа отличаются не только адресатом, и обе ветки
  надо проверять отдельно.
- **Право решать проверяется по отправителю, не по чату.** Первая версия
  авторизации ответов на черновик сверяла `message.chat.id` со списком
  разрешённых личных id. В личном чате с ботом эти числа совпадают, дефект не
  виден. В общей группе (владелец и партнёр обсуждают черновики вместе)
  `chat.id` — это id самой группы, один для всех участников, а `from.id` —
  личный id того, кто написал; проверка по `chat.id` либо пускала бы КОГО
  УГОДНО из группы (если бы id группы случайно совпал), либо НИКОГО (обычно).
  Правило: право действия проверяется по тому, КТО отправил апдейт
  (`from.id`), а не по тому, КУДА он попал (`chat.id`) — это верно для любого
  Telegram-бота, который должен различать участников общего чата.
- **Подписка на событие не значит подписка на ВСЕ нужные события.**
  Регистрация вебхука просила у Telegram только `message` — этого хватало,
  пока боту нужен был один `/start`. Когда модерация добавила кнопки под
  черновиком, обработчик кнопок был написан и работал бы, но сам Telegram их
  не присылает: тип `callback_query` не значился в списке, а `setWebhook`
  всё равно отвечал «ok». Дефект молчит ровно там же, где молчал бы E9: до
  первого реального клика никто не заметил бы разницу между «работает» и
  «зарегистрировано, но не может сработать». Добавляя новый вид входящего
  события (кнопка, ответ, любой другой апдейт), проверяйте список подписки,
  а не только обработчик, — они меняются в разных файлах и по разным поводам.
- **Дефект правила находит чтение, а не замер.** `рудник` внутри «сотрудники»,
  `\bкуп` без слова «покупает», действие, названное существительным, — каждый
  раз замер выглядел законченным, потому что мерил ровно то, что в правило
  написали. Перечислить такие ошибки заранее нельзя; их можно только
  вычитывать. Поэтому после `promote.py` стоит шаг `review.py`: карточку
  читают против текста источника поле за полем. Первый прогон: из 13 карточек,
  которые приток добавил сам, поправить было что у 9, и самое опасное — не
  пустые поля, а МОЛЧАЛИВО НЕВЕРНЫЕ (дата новости вместо даты сделки, «Закрыта»
  на «объявила о приобретении»). Токены на такое чтение дешевле, чем неверная
  карточка в базе.
- **Дата новости — не дата сделки, и это ошибка без всяких признаков.** У
  «Дом.РФ»/«Обсидиан» стояло 3 августа, хотя в источнике «сделка была закрыта
  4 мая»; у «Риглы»/«Здорового города» — 3 августа против «сделки,
  зарегистрированной 30 июля». Ни один тест этого не видит: дата в формате,
  год верный, карточка отрисовывается. Ловится только чтением, а признак
  в тексте всегда один и тот же — «закрыта <число> <месяц>»,
  «зарегистрированной <число> <месяц>».
- **Шаг проверки чтением опасен ровно тем, чем ценен.** Он позволяет записать
  то, чего правило не увидело, — значит, он же позволяет записать выдумку.
  Граница обязана быть механической: каждая правка несёт дословную цитату
  источника, и `review.py` проверяет, что значение из цитаты выводимо (имя —
  подстрока, дата — день и месяц названы прописью при неизменном годе, отрасль
  — слово нашего словаря или профиль компании, статус — слово из закрытого
  списка), а сама цитата дословно лежит в сыром тексте. Проверка написана на
  себе: шесть заведомо неверных правок обязаны получить отказ, и это тест, а
  не намерение.
- **Кириллица в заголовке не доказывает, что сделка российская.** Заголовок
  по-русски у любой новости, включая «Visa купила BioCatch за $2,4 млрд»:
  первое правило «есть кириллица — значит наша» отвергло 0 карточек из 1551,
  то есть не работало вообще. Считать надо ИМЕНА СОБСТВЕННЫЕ (в кавычках или с
  заглавной, за вычетом чужой географии и родовых слов вроде «Продажа»,
  «Инвесторы»), российские маркеры, сумму в рублях и совпадение с профилем
  базы. Замер: правило не подтверждает российский рынок у 4 карточек из 1551
  (0,26%), и лишь ДВЕ из четырёх действительно чужие — остальные наши, просто
  написаны латиницей («MTS StartUp Hub», «ATI.SU»). Поэтому это «на решение», а
  не отказ: терять сделку молча дороже, чем показать человеку четыре карточки
  за три года.
- **Разнобой в разметке — признак нехватки категории, а не небрежности.** 14
  карточек про упаковку лежали в ЧЕТЫРЁХ отраслях: «Химия и удобрения» 6,
  «Пищепром и напитки» 4, «Потребительские товары» 2, «Фармацевтика» 1. Каждая
  метка по-своему логична — сделка про завод упаковки описывается то материалом
  (химия), то содержимым (пищепром), то конечным покупателем (потребительские
  товары), — и именно поэтому разметчик каждый раз выбирал разное. Заводить
  отрасль ради двух записей было бы дроблением, ради двенадцати — нет: они
  ставят «Производство тары» вровень с «Углём» (15) и крупнее десяти уже
  существующих отраслей. Прежде чем чинить разметку правилом, посмотрите, не
  просит ли она новой категории. Граница проведена по ПРОДУКТУ: производит саму
  упаковку — в тару; сырьё и краски ДЛЯ упаковки, а также переработка отходов
  упаковки обратно в сырьё — остаются химией (у Flint Group предмет сделки это
  ЛКМ, «Технониколь» дробит ПЭТ-бутылки в хлопья). Правило знает свою цену:
  12 верных из 14.
- **Факта может не быть в том источнике, из которого собрана карточка.** У
  «Полекса» «Коммерсантъ» пишет «производителя пищевой упаковки», и по этим
  словам отрасль читается неверно; материал («выпускает в Уфе пластиковую
  упаковку») и покупатель («Строма») названы у mergers.ru — второй статьи о той
  же сделке. Поэтому `review.py` умеет дописывать ИСТОЧНИК, а не только поля,
  и проверяет, что дописываемый адрес приток действительно забирал: ссылка,
  взятая из головы, — это ровно то, чего мы избегаем.
- **Заглушку не всегда можно восстановить — но всегда можно перестать
  утверждать.** У 238 карточек дата стояла ровно 1 января: год из источника
  брали, месяц и день не брали. Восстановление исчерпано и измерено:
  `fix_placeholder_dates.py` за два прогона поднял 131 дату по мета-полю
  статьи-источника, а на третьем прогоне из 245 оставшихся нашлась ОДНА
  (у 162 источник не отдаёт дату публикации, у 82 год статьи не совпадает с
  годом карточки — там сомнителен и сам год). Полная дата в адресе статьи
  нашлась у 6 карточек, с совпавшим годом — у 3; в тексте самих карточек — ни
  у одной. Вывод не «оставить как есть»: `2024-01-01` заменено на `2024` —
  год мы знаем и не теряем, исчезает только выдуманный день. Январь 2025 на
  помесячном графике упал с 52 сделок до 10 — всплеск был целиком нашей
  заглушкой. Правило шире дат: если факт не восстанавливается, снимайте
  ЛОЖНУЮ ЧАСТЬ записи, а не оставляйте её ради формата.
- **`new Date("2024")` молча даёт первое января.** Год-только надо ловить
  регуляркой ДО разбора даты, иначе снятая заглушка вернётся на экран сама
  собой и ровно в том же виде — при том, что в данных её уже нет. Родня урока
  про `\w` в JS: правило не падает, а тихо делает не то. Держит тест
  `test_year_only_date_is_never_shown_as_the_first_of_january`, который
  проверяет и `fmtDate`, и карточку, и подпись под графиком.

- **Тест, зависящий от часа, падает не там, где сломано.** Два теста
  публикации (лимит сообщений за прогон и правило бэклога) вызывают
  `send_telegram.main()` — и после введения дневного окна 10:00–19:00 стали
  проходить только днём: вечером `pace_allowance` честно возвращает ноль,
  отправок нет, `assert len(calls) == 3` падает. Сломано при этом ничего не
  было. Хуже другое — соседний тест «бэклог без нового факта не публикуется»
  вечером проходил бы по ЛОЖНОЙ причине: не потому, что правило работает, а
  потому, что вне окна не уходит ничего вообще. Поэтому обход темпа
  (`ignore_pace=True`) добавлен и туда, где тест ждёт пустоты. Правило общее:
  вводя ограничение по времени, пройдитесь по тестам, которые дёргают тот же
  вход, — и по тем, что ждут отрицательного результата, тоже.

- **«Не придержано» — не то же самое, что «выйдет по молчанию».** Очередь
  публикации считала «скоро выйдет» как «всё, что не придержано вручную» —
  и час за часом отчитывала непрочитанную карточку как «выйдет сама», хотя
  `approve.py`'s `plan_actions()` уже год как правильно отказывается
  публиковать по молчанию карточку без `reviewed` (защита от каркасных
  дефектов черновика, записанная выше отдельным уроком). Две настоящие
  сделки («Крупный комплекс в Ленобласти», допэмиссия «М.видео»), рождённые
  18 августа при починке бага притока (см. ниже), простояли в очереди больше
  суток без единого движения — а владелец каждый час получал одно и то же
  «2 карточки выйдут сами, если не трогать» и не понимал, что происходит.
  Правильный вопрос был не «сколько карточек не придержано», а «сколько из
  непридержанных уже прочитаны» — эти два множества разошлись ровно тогда,
  когда в очереди появилась хоть одна непрочитанная карточка, а до этого
  совпадали и маскировали разницу. Починено разделением на три честные
  причины ждать: «скоро выйдет» (прочитана, ждёт истечения суток), «ждёт
  прочтения» (никогда не выйдет по молчанию, пока кто-то не сверит её с
  источником), «придержана» (решение человека) — три места считали одно и то
  же неверно (`main.py`'s `_send_queue_batch`, `_ops_numbers`, `ops_status.py`'s
  `render_publish`), и все три исправлены одним и тем же разделением, а не
  по отдельности. Родня урока про два вида «Уведомлений создано: 0» (ноль,
  который не значит «нет данных») — здесь ноль движения в отчёте не значил
  «всё идёт по плану», а значил «застряло», просто оба состояния выглядели
  одинаково в тексте.
- **Тормоз, который не пропускает НИЧЕГО, прячет вторую поломку за собой.**
  `NEW_CARDS_NEED_REVIEW` (E9) неделю отправлял на ручное решение все новые
  карточки — и это выглядело исчерпывающим объяснением, почему база не
  пополняется. Сняли тормоз и прогнали ворота: прошло по-прежнему НОЛЬ. За ним
  стояла независимая стена — отрасль бралась только у профиля компании, а у
  новой компании профиля нет и не будет, пока карточка не попадёт в базу.
  Замкнутый круг: платформа структурно не могла принять сделку про компанию,
  которой ещё не знает. Сними мы тормоз месяцем раньше — не изменилось бы
  ничего. Правило: если страховка блокирует 100% потока, проверьте, что за
  ней, — иначе годами чинится замок на двери, за которой кирпичная кладка.
- **Замер на придуманном списке — это замер списка, а не правила.** «95,3%
  полноты, 0% ложных» у фильтра притока меряли на 18 темах, написанных руками.
  На живом потоке (2167 записей за сутки, 113 кандидатов размечены чтением)
  точность оказалась 35%: сделками считались «объём торгов на Мосбирже», «курс
  юаня вырос на копейку», «цена Brent ниже $81». Ручной список этого класса
  ошибок не содержал вовсе — его писал тот же человек, что и правило, и он
  придумывал ошибки, которые УМЕЛ придумать. Разметка живого потока лежит в
  `pipeline/ingest/live_labels.json` и коммитится: без неё «стало лучше» —
  непроверяемое утверждение. После правок 35% → 81% без потери единой сделки.
- **«Торги» — это и продажа с молотка, и биржа.** Одно голое слово давало 9
  ложных срабатываний из 74 — больше любого другого признака. Но вырезать его
  нельзя: «Роснефть выкупила Саянскхимпласт на торгах» — профильный случай, а
  «IPO GloraX на Мосбирже» — размещение. Первая версия сужения зарубила 16
  настоящих карточек базы. Биржу узнаём только рядом с рыночным движением
  (объём, индекс, курс, рост-падение), а не по самому слову.
- **Признак ищем в заголовке, отказываем по всему тексту.** Половина ложных
  срабатываний живого потока приходила из аннотации: «Российский разработчик
  получил патент США» прошло из-за «вложил $5 млн в», «В Прикамье жителей
  проинформируют о выборах» — из-за «перешла к». Обзор, дайджест и
  аналитическая колонка ВСЕГДА упоминают чужие сделки мимоходом; заголовок же
  говорит о том, чему посвящён текст. Родня урока про пресс-релиз («два
  текста, склеенных вместе») и про заголовок против «Дополнительной
  информации».
- **Правило не прыгнет выше согласованности собственной разметки.** Словарь
  отраслей по словам предмета сделки даёт 84,5% точности вместе с профилем — и
  дальше упирается не в себя, а в нас: «аэропорт» размечен в базе как
  «Транспорт и логистика» 5 раз и как «Порты и инфраструктура» 5 раз,
  «аптечная сеть» — 6 раз «Фармацевтика» и 4 раза «Здравоохранение». Прежде
  чем гнаться за последними процентами точности, посмотрите, сколько из них
  вообще достижимо.
- **Очередь, которая падает в одноразовый контейнер, — не очередь.** Карточки
  «на решение» складывались в `data/inbox/hold/`, а эта папка не хранилась в
  git: рутина работает в контейнере, который умирает после прогона. Каждый
  день приток находил сделки, аккуратно складывал их в ящик и выбрасывал ящик.
  Снаружи это неотличимо от «ничего не нашли». Всё, что адресовано человеку,
  обязано пережить процесс, который это написал.
- **Канал должен отличать «мы узнали новое» от «канал этого не видел».**
  Публикация смотрела, есть ли карточка в `telegram_posts`, — и у сделки из
  бэклога, которой обогащение дописало источник, выдавала обычный первый пост.
  В канал ушли «новости» о сделках 26 июня, 15 июня и 1 марта 2025 года.
  Читателю канала нужны новости, а не выдача архива за новость: пост о сделке
  старше 30 дней теперь начинается с «Новое о сделке · июнь 2026» и прямо
  называет, что именно стало известно.
- **Контейнер рутины поднимается пустым, и об этом молчат все.** 6 августа в
  среде рутин не оказалось ни `httpx`, ни `pytest`. Первое рубит ВСЕ четыре
  телеграм-скрипта (`send_drafts`, `approve`, `send_telegram`,
  `setup_telegram_webhook`) — они импортируют `httpx` внутри пути записи, то
  есть падают ровно тогда, когда собираются отправлять. Второе хуже: обязательная
  проверка «`python3 -m pytest -q` — ожидается 275 passed» отвечала «No module
  named pytest», и зелёного прогона перед коммитом не было НИ РАЗУ. Видимость
  нормы держалась тем, что приток работает: `fetch.py` ходит в сеть на `urllib`
  и в `httpx` не нуждается. Чинится стартовым хуком
  (`.claude/hooks/session-start.sh`), а не строкой в тексте рутины. Урок шире:
  прежде чем искать причину в своём коде, спросите, есть ли в контейнере то,
  чем этот код написан, — «скрипт не сработал» и «скрипта нечем запустить»
  снаружи неотличимы.
- **Очередь предпросмотра — тоже уже описанные сделки.** Индекс дублей
  `promote.py` строился по одной базе, а прошедшая ворота карточка с 5 августа
  ложится не в базу, а в `pending.json`. Второй прогон в те же сутки пропускал
  те же черновики заново: 6 августа задвоились бы 10 карточек из 11, и в группу
  ушли бы те же карточка и пост под новыми id. Сверяться надо со ВСЕМИ
  множествами, где сделка уже описана, — та же болезнь, что «у базы три
  источника данных, и проверка на дубль обязана смотреть во все», только третьим
  множеством стала очередь модерации. Держит тест
  `test_gate_sees_cards_waiting_in_the_preview_queue`, и он проверен на себе:
  на коде до правки дубль проходит ворота.
- **Тест, который смотрит уже, чем скрипт, падает на верной правке.**
  `test_review_table_is_applied_and_not_pending` искал карточки правок только в
  базе, хотя сам `review.py` читает и базу, и `pending.json`. Первая же правка к
  карточке, ждущей решения основателей, уронила тест с «карточки нет в базе» —
  хотя её там и не должно быть. Родня урока «проверка „чем дополнить" не должна
  быть уже, чем карточка»: расширяя, куда пишет скрипт, посмотрите, куда при
  этом смотрят его тесты.
- **Двадцать первое сообщение не уходит.** Telegram пускает в группу около 20
  сообщений в минуту и отвечает 429 с полем `retry_after`. Рассылка черновиков
  била без пауз и 6 августа отправила ровно 20 из 32: одиннадцатая карточка и
  всё сырьё не дошли, а сказала об этом только строка в логе одноразового
  контейнера. Хуже другое, что вскрылось следом: у карточки ДВА сообщения
  (📣 пост и 🗂 карточка), а отметка `draft_sent` была одна на оба — приди 429
  между ними, карточка считалась бы разосланной целиком, и проект поста не ушёл
  бы уже никогда. Отметка обязана быть у каждого сообщения своя, а темп —
  заложен в отправку.
- **Консоль, куда валят всё, перестают читать.** Ворота отправляют на решение
  куда больше, чем пропускают: 6 августа это 11 карточек против 75 сомнительных
  черновиков, то есть 97 сообщений в группу разом. Показывать сырьё пачками по
  десять можно без потерь — по молчанию оно не публикуется никогда, значит
  очередь ничего не теряет от ожидания; карточки и посты предела не имеют, у них
  молчание = публикация. Предел назван вслух в отчёте прогона: умолчавший предел
  читается как «это всё».

## Модерация притока (5 августа 2026)

Новые карточки НЕ попадают в базу напрямую. Консоль основателей — Telegram-
группа (env `TELEGRAM_REVIEW_GROUP_ID`; без неё — личные сообщения каждому из
`TELEGRAM_REVIEW_CHAT_IDS`). `send_drafts.py` шлёт туда ТРИ типа сообщений:
  * 📣 `[пост <id>]` — проект поста канала. Кнопки «пост в канал»/«без поста»
    (вердикты post_yes/post_no — модификатор канала, НЕ судьба карточки) и ✏️;
    ответ своим текстом заменяет пост и одобряет карточку (approve+edited);
  * 🗂 `[карточка <id>]` — поля + `#/preview/<id>`. Кнопки «✅ Опубликовать»/
    «✋ Придержать»/«✏️ Изменить»/«🗑 Выкинуть» (approve/hold/—/discard);
    discard сильнее таймаута молчания: карточка не выйдет ни на сайт, ни в
    канал и исчезает из очереди насовсем (нероссийский контур, не-сделки);
    ✏️ — НЕ вердикт, кнопка только подсказывает ответить текстом; ответ —
    ЗАМЕТКА (note): её потребляет ТОЛЬКО суточная рутина притока, читает
    `pipeline/ingest/read_notes.py` и применяет через `review.py` (для
    сырья — строит карточку тем же путём, что кнопка «в работу»);
  * ⚠️ `[сырьё <draft_id>]` — черновик, который ворота НЕ пропустили, с
    причиной. Кнопки «это сделка — в работу» (take: `approve.py` превращает в
    карточку предпросмотра и сразу шлёт по ней 📣+🗂) / «не сделка» (drop:
    запоминается в `data/inbox/moderation_state.json`, больше не показывается).
Кнопка/ответ приходят вебхуком на сайт -> таблица `moderation_decisions` ->
почасовая рутина забирает по `/api/moderation/decisions?token=…`
(`MODERATION_TOKEN`, по умолчанию `TELEGRAM_WEBHOOK_SECRET`) и применяет
`approve.py`. Молчание сутки — карточка выходит как есть; СЫРЬЁ по молчанию
не публикуется никогда (ворота его не пропустили — молчание не делает его
сделкой). Решение дописывается в само сообщение группы («— ✅ Одобрено
(Борис)»), чтобы второй человек видел, что первый уже нажал. `/queue` в боте
показывает три блока теми же значками.

Почему так: решение принимает человек в Telegram, вебхук приходит на сайт, а
применяет решение рутина в одноразовом контейнере, которому база сайта
недоступна (приватная сеть) — таблица + API единственный мост. Молчание —
согласие, потому что немой шаг, держащий весь поток, уже был (тормоз E9).
pending.json живёт в git: не закоммитить его — потерять очередь модерации.

Уроки первого дня консоли (6 августа 2026):
- **Ссылка на предпросмотр работает только после деплоя.** Сообщения с
  `#/preview/<id>` ушли в группу ДО того, как pending.json доехал до сайта, —
  и 20 минут владелец видел «только плашку» вместо карточки. Правильный
  порядок в рутине: коммит и push pending.json -> дождаться деплоя ->
  send_drafts. Страховка в коде: `site_pending_ids()` в send_drafts читает
  pending.json С САЙТА и откладывает карточки, которых там ещё нет
  (строка «Отложено карточек: N»).
- **Одна новость в двух изданиях — одно сообщение в группу.** Рижский вокзал
  пришёл из Ведомостей и Коммерсанта двумя черновиками; promote помечает
  второй `dup_in_batch` (общее название в кавычках среди придержанных одной
  партии), send_drafts его не шлёт. Вторая ссылка дописывается источником
  через review.py. Держит тест
  `test_same_story_from_two_outlets_is_one_console_message`.
- **Правила именования новых карточек — мягкие, и только для новых.**
  Заголовок не копирует дословно заголовок источника; в заголовке узнаваемый
  бренд, а не юрлицо (юрлицо — внутри карточки); вместо «крупнейший
  производитель X» — настоящее имя из статьи. Старые карточки под эти правила
  НЕ переименовываются (решение владельца). Правил про недвижимость не
  добавлять — даже жилая бывает значимой; нероссийский контур без российского
  элемента не публикуем.
- **Заголовок сделки называет бренд, `buyer`/`seller_id` — конкретное
  юрлицо, а не наоборот.** Просьба владельца 18 августа: «Яндекс купил
  завод» в заголовке — это правильно и даже лучше для читателя (бренд
  узнаваем), даже если по факту стороной сделки было ООО «Яндекс Заводы».
  Но карточка КОМПАНИИ, на которую ведёт плашка сторон, обязана быть именно
  этим конкретным юрлицом — тем, кто реально приобрёл долю, а не группой
  целиком: тот же принцип, что уже применён к УГМК-Инвест/УГМК и
  Экспанте/Ультиматек (см. лесенку уроков про `holding` выше). С профиля
  конкретного юрлица читатель переходит по бейджу «Входит в группу» на
  профиль группы и видит ТАМ её показатели — это и есть назначение
  двусторонней связи `holding`, которую починили в тот же день: не
  косметика, а ровно тот путь навигации, который владелец описал. Смешивать
  роли нельзя ни в одну сторону: писать `buyer` на профиль группы, когда
  известно конкретное юрлицо, — та же ошибка, что и заголовок с ЕГРЮЛ-именем
  вместо бренда, только в другом поле.

### Как владелец решает — записано 7 августа 2026, для консоли и для будущей автоматизации

Цель, которую владелец назвал прямо: «Компас» должен стать профессиональной
платформой уровня Mergermarket, и со временем сам решать, какую сделку
добавлять, а какую нет. Пока это решение принимает человек в консоли — но
решение не произвольно, у него есть логика, и её стоит записывать по мере
того, как она проявляется на реальных карточках. Ниже — не код-правило (оно
слишком контекстно-зависимо для регулярки), а материал для того, кто решает:
человек в консоли сегодня, промпт рутины притока завтра.

- **Жилая недвижимость — почти всегда мимо, но не по правилу «недвижимость
  мимо».** Владелец отклоняет почти все карточки о продаже квартир, домов,
  отдельных зданий, усадеб — «если какой-то физик просто купил, всё равно».
  Пропускает — если покупатель или предмет сам по себе значим: крупная
  компания, известный актив, сумма или сторона, о которой стоит написать
  отдельно от факта самой сделки с недвижимостью. Это НЕ повод завести признак
  «отрасль = недвижимость → отклонить»: такое правило противоречило бы уже
  записанному уроку выше (жилая бывает значимой) и один раз уже привело бы к
  потере настоящей сделки. Правильное место для этого критерия — подсказка
  тому, кто решает («физлицо купило X, крупных сторон не видно — обычно
  отклоняется»), а не тормоз на входе.
- **Нероссийский контур с российским бенефициаром — это НЕ нероссийский
  контур.** «Если узбекская компания купила другую узбекскую компанию, но
  выяснилось, что это актив какого-то российского олигарха — надо не
  пропускать, а делать карту.» Гейт `russian_evidence()` в `promote.py` уже
  правильно устроен для этого: он отправляет такие черновики на решение
  человека (⚠️ в консоли), а не отклоняет молча — важно НЕ менять это на
  автоотказ. Но решающий (человек сегодня, промпт рутины завтра) обязан перед
  тем, как нажать «не сделка», проверить конечного бенефициара, а не только
  формальные стороны из заголовка — иначе именно такая карточка потеряется.
- **Названия карточек, компаний и разделов — «user friendly», это отдельная
  проверка, не побочный эффект точности.** Формулировка может быть фактически
  верной и всё равно звучать неестественно, канцелярски или переведённой с
  другого языка. Проверка «звучит ли это как живая русская фраза, а не как
  результат работы с данными» — отдельный шаг обзора, наравне с проверкой
  фактов; см. также правило чуть выше «пояснение объясняет смысл числа, а не
  устройство базы» — тот же класс урока, только про заголовки и подписи, а не
  про цифры.
- **Профили компаний — источник неровности качества, которую владелец
  замечает первой.** Разные карточки компаний писались в разное время разными
  методами (правила, ручной ввод, заглушки); из-за этого тон и глубина прыгают
  от карточки к карточке. Это не разовая правка, а постоянная работа: у базы
  1872 профиля и вручную написанное описание есть меньше чем у трети (см.
  журнал `pipeline/write_company_descriptions*.py`). Ориентир при следующем
  профиле — не просто «что делает компания», а тон и длина такие же, как у уже
  написанных сильных примеров (Сбербанк, Яндекс), не выдумывая ничего сверх
  общеизвестного рода занятий.
- **Превосходная степень — не сама по себе штамп; штамп — превосходная степень
  без меры.** Профессиональные базы (Crunchbase и похожие) советуют вычищать
  «лучший», «ведущий», «самый» — первая реакция «вычистить всё такое слово»
  была бы неверной. Замер по базе (7 августа): 18 профилей со словом
  «крупнейший»/«ведущий», и 17 из них называют ПРОВЕРЯЕМУЮ меру — «Крупнейший
  частный банк России» (Альфа-Банк, уточнение «частный» отличает его от
  Сбербанка), «крупнейший в стране банк сельхозземель по площади» (Био-Тон,
  мера прямо в тексте) — это не штамп, а полезный факт о масштабе. Настоящий
  штамп нашёлся один — «Ведущий российский разработчик…» (Технорэд): «ведущий»
  без ответа на вопрос «по чему» (`pipeline/fix_vague_superlative_descriptions.py`).
  Признак «есть превосходная степень» — повод прочитать конкретное
  предложение, а не правило для сплошной чистки; родня урока «признак дефекта
  — повод прочитать, а не основание стереть».
- **Симптом, починенный трижды в трёх разных файлах, — сигнал, что чинили не
  корень.** Прямые кавычки вместо « » в title/buyer_name/asset правили
  вручную три раза за две недели — `fix_straight_quotes.py` (2 августа, 12
  карточек), `fix_new_card_titles_batch3.py` (8 августа: «та же болезнь, в
  новых карточках снова»), `fix_straight_quotes_batch1.py` (16 августа, ещё
  4 карточки). Каждый раз чинили СЛЕДСТВИЕ (уже записанные карточки), ни разу
  — ПРИЧИНУ: `build()` в `draft.py` копировал `title` из статьи дословно, а
  статьи набраны прямыми кавычками, и `clean_name()` не нормализовала стиль
  извлечённых имён сторон. Починено 16 августа на входе, а не на выходе:
  `normalize_quotes()` в `draft.py` красит прямые кавычки в « » при сборке
  ЛЮБОГО нового черновика (title и, через `clean_name()`, buyer_name/asset/
  seller), `review.py`'s `check()` отдельно отказывает в правке этих же
  полей через `--write`, если в `new` остались прямые кавычки (энрич может
  принести дефект тем же путём, что и приток), а `test_data.py`'s
  `test_no_straight_quotes_in_structural_fields` — забор с третьей стороны:
  ловит регресс по ЛЮБОМУ пути записи, включая тот, о котором мы ещё не
  думали. Общее правило: если один и тот же класс дефекта чинится больше
  одного раза, следующий вопрос — не «где ещё почистить», а «где он
  ВОЗНИКАЕТ», и правка идёт туда, плюс тест на всю базу, а не на
  прочитанные карточки.

## Чего не делать

- Не создавать pull request без явной просьбы.
- Не переписывать историю git, не делать `push --force`.
- Не удалять данные массово и не «чистить» профили компаний без разбора: среди
  них есть настоящие активы сделок.
- Не добавлять внешние CDN, шрифты и сервисы — всё должно работать из России.
- Не подменять отсутствующие данные правдоподобными: пустое поле честнее.
