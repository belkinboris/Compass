# Правила работы в репозитории «Компас»

## Что это

Одностраничное приложение о сделках M&A российского рынка. FastAPI отдаёт
статику, весь интерфейс — один файл `static/index.html` (~1900 строк, без
сборки и без внешних зависимостей). Данные лежат в JSON и подгружаются на клиент.

                              /api/assistant/bench (стенд сравнения моделей, по токену)

- `route()` — хеш-роутер; `render*()` — по экрану на функцию.

## Запуск и проверка

```bash
uvicorn main:app --reload            # http://127.0.0.1:8000
python3 -m pytest -q                 # 1099 passed, 33 skipped, 15 xfailed (≈8 мин: интерфейс — самое долгое)
python3 -m pytest test_data.py -q    # только инварианты базы, без браузера (0,1 с)
```

Три набора тестов:

| файл | что проверяет | нужен браузер |
|---|---|---|
| `test_kompas.py` | `yandex_search` и `/api/ask` | нет |
| `test_data.py` | инварианты базы: ссылки, роли, соглашения о записи | нет |
| `test_ui.py` | экраны открываются, не падают, не переполняют | да |

Скриншоты и проверка интерфейса — Playwright, браузер уже стоит:

```python
br = await p.chromium.launch(executable_path="/opt/pw-browsers/chromium")
```

Не запускать `playwright install` — браузер предустановлен
(`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`). Это правило про ЭТУ машину: в CI
(`.github/workflows/tests.yml`) Chromium ставится явно, потому что там его нет.
`test_ui.py` использует предустановленный путь, только если файл существует.

**Локальный сервер — три обязательные пустые/выключенные переменные.**
Контейнер рутин несёт боевые токены и ключи; локальный `uvicorn` без
защиты бьёт настоящими сообщениями настоящим людям и тратит настоящую
платную квоту (оба случая уже происходили). Запуск локального сервера
для health-check/приёмочных сценариев — ТОЛЬКО так:
`DATA_REFRESH_ENABLED=0 TELEGRAM_BOT_TOKEN= API_FNS_KEY= uvicorn main:app`.
`conftest.py` делает это за `pytest` сам, но ручной запуск сервера — нет.
Подробности и найденные инциденты — `KNOWN_ISSUES.md`.

## Язык для людей — обязательное правило для ВСЕХ текстов, которые читает человек

Записано 31 августа 2026 после прямой жалобы владельца и партнёра: они
пересылали друг другу фразы из наших отчётов и смеялись, потому что не
понимали их. Цитаты из той переписки — «Кампания привязки ИНН сработала
как рентген базы», «Финансы цели», «Лига консультантов с честными
знаменателями», «честный пустой результат». Каждая из них что-то значит
для того, кто читал этот файл, — и ничего для человека, который просто
открыл Telegram утром.

Правило: **любой текст, который увидит человек, пишется так, как вы
сказали бы это вслух партнёру, не читавшему наш код.** Это касается не
только экрана сайта (для него правила уже были), но и: постов канала,
сообщений и отчётов в Telegram-консоли, строк `ops_status`, ответов
владельцу в чате, текста кнопок и вопросов бота. Сообщения коммитов и
эта документация — внутренние, там диалект допустим.

Как проверить себя перед отправкой любого текста человеку:
- **Прочитайте фразу голосом.** «Дополнили 3 карточки, у Степи — честный
  пустой результат» вслух не говорят. Говорят: «Проверили 3 сделки; по
  Степи новых фактов не нашлось».
- **Слова нашего диалекта не выносить к людям:** «знаменатель», «линза»,
  «честная пустота / честный пустой результат», «дочитывание», «обыск»,
  «замер», «штамп», «прогон», «инвариант», «идемпотентный», «bulk»,
  «цель» в значении «покупаемая компания» (говорите «покупаемая
  компания»). Внутри кода и доков — пожалуйста.
- **Не сочинять эффектных метафор** («рентген базы», «лига с честными
  знаменателями»). Метафора, которую нужно расшифровывать, хуже скучной
  точной фразы.
- **Отчёт рутины начинается с трёх строк для человека:** что нового
  (по-человечески), что нужно от вас, сколько ждёт в очереди. Механика и
  подробности — ниже, для тех, кому интересно.

Это продолжение уже записанного правила «пояснение объясняет смысл
числа, а не устройство базы» — теперь оно распространяется на все
тексты для людей, а не только на подписи к цифрам на экране.

## Известные ошибки и их решения

Конкретные баги, найденные и починенные в этом проекте (регэкспы, поля, функции, тесты) — в отдельном файле `KNOWN_ISSUES.md`. Читать ПЕРЕД тем, как писать правило или чинить карточку (не наступать на те же грабли второй раз), и ПОСЛЕ, на вычитке/приёмке, если результат выглядит подозрительно похожим на что-то уже виденное. Правило записывается туда СРАЗУ, при первом обнаружении бага (не после повтора) — симптом, причина в одну фразу, чем исправлено (файл/тест), без истории «как искали и что перепробовали».

## Где что лежит и когда чистить документы (21 сентября 2026)

Вопрос владельца после двух чисток подряд: «не удалили ли лишнего и как
сделать, чтобы нужное сохранялось, а файлы не пухли». Ответ — не
осторожность на глаз, а одно деление, от которого зависит всё остальное.

**Документы делятся по СПОСОБУ ЧТЕНИЯ, а не по важности.** Файл, который
читают ЦЕЛИКОМ каждый прогон, умножает каждый свой знак на число прогонов —
ему нужен жёсткий потолок, и потолок здесь не бюрократия, а единственное,
что заставляет писать короче. Файл, в который ИЩУТ по запросу, не стоит
ничего, пока за один вопрос открывают одну запись, а не весь файл: он может
расти вечно.

| куда | что туда пишут | как читают | потолок |
|---|---|---|---|
| CLAUDE.md | ПРАВИЛА, действующие на каждом прогоне | целиком, каждый час | 110 тыс. |
| PRODUCT_ROADMAP.md | ОТКРЫТАЯ работа + свежий журнал | целиком, рутина качества | 200 тыс. |
| KNOWN_ISSUES.md | баги: симптом, причина, чем починено | `--find`, когда чинят похожее | **нет** |
| PRODUCT_ROADMAP_ARCHIVE.md | закрытая работа и замеры | `--find`, когда вопрос похож на старый | **нет** |
| консоль (`send_open_questions.py`) | вопросы, ждущие ответа человека | владелец в Telegram | — |

**У KNOWN_ISSUES.md потолка НЕТ, и это решение, а не недосмотр.** Потолок
на нём простоял полдня 21 сентября и снят по возражению владельца: «просто
не будет хватать места на запись новых проблем и решений, а в таком случае
они каждый раз будут вырабатываться заново». Возражение точное — такой
потолок экономит ровно те токены, ради которых ставится. Вместо него
действует инвариант «один вопрос стоит одну запись»
(`test_docs.py::test_a_searched_document_keeps_its_answer_the_size_of_one_entry`):
каждая запись лежит под своим заголовком `##`, вне заголовков не болтается
текст, и ни одна запись не разрослась до главы (потолок 12 тыс. знаков на
ЗАПИСЬ; замер 21 сентября: 356 записей, медиана 579, максимум 9 798).
Пока это так, размер файла никого не касается.

**Искать, а не читать: `python3 pipeline/docs_budget.py --find "<слова>"`.**
Ищет по ЗАПИСЯМ в KNOWN_ISSUES.md и в архиве, возвращает заголовок, адрес
«файл:строка» и начало записи. Заголовок называет симптом, поэтому
совпадение в нём весит больше, чем совпадение в теле, — иначе выигрывает
длинная запись журнала, в которой нужные слова просто встретились порознь.
Это и есть обязательный способ обращения к обоим файлам: читать их целиком
(276 тыс. и 2,3 млн знаков) дорого, а не читать вовсе — значит выводить
заново то, что уже измерено.

**Архив — не мусор, это проверено счётом.** 920 записей, в среднем 2,4 тыс.
знаков, и у 238 внутри замер или отвергнутая гипотеза с цифрами: «точность
отрасли по аннотации падала с 75% до 61–71% в каждом варианте», «из 85
профилей с превосходной степенью мера не названа у одного». Такая запись
дороже ненаписанного правила — без неё следующий прогон переоткрывает
отвергнутую гипотезу за токены. До 21 сентября архив не читал никто и
ничем: он был не мусором, а недоступным. `--find` ищет в нём наравне с
KNOWN_ISSUES.md — этого достаточно, переносить из него ничего не нужно.

**Когда чистить — не «когда разрослось», а по запасу.** `python3
pipeline/docs_budget.py --stats` печатает, сколько осталось до потолка у
двух файлов с потолком, и помечает ⚠️ всё, что перевалило за 85%: это
сигнал чистить СЕЙЧАС, пока потолок не уронил чужой прогон (сегодня ⚠️ у
обоих: CLAUDE.md 90%, бэклог 86%). Бэклог двигает `roadmap_archive.py
--journal --write` — это ответ на «надо понять, когда снова это делать»:
не по ощущению и не по календарю, а когда `--stats` показал ⚠️.

**Чем проверять, что чистка ничего не потеряла.** `docs_budget.py
--anchors <коммит до чистки>` сравнивает не тексты (при чистке текст
переписывают, построчный diff бесполезен), а ЯКОРЯ — имена скриптов,
тестов и id карточек, на которые документ ссылался. Исчезнувший якорь —
повод прочитать, а не приговор: одноразовый `fix_*.py` по одной карточке
помнить незачем. Проверено на чистке 18 сентября (CLAUDE.md 541 → 113
тыс. знаков): из 131 имени скрипта потерялись 16, и все — такие
одноразовые правки; ни одного правила и ни одного живого теста среди них
нет, потому что знание теста живёт в его докстроке, а не в документации.

## Что искать для линзы «Юрист» при чтении статьи

Читая статью для карточки сделки, ищите не только «кто кому сколько», но и
чем обставлена сделка юридически:

- **Заверения об обстоятельствах** (representations and warranties) — что
  продавец подтвердил о предмете сделки.
- **Возмещение потерь / индемнити** — кто платит, если заверение окажется
  неверным, и есть ли предел.
- **Ограничение ответственности** — потолок, срок предъявления претензий,
  порог существенности.
- **Отлагательные и отменительные условия** — что должно случиться до
  закрытия (согласие ФАС, правкомиссии, кредиторов, смена контроля).
- **Опцион** — колл/пут, обратный выкуп, право первого отказа,
  tag-along/drag-along.
- **Отложенный платёж (earn-out)** — часть цены зависит от будущих
  показателей.
- **Эскроу и обеспечение** — где лежат деньги до закрытия, залог,
  поручительство.
- **Неконкуренция и непереманивание сотрудников** — на какой срок и
  территорию.
- **Обязательства сохранить бренд, команду, производство** — часто
  единственное «условие», которое вообще раскрывают в российских сделках.
- **Применимое право и порядок разрешения споров** — редко, но встречается.

**Условие сделки или реассюранс-фраза продукту?** Перед тем как записать
найденное предложение в `law.terms`, задайте ему один вопрос: это условие,
на котором ПОКУПАТЕЛЬ согласился на сделку, — или сообщение о том, что
ПРОДУКТ/БРЕНД цели продолжит работать как раньше, адресованное её
собственным клиентам? Второе дословно похоже на первое («стандарты и
сертификаты сохранятся» рядом читается как «условие сделки»), но это
пресс-релизная фраза-заверение, а не переговорное условие — ей не место в
«Юристе», даже если она называет те же слова («сертификат», «стандарт»),
что и настоящее обязательство сохранить бренд. Отличить одно от другого
можно только вопросом «кому и о чём эта фраза», а не по форме предложения.

**Куда класть найденное.** Всё это идёт в `law.terms` (условия), `law.struct`
(как устроена сделка юридически) и `law.appr` (согласования), с тем же
требованием дословной цитаты источника. Если условие уже названо в тексте
карточки, но лежит в «Контексте» или «Дополнительной информации», а не в
своём поле, — перенос в нужное поле не считается новым утверждением, и
делать его нужно.

## Критерий готовности и контроль качества аналитики (6 сентября 2026)

Записано после второго аудита и разбора владельца с внешним рецензентом.
Вопрос, на который здесь есть ответ: какая проверка объявила исправления
первого раунда готовыми и почему она не заметила остаток.

**Что было приёмкой раунда 1 и почему этого не хватило.** Готовность
подтверждали три вещи: юнит-тесты на придуманных примерах (те же правила,
что и в коде, — они проверяют, что код делает заложенное, а не что
заложенное верно), счётчики («кандидатов 57 → 29 чистых») и исчезновение
НАЗВАННЫХ аудитором примеров (K2-9b, OneCell, «Открытие»). Ни одна из трёх
не смотрела на оставшийся список целиком глазами читателя: Guess (30%) и
«Полиматика» (49%) стояли в тех же 29 строках, что и после починки, — их
никто не открыл. Ассистент проверяли ПЕРВЫМ вопросом, а не цепочкой.
Дубли искали по признаку теста (два названия в кавычках при одной сумме),
а не по предмету сделки. Общее у всех промахов: проверялось, что механизм
сработал, а не что результат на экране правильный.

**Три правила приёмки, действующие с этого дня.**

1. **Неизвестность — не допуск к расчёту.** В мультипликаторы и в «Только
   покупки» идёт только то, что карточка УСТАНОВИЛА: доля, приобретаемая
   ИМЕННО в этой сделке (`stake_established`), сумма — цена, названная
   сторонами (`sum_basis == 'disclosed'`), предмет — один профиль с
   подтверждённым ИНН, не лот и не банк, сделка состоялась. Карточка без
   установленной доли остаётся в базе и в очереди на чтение, но не в
   статистике; причины отказа видны в ответе `/api/analytics/multiples`
   (`excluded`). Замер в день введения: из 38 кандидатов доля была названа
   у 10, у 24 — нет, и до этого все 24 шли в расчёт как «потенциально
   100%». Чтение источников тем же днём (`pipeline/ingest/fixes/
   batch_shares_2026_09_06_a.py`, `_b.py`): у 9 доля названа дословно и они
   вернулись в расчёт, у 2 куплено меньше 95% («Евроонко» — 11,5%,
   СКАУТ-КР — 51%), у 12 источники говорят «продала бизнес» без цифры — их
   в расчёте нет, пока кто-то не найдёт формулировку с долей.
   **Как устанавливается доля (вторая критика рецензента, тот же день).**
   Первая починка брала НАИМЕНЬШИЙ из названных процентов — рецензент
   прав, что это ошибка, а не осторожность: у «ранее владел 30%, купил 70%»
   наименьший — про прошлое, у «первый этап 68%» — про этап, у «участник
   консорциума 10%» — про соседа. Теперь процент засчитывается по СЛОВУ
   РЯДОМ: о приобретении (купил, выкупил, приобрёл, продал, переданы,
   перешли) — купленная доля; о результате (консолидировал, довёл до,
   сохранил, принадлежит, владеет) или об истории (ранее, прежде, в 2021
   году) — нет; глагол ищется и до процента, и после него до конца простого
   предложения («100% акций АО «КИВИ» переданы Fusion Factor»); в поле
   предмета (`eco.share`, `asset`) процент в начале поля — доля по смыслу
   самого поля, если за ним не идёт слово о владении. Несколько РАЗНЫХ
   процентов о покупке (этапы, консорциум, реструктуризация покупателя) —
   доля не установлена, не наименьший из них. Явное поле карточки
   `stake_acquired` (0 < доля ≤ 100, пишется через review.py с цитатой или
   одноразовым скриптом с `assert`) сильнее любого разбора — для карточек,
   где текст честно неоднозначен («Ингосстрах Банк»: 99,9% в заголовке,
   «100% перешли к…» о самом покупателе в предмете). Замер по 1239 покупкам
   2022+: доля установлена у 448 против 588 у правила наименьшего; порог
   95% проходят 183 против 191; из 36 сделок, у которых допуск изменился,
   правило наименьшего ошибалось в обе стороны — считало покупкой 100%
   «Орехов консолидировал 100% «Азота»» (куплено 40%), «Ростелеком
   консолидировал 100% ОМП», «почти полностью занят арендаторами»
   (Поклонка), и покупкой 1,35% — «Балтику» (98,65% напрямую + 1,35%).
   Клиентская копия — `stakeEstablished()` в `static/index.html`, сверена
   с Python на всех 1374 карточках клиента (0 расхождений) и на золотой
   выборке. `deal_multiples.DATE_BASES`/`date_basis` — тот же приём для
   даты: `'publication'` у Boxberry говорит, что 24 апреля 2025 — день
   СООБЩЕНИЯ о закрытии, не день закрытия, и карточка с ассистентом
   так и пишут.
   **Смысл суммы и допуск к расчёту — два признака, не один.** Смысл
   (`sum_basis`: цена, оценка, диапазон, нижняя граница, стартовая цена,
   валюта, объём привлечения, не цена) — свойство карточки, и диапазон
   остаётся диапазоном: он бывает и пределами цены по договору (earn-out),
   и оценкой, и переименовывать его в «оценку» нельзя (подпись на экране —
   «диапазон (пределы цены или оценка — способ расчёта не определён)»).
   Допуск (`ADMITTED_SUM_BASES`, на клиенте `isSoftSum`/`countsAsPrice`) —
   решение конкретного расчёта: в мультипликаторы и в топ покупок идёт
   только 'disclosed', диапазоны не идут, пока для них нет метода.
   **Цена пакета пересчитывается на 100% компании — порог «доля 95% и
   выше» ОТМЕНЁН 6 сентября 2026** (`deal_multiples.implied_full_price`,
   клиентская копия `impliedFullPrice`). Вопрос владельца: «неужели из
   полутора тысяч сделок цену и выручку мы знаем только у девяти? мы же
   практически у всех ООО видим из отчётности показатели». Замер воронки
   ответил, что дело НЕ в отчётности: 1564 карточки → 1372 с 2022 года →
   1189 покупок со сменой контроля → 174 с ценой в рублях → 142 с
   привязанным предметом → 103 с подтверждённым ИНН (не банк, не лот) →
   81 с пригодным отчётом НА ПРОДЕ. То есть знаменатель есть почти у всех,
   кого мы вообще довели до этого шага, а на экран проходили единицы —
   потому что из 103 доля 95% и выше стояла у 22, а у 49 не была
   установлена вовсе. Порог отсекал не «плохие данные», а весь класс
   ПАКЕТНЫХ покупок, которых на рынке больше, чем стопроцентных.
   Заменено по существу, а не ослаблено: цена, уплаченная за X%, делится
   на X — получается стоимость всей компании «по этой сделке» (так
   сопоставляют сделки в отраслевых базах), и в подписи прямо сказано, с
   какого пакета сделан пересчёт. Нижняя граница теперь про
   ОСМЫСЛЕННОСТЬ пересчёта, а не про контроль: `MIN_SCALABLE_STAKE = 25`
   — у пакета меньше четверти нет ни контроля, ни пропорционального
   влияния, и «цена ÷ доля» превращается в фантазию. Три вещи, которые
   стоит помнить об этом пересчёте:
   - **Цена, которая УЖЕ за всю компанию, не делится на долю никогда.**
     `scope` из чтения (`equity` — вся компания, `ev` — с долгом,
     `package` — пакет) сильнее самой доли: без этой ветки величина
     поделилась бы на долю дважды, и мультипликатор вырос бы вдвое-втрое
     на ровном месте. Проверка на себе — отдельный тест
     (`test_price_for_the_whole_company_is_never_divided_by_the_stake`).
   - **Премия за контроль и скидка за миноритарный пакет в пересчёте не
     учтены** — это сказано в методике на экране, а не только здесь:
     30% Guess по этой формуле дают ту же стоимость компании, что и
     100%-я покупка, хотя за контроль обычно платят дороже. Мы не
     умеем это поправить и не притворяемся, что умеем.
   - **Числитель у мультипликатора и у строки «не показана» — один.**
     `_why_not` считает выброс от той же пересчитанной цены; иначе
     сделка исчезала бы из списка с числом, которого нигде нет.
   Текстовых кандидатов стало 49 вместо 14 — из них 33 дал сам пересчёт,
   ещё 16 пришли следом, когда правило перестало требовать НАЗВАННОГО
   ПРОДАВЦА (см. ниже). Родня уже записанного «инвариант можно заменить,
   но не отменить»: порог остался, изменился вопрос, на который он отвечает.

   **Имя продавца в мультипликаторе не участвует — и требовать его было
   подменой.** `dm.admission` до того же дня отказывала сделке, у которой
   «названы не обе стороны». В мультипликаторе участвуют цена, доля,
   предмет и его отчётность; продавец — нет. Требование стояло дешёвым
   признаком «сделка описана хорошо» и заодно страховкой от допэмиссии
   (у cash-in продавца нет), но страховка эта негодная: у обычной покупки
   продавца сплошь и рядом не раскрывают («МТС приобрела 51% «Винтео»»,
   «Магнит» покупает контрольный пакет «Азбуки вкуса»» — 16 таких сделок).
   Теперь требуется только покупатель (`no_buyer`), а от cash-in защищает
   подтверждаемая ЧТЕНИЕМ смена контроля — там, где этот вопрос и решается.
   Нашлось не замером, а инвариантом «чтение подтверждает, но не
   расширяет» (`test_gold_verified_multiples_are_a_subset_of_rule_
   candidates`): два чтения подтвердили факты «Винтео», а текстовые
   правила отказали — и это был сигнал проверить ОБОИХ, как он и задуман.
   Тот же инвариант тем же вечером поймал две настоящие дыры в данных:
   у VK/«Зингера» покупатель, а у Wink/«ЛайфСтрима» продавцы стояли
   ТОЛЬКО в тексте карточки (починено переносом в поля с проверкой
   дословности).

   **Настоящее узкое место — не порог доли и не отчётность, а ПЕРИМЕТР.**
   Ночная кампания чтения (76 сделок, четыре пары читателей, 6 сентября
   2026) дала честный ответ на вопрос владельца. Мультипликатор получили
   12 сделок вместо 5; «Крупнейшие покупки» выросли с 23 до 49, сделок с
   прочитанной ценой — 120. Но у 38 из 76 прочитанных периметр ОТВЕРГНУТ:
   куплена группа («Рольф» — четыре юрлица; НМЖК — комбинаты, МЭЗы и
   элеваторы; «Агро-Белогорье» — 20 свинокомплексов; «Учи.ру» — вместе с
   «Учи.Дома» и «ЯКласс»), или куплено имущество, а не юрлицо («Белая
   площадь», ТРЦ «Аквилон», логопарк FM Logistic), или в знаменателе
   оказался отчёт ПРОДАВЦА (ZONT/«Аэротель») либо ПОКУПАТЕЛЯ
   («Лента»/«Утконос», «Медскан Лаб»), или однофамилец (digital-агентство
   «Апрель» против аптечной сети «Апрель»), или головная компания вместо
   группы («Росспиртпром» — 1,8 млрд ₽ в отчёте против 10,7 млрд ₽
   выручки от спирта; ЮГК — 33,9 против 75,9 млрд ₽; Globaltruck — 132,7
   млн ₽ против 15,4 млрд ₽). Вывод, который стоит помнить и не
   переоткрывать: в российских открытых данных отчётность сдаётся по
   ЮРЛИЦУ, а сделки заключаются по ГРУППЕ. Это не чинится ни правилом, ни
   расширением реестра ИНН — только чтением по одной сделке, и поэтому
   список мультипликаторов будет расти медленно и оставаться небольшим.
   Показать десяток проверенных сделок с названным периметром честнее,
   чем сотню, где знаменатель взят от чужого юрлица.

   **Медианы мультипликаторов скрыты** (`SHOW_MULTIPLE_MEDIANS`, по
   умолчанию выключено; список сделок с ценой и показателем и методика
   остаются): «10 чистых» значит «прошли правила допуска», а не «сопоставимы
   между собой» — периметр, долг и год отчётности методикой не утверждены,
   и одна цифра по десятку сделок читалась бы как ориентир рынка.
   Включение — решение владельца после оценщика.
   **Не-дубли помнятся с отпечатком.** Пара, прочитанная и признанная
   двумя разными сделками, не показывается сканеру снова
   (`pipeline/gold/non_duplicates_seen.json`), но отпечаток считается по
   заголовку, дате, сумме и сторонам: если одна из карточек существенно
   изменилась, пара открывается заново.
2. **Ожидаемый результат фиксируется независимо от кода.**
   `pipeline/gold/analytics_gold.json` — контрольная выборка: для каждой
   сделки чтением карточки и источников записано, какая доля куплена, что
   означает сумма, должна ли сделка попасть в мультипликатор и в топ
   покупок; отдельно — пары дублей и не-дублей и цепочки вопросов
   ассистенту. `test_gold_analytics.py` сверяет серверные правила с
   таблицей, `test_ui.py::test_gold_rows_agree_with_client_rules` —
   клиентские копии на тех же карточках. Строка, где карточка ещё не
   соответствует истине (`pending`), падает строгим xfail и краснеет, когда
   данные починят, — снять `pending` руками. Выборку пополняет каждый
   найденный дефект: сначала строка с ожиданием, потом починка. Поле
   `verified_at` пусто, пока таблицу не прочитал владелец.
3. **«Готово» — это показанный результат на работающем сайте.**
   `pipeline/acceptance_check.py` проходит пользовательские сценарии на
   боевом (или локальном) сайте и печатает протокол: что проверяли, где,
   что увидели — база на сайте совпадает с репозиторием; мультипликаторы
   без запрещённых выборкой сделок, долей ниже 95% и не-цен; ассистент
   держит сделку по цепочке из двух вопросов; PDF — настоящий PDF с
   кириллицей; «Только покупки» без оценок и финансирования; адреса
   слитых дублей открывают оставшиеся карточки; ошибок страницы нет.
   Запускается после каждого существенного изменения данных, аналитики,
   ассистента или экспорта — до того, как сказать «готово» владельцу, и
   отчёт о готовности состоит из строк этого протокола, а не из «тесты
   зелёные». PDF проверяется по САМОМУ скачанному файлу: текст извлекается
   (pdfminer), в нём обязаны читаться слова заголовка по-русски и не должно
   быть служебных пометок («Источник: обогащение»).

**Чего не делаем.** Не строим большую систему контроля до беты: три
правила выше, выборка на два-три десятка сделок и прогон сценариев после
изменений. Утверждение методологии мультипликаторов (формулы и условия
допуска) — за оценщиком и владельцем; код ждёт этого решения с честной
подписью на экране, а не заменяет его.

## Слой фактов: числа считаются по подтверждённым фактам, а не по прозе (6 сентября 2026)

Архитектурное решение после двух аудитов и двух разборов рецензента,
одобрено владельцем («переход от расчётов по прозе к структурированным
фактам с источниками поддерживаю; согласился бы на меньшее покрытие
аналитики ради проверяемости»). Три структурные причины повторявшихся
дефектов: единицей правды была проза карточки и аналитика выводила из неё
числа регэкспами; у факта не было происхождения (прочитан, выведен правилом
или предположен — для расчёта одинаково); правила жили в двух исполнителях
(Python и JS) и расходились. CLAUDE.md рос уроками «регэксп не увидел
форму слова» — это признак, что знания хранились не там.

**Устройство (`facts.py`, `pipeline/facts_derive.py`, `pipeline/facts_confirm.py`).**
- У каждой сделки есть объект `facts` с пятью вычислимыми фактами: доля,
  приобретаемая в ЭТОЙ сделке (`stake`: значение, объект, событие); цена
  (`price`: рубли, КАК раскрыта — `meaning` из `SUM_BASES`, и ЗА ЧТО —
  `scope`: пакет / вся компания / с долгом); дата и её основание; природа
  сделки как НЕ взаимоисключающие признаки (смена контроля, деньги в
  компанию, финансирование, торги, реорганизация — рецензент прав, что на
  торгах можно купить контроль); предмет как юрлицо с ИНН из реестра и
  подтверждением периметра (что отчётность этого юрлица описывает
  купленный бизнес). Всё остальное в карточке остаётся прозой.
- У каждого факта есть основание `basis`: `rule` — предложено разбором
  текста; `read` — одно чтение с дословной цитатой; `verified` — два
  НЕЗАВИСИМЫХ чтения сошлись в значении и смысле (`verified_by: model×2`;
  подтверждение человеком — `human:<имя>`, отличается); `disputed` —
  разошлись, ждёт человека; `stale` — карточка изменилась после чтения
  (отпечаток `card_hash` полей, по которым факт читали) — допуск снят до
  повторного чтения. Правила больше не решают, они ПРЕДЛАГАЮТ: неверное
  правило может лишь поставить не того кандидата в очередь чтения, на
  экран число попадает только после чтения. Поэтому число правил перестало
  влиять на достоверность, и наращивать их больше не нужно: непонятая
  формулировка идёт в очередь чтения, а не в регэксп.
- **Допуск — отдельно для каждого показателя** (`facts.admitted`,
  причины — `facts.REASON_LABELS`): число сделок и отрасли — по факту
  существования и отрасли; суммы по годам и отраслям (графики) — покупка,
  состоялась, цена названа сторонами в рублях хотя бы по тексту (`rule`);
  список крупнейших покупок — то же, но цена ПРОЧИТАНА в источнике;
  мультипликатор — смена контроля, одно юрлицо с ИНН, не банк и не лот,
  периметр подтверждён, доля ≥95% и цена — всё `verified`, плюс отчётность
  за нужный год на сервере. Отсутствие цены не выкидывает сделку из числа
  сделок, отсутствие доли не мешает показать её цену.
- **Три уровня проверки — разные и хранятся раздельно.** Источник: цитата
  дословно лежит в тексте статьи (кэш `data/inbox/raw/*-articles.jsonl`,
  скачивается при сборке очереди) и значение выводимо из неё. Смысл:
  цитата подтверждает существование слов, не трактовку («500 млрд ₽»
  стояли в источнике и были допэмиссией), поэтому читатель отвечает про
  объект, событие и периметр, а факт становится `verified` только при
  согласии двух чтений. Арифметика: `facts.number_checks` — порядок
  величины, единицы, валюта, доля пакета против цены всей компании; так
  нашлась «2,5 тыс. ₽ (номинальная цена по решению суда)» в допущенных.

  Клиентские копии регэкспов удалены. Держит `test_data.py::
  test_facts_are_current`: derive обязан совпадать с тем, что в базе.

  человек смотрит только `disputed` и выборочно 1–2 подтверждённых
  (владелец: «я как человек могу максимум 1–2 проверить»). Медианы
  мультипликаторов скрыты (`SHOW_MULTIPLE_MEDIANS`), индивидуальные
  мультипликаторы показываются только для `verified`-сделок, с формулой и

## Открытые вопросы к владельцу живут в консоли, а не здесь (20 сентября 2026)

Владелец: «не засоряй CLAUDE.md, нужно так систему выстроить, чтобы наш фон
не засорялся, в противном случае у нас каждое изменение сжирало много
токенов». Он прав, и механизм для этого уже был: `pipeline/send_open_questions.py`
шлёт вопрос в консоль отдельным сообщением с маркером `[карточка <id>]`, а
ответ возвращается через тот же мост, что и решения модерации. То есть очередь
вопросов — это Telegram, а не документация.

**Правило: в CLAUDE.md пишутся ПРАВИЛА, а не ОЧЕРЕДИ.** Правило читают на
каждом прогоне, и оно окупается; вопрос, ждущий ответа, читают на каждом
прогоне зря — и он дорожает сам, пока висит. Нашёл расхождение, которое без
человека не решить, — вопрос идёт в `send_open_questions.QUESTIONS` и оттуда в
консоль. Сюда попадает только то, что уже решено и стало правилом.

**Правило для «обсуждается» без новостей много лет (решение владельца,
19 сентября 2026).** Молчание без прямого опровержения не делает сделку
несостоявшейся — статус остаётся «обсуждается». Но если прошло больше двух
лет без подтверждения и без опровержения, в конец `eco.context` (или в
`extra`, если `eco.context` нет) дописывается дословно: «Обсуждение тянется
больше двух лет без единого подтверждения — есть вероятность, что сделка не
состоялась.» Без вариаций, чтобы формулировка узнавалась.

## Стоимость прогона — это контекст, а не работа (замер 9 августа 2026)

ГЛАВНАЯ ЦИФРА. Прочитать статью и внести правки в карточку стоит ~4 тыс.
токенов. Прочитать CLAUDE.md + PRODUCT_ROADMAP.md + review.py, без чего рутина
не начинает работу, — 284 тыс. То есть при обогащении «по одной карточке за
часовой прогон» 98% денег уходит НЕ на работу, а на перечитывание одного и
того же. Обогащение 166 карточек 2022 года: по одной — 32 млн токенов,
партиями по 25 — 2,5 млн. Разница в 13 раз, и она вся в накладных.

ОТСЮДА ПРАВИЛО: содержательную работу над МНОЖЕСТВОМ карточек делать
ПАРТИЯМИ в одной сессии, а не по одной в почасовой рутине. Почасовая рутина
хороша для того, что и должно случаться по одной: реакция на поломку, разбор
свежего притока, ответ на заметку партнёра. Разгребание накопленного долга ею
делать дорого.

БЭКЛОГ — ТОЛЬКО ОТКРЫТАЯ РАБОТА (20 сентября 2026, вопрос владельца: «зачем
там столько зачёркнутых»). Он прав, и вот счёт: закрытые пункты занимали
21,6 тыс. токенов, то есть их перечитывала каждая рутина каждый час и не
действовала по ним никогда. Закрытый пункт уезжает в архив целиком, в бэклоге

## Три рутины и цикл обучения механики (записано 9 августа 2026)

ТРИ РУТИНЫ, ТРИ ГЛАГОЛА. Их намеренно три, а не десять, и делятся они не по
скриптам, а по тому, что происходит с данными:

| рутина | когда | глагол | что делает |
|---|---|---|---|
| приток | 08–21 МСК, ежечасно (:20) | ПРИХОДИТ | **быстрый путь для новой сделки первым** (fetch → triage → promote → сборка чтением → приёмка → консоль), потом enrich, разбор сырья и всё остальное — см. «Конкурент раньше и богаче» |
| публикация | 10:00–19:00 МСК, ежечасно | ВЫХОДИТ | решения из консоли → база → **приёмка** карточек из кнопки «в работу» и карточек базы перед первым постом → посты в канал (с вычиткой) |
| качество | ежечасно | УЛУЧШАЕТСЯ | сначала видимые поломки, потом очередь дочитывания (G7), потом подтверждение фактов двумя читателями (`facts_confirm.py --queue`, см. «Слой фактов»), потом очередь находок аудита (`audit_queue.py --queue`, начиная с классов, которые искажают факт сделки), потом бэклог блока G (PRODUCT_ROADMAP.md, раздел G — весь список, не только первые пункты) |

Каждый прогон, тронувший карточки, перед pytest выполняет `python3 pipeline/facts_derive.py --write` (слой фактов; `review.py`/`approve.py` делают это сами). Новое существенное встраивается ВНУТРЬ этих трёх, а не заводит четвёртую:
вычитка постов — шаг публикации, дочитывание старых карточек — шаг качества,
обучение механики — шаг качества. Отдельная рутина заводится только если у
работы своё расписание, которого нет ни у одной из трёх.

подробности сделки, не делали ни разу; если возвращаться к вопросу

ЦИКЛ ОБУЧЕНИЯ МЕХАНИКИ. Таблица `FIXES` в review.py — это не только журнал

и делит промахи на два вида: механика ПРОМОЛЧАЛА (128 из 156 — норма для
полей, требующих смысла) и механика СОВРАЛА (28 — это и есть материал для
новых правил, потому что неправда уезжает в базу и в канал как факт).

базе, и результат — принят ИЛИ ОТВЕРГНУТ — дописывается в `LEARNED`/`REJECTED`
того же файла. Отвергнутая гипотеза с цифрами ценнее ненаписанного правила:
без записи следующий прогон переоткрывает её за токены (9 августа так были
измерены и отвергнуты три подряд гипотезы про отрасль из аннотации).

ЧТО МЕХАНИЗИРУЕТСЯ, А ЧТО НЕТ — ЭТО ИЗМЕРЕНО, А НЕ МНЕНИЕ. Механикой хорошо
берутся форма и запрет: падеж предмета (`casing.py`, 19 срабатываний, 0
ложных), отказ брать число не из того предложения (`NOT_A_PRICE`, зарубает 3,

(`is_generic_description`, ошибок покупателя 82 → 77). Не берётся смысл:
отрасль по аннотации меряли трижды — точность падала с 75% до 61–71% в каждом
варианте. Отсюда рабочее разделение: механика отвечает за «как записано» и за
«этого брать нельзя», чтение — за «что здесь на самом деле сказано». Убрать
чтение целиком нельзя не из осторожности, а по замеру.

обратно — `mcp__Claude_Code_Remote__update_trigger` на `trig_011pXpFqxFGU9v64GRHN95Hu`

## Приток (`pipeline/ingest`, `pipeline/publish`)

Конвейер одной новости: `fetch.py` (забор в `data/inbox/raw/`, без сети —
только складывает) → `classify.py` (фильтр «это вообще сделка?», измеренный
на реальном потоке, не на придуманном списке) → `match.py`/`enrich.py`
(сверка с уже существующими карточками, дополнение только по СИЛЬНОМУ
совпадению) → `draft.py` (сборка черновика: стороны, дата, сумма, отрасль) →
`promote.py` (ворота: ПУСТИТЬ / НА РЕШЕНИЕ / ОТКАЗ — приток не пишет в базу
напрямую) → `review.py` (чтение источника, дословные цитаты, штамп
`reviewed`) → `link_parties.py` (привязка сторон к профилям компаний,
идемпотентно) → `accept_card.py` (приёмка перед консолью — см. раздел ниже)
→ `send_drafts.py` (в консоль, только когда карточка есть на самом сайте) →
решение человека → `approve.py` (применяет) → `send_telegram.py`
(публикация, только когда карточка уже отдаётся с сайта; `post_preview`,
если есть, важнее живого рендера).

Три момента, о которые конвейер уже спотыкался и для которых есть защита:
- **Молчание — не то же самое, что «ничего не произошло».**
  `pipeline/ops_status.py` шлёт строку в консоль в конце КАЖДОГО прогона,
  включая пустой (кроме одного тихого часа в сутки для притока — см.
  `intake_is_quiet_hour()`), — иначе «прогон был, ничего не нашлось» и
  «прогона не было вовсе» выглядят одинаково.
- **Одна новость в двух изданиях — одно сообщение в консоли.**
  `dup_in_batch` в `promote.py` гасит второй черновик о той же сделке в
  одной партии.
- **Латиница в заголовке — не признак нероссийской сделки.**
  `russian_evidence()` ищет российские маркеры (₽, ООО/АО, известный
  российский профиль по кириллическому имени) до того, как отклонить
  черновик; полностью собранный черновик с латинскими именами сторон
  показывается консоли под честной причиной, а не прячется молча.

Класс дефектов «правило написали по одному примеру, а оно не работает на
соседнем» (падежи, `\w`/`\b` в регэкспах, разбор дат, извлечение сумм из
чужого абзаца) — самый частый источник находок притока. Конкретные случаи и
их починки — в `KNOWN_ISSUES.md`.

## Приёмка карточки перед консолью и каналом (11 сентября 2026)

Владелец, второй раз за день открыв свежую карточку с теми же дефектами
(предмет-описание в косвенном падеже, некликабельные стороны, газетная фраза
под «Юристом», «Зачем» об объёме рынка, один источник там, где статья сама
ссылается на пресс-релиз): «это уже не первый раз… я не понимаю, почему я
должен смотреть case by case, хотя нужно сразу карты делать нормальные.
Необходимо обеспечить, чтобы такого больше не было». Токены — не
ограничение (Max ×20): каждую карточку и каждый пост можно прочитать
целиком до публикации.

**Диагноз, почему повторялось.** Каждый из дефектов уже был закрыт
правилом — но правило стоит на ОДНОМ пути (draft.py, review.py,
link_parties) и проверяет ОДНО поле по ФОРМЕ: дословность цитаты, регэксп,
падеж. Карточка приходит несколькими путями (ворота притока, кнопка «в
работу» в консоли, правки дочитывания), а вопросы владельца — про СМЫСЛ:
«это имя компании или описание?», «это ответ на „зачем"?», «это условие
сделки или пресс-релиз?». Ни одна проверка формы на них не отвечает, и не
было шага, где кто-то читает ГОТОВУЮ карточку и пост целиком глазами
читателя. Этим читателем был владелец.

**Что сделано — не ещё одно правило, а замок на выходе.**
`pipeline/ingest/accept_card.py` + бриф `pipeline/ingest/CARD_ACCEPTANCE_BRIEF.md`:
одно чтение на карточку по чек-листу владельца (источники, включая
первоисточник по ссылке из статьи; стороны — профили, а не текст; предмет
назван и в именительном падеже; заголовок читается вслух; «Зачем» о мотиве
или пусто; каждое поле о своём; язык человеческий; пост прочитан как
подписчик; статус и дата о том событии, что описано). Читатель — саб-агент
рутины — правит карточку через существующие механизмы (профили и привязки —
здесь; факты с цитатой — review.py; проза — proofread.py, который с этого
дня видит и очередь предпросмотра) и отвечает файлом
`data/inbox/acceptance/<дата>.json`. Скрипт проверяет ответ механически
(новых имён в заголовке нет, профиль — имя, а не описание, и не близнец
существующего, описание без пресс-атрибуции, чек-лист закрыт, у роли без
профиля названа причина) и ставит штамп `accepted` только когда
механических находок не осталось. Три гейта читают штамп: `send_drafts`
(без него 🗂/📣 в консоль не уходят — владелец видит принятую карточку, а не
корректирует сырую), `approve.plan_actions` (молчание не публикует
непринятую), `send_telegram` (первый пост только с штампом; `post_override`
владельца — сильнее; правки уже вышедших постов не здесь). Забыть шаг
нельзя: каждый гейт называет в отчёте, сколько карточек ждёт приёмки.

**Где шаг стоит в рутинах.** Приток: после сборки чтением
(`REVISION_BRIEF`) и до `send_drafts` — `accept_card.py --queue` → читатель →
`review.py --write` / `proofread.py … --write` при необходимости →
`accept_card.py --check` → `--apply … --write`. Публикация: то же для
карточек, рождённых кнопкой «в работу» (approve.py их создаёт и шлёт в
консоль сам — без штампа они дождутся этого шага), и для карточек базы,
которым предстоит первый пост (очередь `--queue` их показывает). Качество:
шаг не нужен — оно работает с уже опубликованными карточками; если правка
качества снимает штамп (не снимает: штамп — про приёмку перед публикацией,
а не про вечную чистоту), очередь вычитки по-прежнему ловит прозу.

**Цена.** Одно чтение на карточку, досье ≈3–5 тыс. токенов, при 2–5
карточках в день — копейки рядом с одной карточкой, которую владелец
увидел первым. Лишних проверок нет: механические находки считаются без
сети и без модели, читатель зовётся один раз, и только к тем карточкам, у
которых впереди консоль или канал.

**Что нашлось по дороге и починено тем же днём.** (1) Ночные правки
интерфейса 8 сентября (линза «Юрист» — только согласования, условия и
консультанты; «Как устроена сделка» — на «Обзоре»; второй сигнал
мультипликаторов) были откачены дважды из-за OOM-падений сборки и после
находки причины не вернулись: `format_post.lens_links` уже жил по новому
правилу, а сайт — по старому, и владелец увидел механику размещения под
«Юристом». Возвращены целиком (`git diff 9d8b2dc 9d8b2dc^` ложится на HEAD
без конфликтов; test_ui 104 passed). (2) «Зачем» в посте брало «любое
предложение „Цели сделки", которое влезло в 200 знаков»: мотив PT/CyberOK
не влез, и выбор по длине взял оценку рынка. Теперь — только первое
предложение о мотиве (`format_post._why_sentence`, `NOT_A_MOTIVE`); не
влезло — строки нет вовсе, лучше нет строки, чем строка не о том.
(3) Вычитка не видела очередь предпросмотра — владелец читал сырую прозу в
консоли (второй раз, см. урок «Владелец видит карточку в консоли РАНЬШЕ,
чем её вычитывают»): `proofread.py` теперь грузит и пишет оба файла.
(4) `main._send_queue_batch`/`_ops_numbers` и `ops_status` считали «выйдет
сама» по `reviewed` — с гейтом приёмки это снова обещание, которое не
сбудется (родня «Не придержано — не то же самое, что выйдет по молчанию»);
«скоро выйдет» теперь требует и `accepted`.

## Разрешение дублей чтением, а не консольной кнопкой (13 сентября 2026)

Тем же вечером, что и слияние «Метрополиса», владелец возразил на план
развивать консольную кнопку «это этап уже описанной сделки»: «мне бы
хотелось, чтобы ты сам понимал, что это дубль, чтобы мне не пришлось
нажимать». И указал на нюанс, которого раньше не было в архитектуре: дубль —
не всегда новый этап (веха). Это может быть буквально то же самое, что уже в
карточке, без единого нового факта, — тогда черновик просто не должен
становиться карточкой и вопросом, а не только не становиться отдельной
карточкой при подтверждённом этапе.

**Что было не так с прежним планом.** Кнопка в консоли решала только ТУ
ЧАСТЬ задачи, которую человек уже увидел и распознал сам, — она превращала
«да, это тот же дубль» в веху одним нажатием. Но само распознавание («нет ли
случайно карточки про это же?») оставалось на человеке: `near_duplicate()`
в `promote.py` (см. запись про ТЦ «Метрополис» выше) только НАХОДИЛ
кандидата и клал его в hold с причиной «проверьте, не дубль ли» — то есть
ровно тот рутинный вопрос, который владелец просил не задавать.

**Устройство.** `near_duplicate()` больше не спрашивает владельца
напрямую. `promote.check()` получил необязательный `dup_out` — список,
в который near_duplicate() кладёт найденного кандидата отдельно от
человекочитаемой строки в `hold`. `main()` смотрит: если у черновика
РОВНО ОДНА причина hold и это подозрение на дубль — черновик уходит не в
`data/inbox/hold/` (откуда `send_drafts.py` спрашивает владельца), а в
`data/inbox/duplicates/<дата>.json`. Если дубль — лишь одна из нескольких
причин (например, ещё и сторона не названа), поведение не меняется:
дочитывание пары само по себе такой черновик не спасёт, нужен человек
всё равно.

Вторая половина — `pipeline/ingest/resolve_duplicates.py` +
`DUPLICATE_RESOLUTION_BRIEF.md`. Читающий (саб-агент рутины) читает пару
(черновик + карточка-кандидат целиком, включая источники) и решает один
из ПЯТИ исходов, а не один «да/нет»:
  - **`same_fact`** — то же самое, без нового факта; черновик просто не
    становится карточкой. Технически — та же метка, что уже ставит
    `match.py` для сильных совпадений (`raw_titles[...] = 'enrich:<id>'`),
    применённая к слабому, требующему чтения совпадению.
  - **`new_stage`** — новое событие в жизни ТОЙ ЖЕ сделки (сорвались
    переговоры, получено согласование, сделка закрыта) — дописывается
    `events[]` карточки-кандидата, дословность `note` проверяется тем же
    `review.quote_is_real`, что и обычная правка; постворти-виды (`approval`/
    `closed`/`cancelled`) дополнительно получают снимок и заголовок через
    `review.py --milestone`, как и раньше.
  - **`enrich`** — та же стадия, но источник называет деталь, которой в
    карточке ещё нет; уходит в новый файл таблицы `FIXES`
    (`pipeline/ingest/fixes/batch_duplicate_resolve_<дата>.py`) и
    применяется штатным `review.py --write` — резолвер не проверяет
    дословность сам, а зовёт `review.check()` напрямую: один исполнитель
    правил, а не вторая копия проверки.
  - **`separate`** — действительно другая сделка на том же активе:
    кандидату ставится `separate_transaction_reviewed=True` (та же метка,
    что уже использует `match.match()` для этого класса пар), а черновик
    отпускается — резолвер сам вызывает `promote.to_card()`/`new_id()`/
    `link_parties`, то есть ровно тот путь, которым прошёл бы черновик,
    не сработай `near_duplicate()`.
  - **`unclear`** — читающий сам прочитал и не смог решить (источники
    противоречат друг другу, кандидат сам неполон). ЕДИНСТВЕННЫЙ исход,
    доходящий до консоли, — и туда идёт прочитанное обоснование
    читающего, а не вопрос «это дубль?».

**Граница.** `resolve_duplicates.py` не судит о смысле — это делает
читающий. Скрипт не даёт ответу внести выдумку: `--check`/`--apply`
отклоняют ЛЮБОЙ ответ, где цитата не лежит дословно в закэшированном
источнике (`enrich`) или событие того же вида с тем же текстом у
кандидата уже есть (`new_stage`), причём (тем же принципом, что у
`review.py`: «есть отклонённые правки — не пишем НИЧЕГО») весь пакет
ответов отклоняется целиком, если хоть один из них не проходит проверку.

**Чего это не решает.** Задача #115 (консольная кнопка) снята с очереди —
она чинила симптом (нажатие после того, как человек уже нашёл дубль
сам), а не причину; отдельная кнопка больше не нужна, потому что человек
не должен находить дубль сам. Полный цикл (промоут → очередь → чтение →
apply) ещё не прогонялся на живом потоке — первый реальный прогон стоит
проверить особенно внимательно, тем же правилом, что уже записано для
любого долго запертого шага: «первый реальный проход стоит проверять
особенно внимательно, а не считать „раз тормоз стоял — значит, за ним
всё в порядке"».

## Модерация притока (5 августа 2026)

Новые карточки НЕ попадают в базу напрямую. Консоль основателей — Telegram-
группа (env `TELEGRAM_REVIEW_GROUP_ID`; без неё — личные сообщения каждому из
`TELEGRAM_REVIEW_CHAT_IDS`). `send_drafts.py` шлёт туда ТРИ типа сообщений:
  * 📣 `[пост <id>]` — проект поста канала. Кнопки «пост в канал»/«без поста»
    (вердикты post_yes/post_no — модификатор канала, НЕ судьба карточки) и ✏️;
    ответ своим текстом заменяет пост и одобряет карточку (approve+edited);
  * 🗂 `[карточка <id>]` — поля + `#/preview/<id>`. Кнопки «✅ Опубликовать»/
    «✋ Придержать»/«✏️ Изменить»/«🗑 Выкинуть» (approve/hold/—/discard);
    discard сильнее таймаута молчания: карточка не выйдет ни на сайт, ни в
    канал и исчезает из очереди насовсем (нероссийский контур, не-сделки);
    ✏️ — НЕ вердикт, кнопка только подсказывает ответить текстом; ответ —
    ЗАМЕТКА (note): её потребляет ТОЛЬКО суточная рутина притока, читает
    `pipeline/ingest/read_notes.py` и применяет через `review.py` (для
    сырья — строит карточку тем же путём, что кнопка «в работу»);
  * ⚠️ `[сырьё <draft_id>]` — черновик, который ворота НЕ пропустили, с
    причиной. Кнопки «это сделка — в работу» (take: `approve.py` превращает в
    карточку предпросмотра и сразу шлёт по ней 📣+🗂) / «не сделка» (drop:
    запоминается в `data/inbox/moderation_state.json`, больше не показывается).
Кнопка/ответ приходят вебхуком на сайт -> таблица `moderation_decisions` ->
почасовая рутина забирает по `/api/moderation/decisions?token=…`
(`MODERATION_TOKEN`, по умолчанию `TELEGRAM_WEBHOOK_SECRET`) и применяет
`approve.py`. Молчание сутки — карточка выходит как есть; СЫРЬЁ по молчанию
не публикуется никогда (ворота его не пропустили — молчание не делает его
сделкой). Решение дописывается в само сообщение группы («— ✅ Одобрено
(Борис)»), чтобы второй человек видел, что первый уже нажал. `/queue` в боте
показывает три блока теми же значками.

Почему так: решение принимает человек в Telegram, вебхук приходит на сайт, а
применяет решение рутина в одноразовом контейнере, которому база сайта
недоступна (приватная сеть) — таблица + API единственный мост. Молчание —
согласие, потому что немой шаг, держащий весь поток, уже был (тормоз E9).
pending.json живёт в git: не закоммитить его — потерять очередь модерации.

НОВАЯ КАРТОЧКА ВЫХОДИТ НА САЙТ УЖЕ ВЫЧИТАННОЙ (с 4 сентября 2026, см. «Три
рутины»): в прогоне публикации сразу после `approve.py --write` запускается
`python3 pipeline/proofread.py --queue` — он печатает невычитанные карточки
базы, обычно ровно те, что только что перешли из очереди модерации (чаще
всего список пуст, шаг стоит одну команду). До 10 карточек за прогон:
саб-агент с «Правилами для редактора» из `pipeline/PROOFREADING_ROUTINE.md`
переписывает прозаические поля (файл `data/inbox/proofread/<дата>-pub.json`),
`--check`, один раунд переделки, `--write`; карточка без правок — в
`--mark-clean`. Изменения едут в тот же коммит прогона, до отправки постов.

Уроки первого дня консоли (6 августа 2026):
- **Ссылка на предпросмотр работает только после деплоя.** Сообщения с
  `#/preview/<id>` ушли в группу ДО того, как pending.json доехал до сайта, —
  и 20 минут владелец видел «только плашку» вместо карточки. Правильный
  порядок в рутине: коммит и push pending.json -> дождаться деплоя ->
  send_drafts. Страховка в коде: `site_pending_ids()` в send_drafts читает
  pending.json С САЙТА и откладывает карточки, которых там ещё нет
  (строка «Отложено карточек: N»).
- **Одна новость в двух изданиях — одно сообщение в группу.** Рижский вокзал
  пришёл из Ведомостей и Коммерсанта двумя черновиками; promote помечает
  второй `dup_in_batch` (общее название в кавычках среди придержанных одной
  партии), send_drafts его не шлёт. Вторая ссылка дописывается источником
  через review.py. Держит тест
  `test_same_story_from_two_outlets_is_one_console_message`.
- **Правила именования новых карточек — мягкие, и только для новых.**
  Заголовок не копирует дословно заголовок источника; в заголовке узнаваемый
  бренд, а не юрлицо (юрлицо — внутри карточки); вместо «крупнейший
  производитель X» — настоящее имя из статьи. Старые карточки под эти правила
  НЕ переименовываются (решение владельца). Правил про недвижимость не
  добавлять — даже жилая бывает значимой; нероссийский контур без российского
  элемента не публикуем.
- **Заголовок сделки называет бренд, `buyer`/`seller_id` — конкретное
  юрлицо, а не наоборот.** Просьба владельца 18 августа: «Яндекс купил
  завод» в заголовке — это правильно и даже лучше для читателя (бренд
  узнаваем), даже если по факту стороной сделки было ООО «Яндекс Заводы».
  Но карточка КОМПАНИИ, на которую ведёт плашка сторон, обязана быть именно
  этим конкретным юрлицом — тем, кто реально приобрёл долю, а не группой
  целиком: тот же принцип, что уже применён к УГМК-Инвест/УГМК и
  Экспанте/Ультиматек (см. лесенку уроков про `holding` выше). С профиля
  конкретного юрлица читатель переходит по бейджу «Входит в группу» на
  профиль группы и видит ТАМ её показатели — это и есть назначение
  двусторонней связи `holding`, которую починили в тот же день: не
  косметика, а ровно тот путь навигации, который владелец описал. Смешивать
  роли нельзя ни в одну сторону: писать `buyer` на профиль группы, когда
  известно конкретное юрлицо, — та же ошибка, что и заголовок с ЕГРЮЛ-именем
  вместо бренда, только в другом поле.

### Как владелец решает — записано 7 августа 2026, для консоли и для будущей автоматизации

Цель, которую владелец назвал прямо: «Компас» должен стать профессиональной
платформой уровня Mergermarket, и со временем сам решать, какую сделку
добавлять, а какую нет. Пока это решение принимает человек в консоли — но
решение не произвольно, у него есть логика, и её стоит записывать по мере
того, как она проявляется на реальных карточках. Ниже — не код-правило (оно
слишком контекстно-зависимо для регулярки), а материал для того, кто решает:
человек в консоли сегодня, промпт рутины притока завтра.

- **Жилая недвижимость — почти всегда мимо, но не по правилу «недвижимость
  мимо».** Владелец отклоняет почти все карточки о продаже квартир, домов,
  отдельных зданий, усадеб — «если какой-то физик просто купил, всё равно».
  Пропускает — если покупатель или предмет сам по себе значим: крупная
  компания, известный актив, сумма или сторона, о которой стоит написать
  отдельно от факта самой сделки с недвижимостью. Это НЕ повод завести признак
  «отрасль = недвижимость → отклонить»: такое правило противоречило бы уже
  записанному уроку выше (жилая бывает значимой) и один раз уже привело бы к
  потере настоящей сделки. Правильное место для этого критерия — подсказка
  тому, кто решает («физлицо купило X, крупных сторон не видно — обычно
  отклоняется»), а не тормоз на входе.
- **Нероссийский контур с российским бенефициаром — это НЕ нероссийский
  контур.** «Если узбекская компания купила другую узбекскую компанию, но
  выяснилось, что это актив какого-то российского олигарха — надо не
  пропускать, а делать карту.» Гейт `russian_evidence()` в `promote.py` уже
  правильно устроен для этого: он отправляет такие черновики на решение
  человека (⚠️ в консоли), а не отклоняет молча — важно НЕ менять это на
  автоотказ. Но решающий (человек сегодня, промпт рутины завтра) обязан перед
  тем, как нажать «не сделка», проверить конечного бенефициара, а не только
  формальные стороны из заголовка — иначе именно такая карточка потеряется.
- **Названия карточек, компаний и разделов — «user friendly», это отдельная
  проверка, не побочный эффект точности.** Формулировка может быть фактически
  верной и всё равно звучать неестественно, канцелярски или переведённой с
  другого языка. Проверка «звучит ли это как живая русская фраза, а не как
  результат работы с данными» — отдельный шаг обзора, наравне с проверкой
  фактов; см. также правило чуть выше «пояснение объясняет смысл числа, а не
  устройство базы» — тот же класс урока, только про заголовки и подписи, а не
  про цифры.
- **Профили компаний — источник неровности качества, которую владелец
  замечает первой.** Разные карточки компаний писались в разное время разными
  методами (правила, ручной ввод, заглушки); из-за этого тон и глубина прыгают
  от карточки к карточке. Это не разовая правка, а постоянная работа: у базы
  1872 профиля и вручную написанное описание есть меньше чем у трети (см.
  журнал `pipeline/write_company_descriptions*.py`). Ориентир при следующем
  профиле — не просто «что делает компания», а тон и длина такие же, как у уже
  написанных сильных примеров (Сбербанк, Яндекс), не выдумывая ничего сверх
  общеизвестного рода занятий.
- **Превосходная степень — не сама по себе штамп; штамп — превосходная степень
  без меры.** Профессиональные базы (Crunchbase и похожие) советуют вычищать
  «лучший», «ведущий», «самый» — первая реакция «вычистить всё такое слово»
  была бы неверной. Замер по базе (7 августа): 18 профилей со словом
  «крупнейший»/«ведущий», и 17 из них называют ПРОВЕРЯЕМУЮ меру — «Крупнейший
  частный банк России» (Альфа-Банк, уточнение «частный» отличает его от
  Сбербанка), «крупнейший в стране банк сельхозземель по площади» (Био-Тон,
  мера прямо в тексте) — это не штамп, а полезный факт о масштабе. Настоящий
  штамп нашёлся один — «Ведущий российский разработчик…» (Технорэд): «ведущий»
  без ответа на вопрос «по чему» (`pipeline/fix_vague_superlative_descriptions.py`).
  Признак «есть превосходная степень» — повод прочитать конкретное
  предложение, а не правило для сплошной чистки; родня урока «признак дефекта
  — повод прочитать, а не основание стереть».
- **Симптом, починенный трижды в трёх разных файлах, — сигнал, что чинили не
  корень.** Прямые кавычки вместо « » в title/buyer_name/asset правили
  вручную три раза за две недели — `fix_straight_quotes.py` (2 августа, 12
  карточек), `fix_new_card_titles_batch3.py` (8 августа: «та же болезнь, в
  новых карточках снова»), `fix_straight_quotes_batch1.py` (16 августа, ещё
  4 карточки). Каждый раз чинили СЛЕДСТВИЕ (уже записанные карточки), ни разу
  — ПРИЧИНУ: `build()` в `draft.py` копировал `title` из статьи дословно, а
  статьи набраны прямыми кавычками, и `clean_name()` не нормализовала стиль
  извлечённых имён сторон. Починено 16 августа на входе, а не на выходе:
  `normalize_quotes()` в `draft.py` красит прямые кавычки в « » при сборке
  ЛЮБОГО нового черновика (title и, через `clean_name()`, buyer_name/asset/
  seller), `review.py`'s `check()` отдельно отказывает в правке этих же
  полей через `--write`, если в `new` остались прямые кавычки (энрич может
  принести дефект тем же путём, что и приток), а `test_data.py`'s
  `test_no_straight_quotes_in_structural_fields` — забор с третьей стороны:
  ловит регресс по ЛЮБОМУ пути записи, включая тот, о котором мы ещё не
  думали. Общее правило: если один и тот же класс дефекта чинится больше
  одного раза, следующий вопрос — не «где ещё почистить», а «где он
  ВОЗНИКАЕТ», и правка идёт туда, плюс тест на всю базу, а не на
  прочитанные карточки.

У группы-консоли (Telegram) с 4 сентября 2026 — три темы: «Подтверждение
постов», «Обновления», «Общая информация». Номер темы бот узнаёт командой
`/topic` внутри неё (кнопки доходят даже при включённой приватности бота) —
Bot API не даёт список тем, единственный источник — служебное сообщение или
явная команда. `pipeline/console_topics.py` — общая точка входа для адреса
консоли и номера темы; `thread_id('decision'|'update'|'info')` решает, куда
уйдёт сообщение. Тот же модуль умеет пережить смену `chat_id` группы (супергруппа
при включении тем — это ВСЕГДА новый chat_id) через событие `my_chat_member`.

## Вход по заявке — гейт на этапе закрытого тестирования (2 сентября 2026)

Просьба владельца: «как в Автопосте» — посетитель без входа видит вместо сайта
блок «Войти / Запросить доступ», заявка уходит владельцам в Telegram, вход
открывается после одобрения. «Потом уберём» — поэтому всё собрано так, чтобы
снять одной строкой.

- **Включить/выключить:** `ACCESS_GATE` в `main.py` — `os.environ.get(
  "ACCESS_GATE", "1") == "1"`, по умолчанию ВКЛЮЧЕНО (на Timeweb переменной
  нет — гейт работает). Выключить: `ACCESS_GATE=0` в окружении боевого хоста
  или поменять умолчание `"1"` на `"0"` в одной строке. Гейт визуальный: API
  сделок и компаний не закрываются, закрыт только вход в аккаунт.
- **Что делает сервер.** `/api/me` отдаёт `gate` (и `approved` для вошедшего);
  `POST /api/auth/register` при включённом гейте создаёт `User.approved=False`,
  НЕ ставит сессию, отвечает `{"ok": true, "pending": true}` и шлёт заявку в
  консоль (`_notify_access_request`: `_review_chat_ids()` + `tg_api`, кнопки
  `acc:<user_id>:ok|no`; сбой Telegram регистрацию не роняет); `POST
  /api/auth/login` для неодобренного — 403 с `GATE_PENDING_TEXT`. Одобрение —
  ветка `acc:` в `telegram_webhook` рядом с `mod:`: право по `from.id`
  (`_is_reviewer`), решение пишется ПРЯМО в `users` (аккаунты живут в базе
  сайта, рутина не нужна), штамп в сообщение через `_mark_decided`
  (`acc_ok`/`acc_no`). Отклонённый остаётся с `approved=False`: повторная
  заявка тем же адресом — «уже зарегистрирована», дубля нет.
- **Миграция.** `_ensure_user_columns(engine)` в `main.py` (вынесена из
  стартового хука) добавляет `approved` через инспектор SQLAlchemy и ставит
  `True` всем уже существующим аккаунтам отдельным `UPDATE` с параметром
  (не `DEFAULT TRUE`/`DEFAULT 1` — литералы расходятся между SQLite и
  Postgres). Тест на «старой» таблице —
  `test_users_table_created_before_the_gate_gets_approved_column_set_to_true`.
- **Экран.** `renderGate()` в `static/index.html`: `GATE`/`gated()` рядом с
  `ME`; `route()` до первого ответа `/api/me` не рисует ничего (иначе сайт
  мелькает перед дверью — `refreshMe()` сам зовёт `route()` после первого
  ответа), при закрытом гейте рисует гейт и НЕ перерисовывает его на
  повторных вызовах (смена хеша, приход базы) — форму нельзя стирать; адрес
  при этом сохраняется, после входа тот же `route()` открывает его. Шапка и
  футер остаются; `updTop()` считает гейт «не главной» (светлая шапка).
  Общий `authRequest()` обслуживает и гейт, и экран «Аккаунт».
- **Тесты.** `conftest.py` ставит `ACCESS_GATE=0` для всех тестов;
  тесты гейта включают его через `monkeypatch.setattr(main, "ACCESS_GATE",
  True)` (`test_accounts.py`) или вторым сервером `gated_url` с `ACCESS_GATE=1`
  (`test_ui.py`, один сквозной тест). Урок из этого теста: `page.goto` на ТОТ
  ЖЕ адрес с тем же хешем — переход по фрагменту, страница не
  перезагружается и состояние формы остаётся; для чистого старта нужен
  `page.reload()`.
- **Страховка от потерянной заявки — шаг прогона публикации.** Уведомление
  о заявке шлёт сам сайт, и его сбой регистрацию НЕ роняет (заявка важнее
  уведомления) — значит, заявка может лежать на сайте, а в консоли о ней
  никто не узнает; человек будет ждать доступа молча. Каждый прогон
  публикации вызывает `python3 pipeline/send_access_requests.py --write`:
  он берёт ожидающих через тот же `/api/access/requests?token=…` и шлёт по
  каждому сообщение с кнопками «Одобрить»/«Отклонить». Показанное помнится в
  `pipeline/access_requests_sent.json` (в git), поэтому почасовой шаг не
  превращается в ежечасное напоминание об одной и той же заявке; повторить
  вручную — `--again`. Id для кнопок берётся ИЗ ОТВЕТА БОЕВОГО САЙТА: 4
  сентября 2026 кнопка с id из локальной базы одобрила на проде совсем
  других людей.
- **Что не сделано.** Письма заявителю не шлём (SMTP нет) — экран честно
  говорит «вход по этим данным заработает, обычно в течение дня». Когда гейт
  снимут, `approved` можно оставить: он ни на что, кроме гейта, не влияет.

## Границы разговора ассистента — гейт, а не строка в промпте (19 сентября 2026)

Партнёр (Ксюша) и Артём прогнали боевого ассистента по «неудобным»
вопросам, и он: собрал компромат на ВТБ и на реальную юрфирму с именем
живого юриста (источники — анонимные каналы и сайты жалоб), назвал
конкретную сделку в ответ на «какие сделки совершены в нарушение закона»,
прочитал лекцию про нотариальное удостоверение ДКП и пересказал прогнозы
аналитиков по акциям Сбербанка. Реакция партнёра: «Ему надо как-то
заблочить всю эту херню».

**Дефект был не в формулировке промпта.** Решение «отвечать ли на этот
вопрос вообще» не принимал НИКТО: оно оставалось внутри модели, рядом со
строкой «от тебя ждут вывод, а не пересказ выдачи». Отказ рождался
недетерминированно, иногда по-английски, и всегда ПОСЛЕ того, как поиск
сходил в интернет, — интерфейс показывал найденные ссылки рядом с отказом.

**Устройство.** `assistant_policy.py` — чистая функция без сети и без
модели: `classify(question) -> Verdict`. Гейт стоит ПЕРВОЙ строкой в трёх
точках входа (`/api/ask`, `/api/assistant/lookup`, `/api/assistant/bench`),
то есть до поиска по базе, до Яндекса и до модели — ни запроса в интернет,
ни денег, ни «источников», которые нечем оправдать. Четыре класса отказа
(компромат, вопрос-обвинение, юрконсультация, инвестсовет), тексты лежат в
одном месте (`ANSWERS`), по-русски, и каждый говорит, с чем ассистент
ПОМОЖЕТ. `SCOPE_RULES` в `SYSTEM_BASE`/`SYSTEM_WEB` — второй рубеж на
формулировку, которой гейт не знает. `looks_like_refusal()` не даёт
подставить источники к отказу, написанному самой моделью. Клиент не рисует
«Ответ помог?» под отказом.

**Границы гейта — намеренные, и их не надо «доделывать».** Он ловит то, что
опознаётся ПО СЛОВАМ намерения, и НЕ пытается распознать «вопрос не по
теме» вообще (песня, знакомства, игры): у таких вопросов нет общего
словаря, регулярка на них даёт ложные отказы живым вопросам о рынке — это
остаётся модели. Гейт, который перестраховывается, ломает продукт тише,
чем гейт, который пропускает лишнее, поэтому замер ложных срабатываний
идёт по вопросам, собранным ИЗ ЖИВОЙ БАЗЫ (имена компаний, отрасли,
заголовки сделок), а не по списку из головы: `test_assistant_policy.py` —
14 реальных вопросов из переписки ловятся, 0 отказов на 600+ законных.

**Общий урок.** Правило, которое должна исполнять модель, — не правило, а
пожелание. То, что обязано выполняться всегда, ставится кодом ДО модели,
ровно как ворота `promote.py` стоят до чтения: механика отвечает за «этого
брать нельзя», чтение (здесь — модель) за «что здесь на самом деле
сказано». И признак, совпадающий со словарём собственного интерфейса,
ловит своих: «досье» просилось в признаки компромата и убрано оттуда,
потому что на странице компании у нас самих стоит ссылка «Полное досье
компании».

**Веб-режим: сначала «Компас», потом сеть.** Просьба Дани в тот же день —
«поиск по интернету убирать не надо, но пусть сначала смотрит карту и
источники, если есть, потом расширяет поиск». `SYSTEM_WEB` теперь называет
порядок работы тремя шагами (что знает «Компас» → чем выдача дополняет и
проверяет → если «Компас» молчит, так и сказать) и оценивает сами
источники: деловое издание, сайт компании, реестр — годятся; анонимные
телеграм-каналы, сайты отзывов и жалоб, форумы — нет.

## Показателей на витрине — пять, остальные под кнопкой (19 сентября 2026)

Реакция владельца на первую версию блока: «слишком много показателей и
выглядит как мусор». Было пятнадцать карточек, у каждой три строки
пояснения, — читатель не находит в этом того, за чем пришёл.

**Что оставлено наверху.** Те числа, которыми компанию описывают в одной
фразе при разговоре о сделке: прибыль до процентов и налога, рентабельность
по ней, оборотный капитал, чистый долг и долг к прибыли (`PRIMARY_KEYS` в
`company_finance.py`). Выручка и чистая прибыль сюда не входят — они уже
стоят выше графиками. Оборотный капитал в этой пятёрке потому, что его
уровень на закрытии обсуждают в каждой второй сделке, а не потому, что он
красивее прочих.

**Остальные десять никуда не делись** — открываются кнопкой «Ещё N
показателей» на том же месте, без перерисовки вкладки. Спрятать и удалить
— разные вещи; разбор глубже одной фразы тоже кому-то нужен, и считается
он по тем же данным.

**Одно исключение из постоянного списка.** «Прибыль не от продаж»
поднимается наверх, когда её больше, чем прибыли от продаж. Это не
украшение: у «Урбантеха» за 2025 год рентабельность по чистой прибыли
выходит 93,6%, и выглядит это выдающимся бизнесом, пока не увидишь, что
почти вся прибыль пришла не от продаж. Предупреждение показывается тогда,
когда есть о чём предупреждать.

**Пояснения тоже режутся.** Оговорка «EBITDA не посчитать, потому что нет
амортизации» стоит общей строкой под блоком и называет нужный показатель
поимённо — повторять её внутри двух карточек значило тратить шесть строк
на то, что читатель уже прочёл ниже.

Общий урок, продолжающий запись про мультипликаторы: строгость и полнота
не отменяют обязанности сделать витрину читаемой, и «показать всё, что
посчитали» — не то же самое, что «показать полезное». Решение, ЧТО стоит
наверху, принимает владелец, а не полнота расчёта.

## Подписки: одна сущность, три условия (19 сентября 2026)

Просьба Дани: «нужно включать функцию подписаться на компанию и на отрасли
если не включена». Разбор показал, что состояние было разным у двух половин.

**Отрасль работала, но называлась не тем.** Подписка на отрасль жила в ленте
сделок под кнопкой «Сохранить подборку», а в кабинете — под заголовком
«Подборки по рынку»; на самой странице отрасли кнопки не было. То есть
функция была, а нажать её там, где ищут, было нельзя.

**Компании не было вовсе.** Сердечко в каталоге писало id в `localStorage` и
обещало «список — в кабинете», хотя кабинет о нём не знал, а рассылка
уведомлений — тем более (подробности — `KNOWN_ISSUES.md`).

**Решение — не четвёртая таблица.** `company_id` добавлен в `SavedFilter`,
туда же, где отрасль, слово и порог суммы: подписка — одна сущность, у
которой условия складываются по И («сделки «Магнита» дороже 5 млрд ₽»).
Отдельная таблица завела бы и вторую ленту, и второй экран, и второе место,
где чинить дедупликацию уведомлений.

**Компания сопоставляется по ID ПРОФИЛЯ, а не по названию.** Подписка по
названию у нас уже есть (`keyword`) и ловит лишнее: «Магнит» находит и
«Магнитогорский металлургический комбинат». Роль в карточке проставлена
ссылкой на профиль (`buyer`, `target`, `seller_id`, `asset_id`) — промахнуться
нечем. Обе стороны закреплены тестом на этой самой паре.

**Что ещё сделано, чтобы функция считалась включённой:** кнопки «Следить за
сделками компании» (профиль компании) и «Следить за сделками отрасли»
(страница отрасли); список в кабинете называет компанию по имени и ведёт
ссылкой на её страницу; подписка на несуществующий профиль отклоняется с
ошибкой, а не принимается молча (иначе человек ждёт писем, которых не
бывает); повторное нажатие сердечка не создаёт вторую подписку; сердечки,
отмеченные до входа, переезжают на сервер при первом входе.

## Заметки от пользователей — приём правок с карточек сделок (19 сентября 2026)

Кнопка «Уточнить или дополнить» на карточке сделки и форма в футере
(`POST /api/deals/{id}/corrections`, `POST /api/corrections`) пишут
в таблицу `correction_requests` боевой базы. До этого дня канал был
write-only: ни один экран, ни один скрипт эту таблицу не читал — заявка
могла годами лежать непрочитанной, единственный способ её увидеть —
прямой SQL-запрос к боевой базе (найдено разбором вопроса партнёра «где
оказывается моё уточнение», Ксюша отправила такое по сделке Positive
Technologies/CyberOK и не получила ответа).

- **Мост для рутины** (та же схема, что у решений модерации и заявок на
  доступ): `GET /api/corrections/pending?token=…` отдаёт необработанные
  заявки (`status="new"`), `POST /api/corrections/consume` УДАЛЯЕТ
  показанные — в отличие от заявок на доступ (те остаются как аккаунты),
  здесь постоянное место текста теперь Telegram, а не эта таблица
  (владелец: «если они засоряют базу данных, то нужно их оттуда убирать»).
- **Тема консоли** — «Заметки от пользователей» (`CONSOLE_TOPIC_NAMES`/
  `pipeline/console_topics.TOPIC_NAMES`, ключ `user_notes`), заведена
  владельцем в тот же день. Название сделки в сообщении берётся из
  `static/data/deals_promoted.json` локального чекаута (с учётом `merged`
  — карточка могла с тех пор слиться с другой), а не с сайта.
- **Скрипт** — `pipeline/send_corrections_to_console.py --write`, шаг
  рутины публикации (без своего расписания — как и `send_access_requests.py`).
- **Ограничение, о которое уже упёрлись.** Текст инструкции у уже
  существующей рутины можно менять только из её же собственной сессии —
  не из соседней. Из-за этого добавление шага в саму рутину публикации
  требует либо действия владельца (правка Routine через интерфейс), либо
  отдельного маленького триггера. Тот же механизм — вероятная причина,
  почему `send_access_requests.py` (см. «Вход по заявке» выше) мог
  перестать реально вызываться рутиной публикации, даже оставаясь описанным
  здесь: не проверено, включить в ближайшую сверку темы.

## Раскрытие ПАО: что можно взять, а что закрыто (разведка 19 сентября 2026)

Просьба владельца: «что надо и там и там, в отношении ПАО на e-disclosure
могут важные вещи раскрываться, которые хорошо бы у нас показывать».
Записываю результат, чтобы это не переоткрывали за токены.

**e-disclosure.ru забрать НЕЛЬЗЯ, и это проверено дважды.** Сайт отвечает
кодом 200 и 374 КБ, но в теле не содержимое, а страница JS-проверки
(ServicePipe): в ответе `cookie_spid`, `<noscript><meta http-equiv="refresh">`,
а слова «раскрытие» нет вовсе. Сначала я решил по коду 200, что сайт
доступен с браузерным заголовком, — это была ошибка, код ответа тут ничего
не говорит (родня урока про catch-all: «200 не значит, что вам ответили по
существу»). Независимо от защиты, `robots.txt` прямо запрещает `/api/*` и
`/Company/Search?*` — то есть поиск по компаниям забирать мы и не вправе.

**Реестр выпусков ЦБ — работает и полезен.** Обычный GET по ИНН:
`https://www.cbr.ru/registries/rcb/ecb/?UniDbQuery.Posted=True&UniDbQuery.SearchType=2&UniDbQuery.SPhrase=<ИНН>`
(`SearchType`: 2 — ИНН, 1 — ОГРН, 3 — наименование, 4 — код эмитента).
Отдаёт ИНН → ОГРН → полное наименование → КОД ЭМИТЕНТА. Проверено на
«Аэрофлоте» (00010-A), «Ростелекоме» (00124-A), «Магните» (60525-P),
МТС (04715-A). Код эмитента — сквозной ключ, которым компания опознаётся на
лентах раскрытия. Выгрузки (xlsx/csv) на этой странице нет, только форма;
годовые xlsx лежат в `/registries/rcb/` и `/vfs/finmarkets/files/supervision/`.

**Сами сделки в реестре ЦБ не лежат** — там только сведения о выпусках.
Сообщения о существенных фактах (смена контроля, крупные сделки, сделки с
заинтересованностью) публикуются на ПЯТИ аккредитованных лентах, и эмитент
раскрывается ТОЛЬКО В ОДНОЙ по договору — зеркал нет. Четыре ленты, кроме
e-disclosure, отдают содержимое обычным запросом
(disclosure.1prime.ru, disclosure.skrin.ru, www.disclosure.ru), но открытого
машинного интерфейса нет ни у одной: RSS у ПРАЙМа выключен (закомментирован
в исходнике), списки документов у СКРИНа подгружаются джаваскриптом. Путь,
который остаётся, — серверная форма поиска ПРАЙМа (ASP.NET WebForms,
windows-1251, с `__VIEWSTATE`, без капчи), плюс такие же обходы остальных.
Это работа на несколько дней, а не одна команда.

**Замер охвата (выборка 60 из 1101 участника сделок с подтверждённым ИНН):**
18 из 60 нашлись в реестре выпусков ЦБ — около 30%, то есть примерно 330
компаний. НО: быть в реестре выпусков и быть обязанным публиковать
существенные факты — РАЗНЫЕ вещи. Любое АО имеет зарегистрированный выпуск
при учреждении; раскрываться на ленте обязан более узкий круг. Прежде чем
строить забор, нужен следующий замер: у скольких из этих компаний вообще
есть страница на одной из пяти лент.

**Чего не делать.** Не пытаться обойти проверку e-disclosure: и технически
это гонка, и robots запрещает прямо. Не считать «есть в реестре выпусков»
синонимом «раскрывает сделки».

**Чем это ценно, если дойдут руки.** Существенный факт — первоисточник от
самой стороны сделки, то есть `attribution: parties` по нашей же
классификации, а не пересказ издания. Для слоя фактов это лучшая цитата,
чем новость, — но и самая узкая: только публичные компании и только то, что
они обязаны раскрыть.

## Незавершённое (бэклог)

- **Финансовые данные компаний (API-ФНС).** Работает: платный ключ куплен,
  реестр решений `pipeline/fns_registry.py` живёт в git (1700+ строк, 1000+
  подтверждено), синхронизация — ежедневным триггером и стартовым сканом на
  проде. Очередь «нужен ИНН» доставляется в консоль почасово.
- **Финансы банков (ЦБ РФ).** Работает: `pipeline/cbr_fetch_bank_summary.py` +
  `pipeline/cbr_sync_bank_finance.py`, блок «По данным Банка России» на
  профиле банка, данные по 17 банкам на день последней проверки, обновляется
  ежедневным триггером.
- **Группы компаний (`holding`).** Механизм готов (ownership из ЕГРЮЛ-
  учредителей, двусторонняя связь «входит в группу»/«в группу входит»), но
  заполнено только у малой части профилей — расширение требует отдельной
  кампании, не одной команды.
- **Автоматический детектор падежных двойников компаний — испробован,
  отклонён.** Порог «общее начало слова от 3 знаков» (как в `review.py` для
  имён внутри одной сделки) даёт на именах РАЗНЫХ компаний 350+ ложных
  срабатываний на общих деловых корнях («Группа» ловит любую «Группу»,
  «Мед» — любую компанию с «мед» в имени). Для такой проверки нужен
  морфологический разбор головы имени (как уже есть в `pipeline/ingest/
  casing.py` для падежа предмета сделки), а не наивное сравнение слов —
  не реализовано.

## Чего не делать

- Не создавать pull request без явной просьбы.
- Не переписывать историю git, не делать `push --force`.
- Не удалять данные массово и не «чистить» профили компаний без разбора: среди
  них есть настоящие активы сделок.
- Не добавлять внешние CDN, шрифты и сервисы — всё должно работать из России.
- Не подменять отсутствующие данные правдоподобными: пустое поле честнее.
